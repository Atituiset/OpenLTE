OpenLTE 源码精读：从入门到进阶

第 1 章 项目总览与构建运行

作为全书的第一章，这一章的目标很朴素：让你知道 OpenLTE 这个仓库每一块是干什么的，能把它编译出来，并亲眼看到 eNodeB 跑起来、用 telnet 连上它的控制台。读完后你应该能在脑子里画出一张"仓库地图"，后面每一章讲到某个文件时，你能立刻知道它在地图上的哪个位置。

1.1 这个仓库是什么

一句话：OpenLTE 是一个用 C++ 写的、可以在普通 PC + SDR（如 USRP B200/B210、bladeRF）上真实运行的 LTE FDD eNodeB，附带一套扫频、录文件、生成测试信号的工具，以及一套 Octave 写的离线物理层接收机。

用你熟悉的东西类比：如果把 LTE 网络想象成一个 Wi-Fi 热点 + 认证服务器，那么这个仓库大致相当于"hostapd + 一个极简 RADIUS，全部塞在一个进程里"，只不过协议栈从 802.11 换成了 3GPP 的 LTE。它不仅能发射信号让手机搜到并附着，还把 MME（移动性管理）、HSS（用户数据库）这些核心网网元简化后嵌进了同一个进程。

README 开宗明义：「OpenLTE is an open source implementation of the 3GPP LTE specifications」（README.md:3）。仓库是 SourceForge 上 openlte 项目的克隆（README.md:5），顶层 CMake 里标着版本 0.20.5（CMakeLists.txt:26）。

需要提前知道的一件事：OpenLTE 没有实现 S1AP。真实网络里 eNodeB 通过 S1 接口连到核心网，OpenLTE 直接把 MME/HSS 做成了进程内的子系统。这对读者反而是好事——少了一层编解码的壳，读协议代码更直接。

1.2 目录树逐层讲解

先看全局，再逐块解释。顶层 CMake 的 add_subdirectory 顺序就是仓库的"成分表"（CMakeLists.txt:160-166）：

add_subdirectory(liblte)
add_subdirectory(libtools)
add_subdirectory(LTE_fdd_dl_file_gen)
add_subdirectory(LTE_fdd_dl_file_scan)
add_subdirectory(LTE_fdd_dl_scan)
add_subdirectory(LTE_file_recorder)
add_subdirectory(LTE_fdd_enodeb)

整个仓库可以分成四类目录：

公共头文件：cmn_hdr/

cmn_hdr/typedefs.h 定义了全项目通用的 uint8、uint32 等类型别名。内容很少，但几乎每个 .cc 都会包含它——类似于你们项目里的 common/types.h。

三个库：liblte、libtools（外加 cmn_hdr）

这是仓库的"内核"，下一节详细讲它们的分工。这里先记住：

  • liblte/：LTE 协议库，RRC / NAS（MME）/ MAC / RLC / PDCP / 安全算法 / 物理层，全部在这里。这是全书精读的重点。
  • libtools/：与协议无关的工具——socket 封装、IPC 消息队列、scoped lock 之类，相当于项目里的 utils/。

五个可执行程序目录

每个目录都有自己的 hdr/、src/ 和 CMakeLists.txt，编译出一个可执行文件：

目录产物干什么用
LTE_fdd_enodeb/LTE_fdd_enodeb主程序：完整的 FDD eNodeB（含简化 MME/HSS/IP 网关）
LTE_fdd_dl_scan/LTE_fdd_dl_scan实时扫频：接 SDR 扫 LTE 下行信号，解出小区信息
LTE_fdd_dl_file_scan/Python 脚本 + 共享库离线扫频：解一个录好的 IQ 采样文件
LTE_fdd_dl_file_gen/Python 脚本 + 共享库生成 LTE 下行 IQ 采样文件（造测试数据）
LTE_file_recorder/LTE_file_recorder把 SDR 收到的原始 IQ 样本录到磁盘

后四个可以类比成抓包工具链：LTE_file_recorder 是 tcpdump（录原始数据），LTE_fdd_dl_file_scan 是离线 Wireshark，LTE_fdd_dl_scan 是在线 Wireshark，LTE_fdd_dl_file_gen 是发包器。

注意 LTE_fdd_dl_file_scan 和 LTE_fdd_dl_file_gen 这两个目录的产物形态不同：它们先把 C++ 部分编成共享库（add_library(... SHARED ...)，见 LTE_fdd_dl_file_scan/CMakeLists.txt:3 和 LTE_fdd_dl_file_gen/CMakeLists.txt:3），再通过 SWIG 包一层 Python 接口，最终用户跑的是 python/ 下的 Python 脚本（LTE_fdd_dl_file_scan/CMakeLists.txt:33）。读这两个目录时看到 .i 文件（SWIG 接口文件）不要惊讶。

octave/：离线物理层参考实现

octave/ 下有 60 多个 .m 文件，是一套 Octave/MATLAB 写的 LTE 下行物理层接收机：同步、信道估计、Turbo 译码、MIB/SIB 解包都有。它不链接任何 C++ 代码，是作者用来验证算法正确性的"参考答案"。README 末尾给了用法（README.md:469-478）：把 Test captures/LTE_test_file_int8.bin 按 int8 读进来、I/Q 交错拆成复数序列，喂给 lte_fdd_dl_receive 就能离线解出小区。

Test captures/

只有一个文件 LTE_test_file_int8.bin，是预先录好的 IQ 采样，专门给 LTE_fdd_dl_file_scan 和 Octave 接收机当输入。没有 SDR 硬件的读者可以用它体验"解出真实 LTE 信号"的过程。

1.3 三个内部库的分工：从 CMakeLists 看依赖关系

想知道一个库里装了什么、谁依赖谁，最可靠的办法不是猜，而是看 CMakeLists 里的 target_link_libraries。

liblte 编出静态库 lte，源文件清单在 liblte/CMakeLists.txt:2-12：

add_library(lte
  src/liblte_common.cc
  src/liblte_interface.cc
  src/liblte_phy.cc
  src/liblte_mac.cc
  src/liblte_rlc.cc
  src/liblte_pdcp.cc
  src/liblte_rrc.cc
  src/liblte_mme.cc
  src/liblte_security.cc
)

这份清单本身就是一张 LTE 协议栈分层图：phy（物理层）→ mac → rlc → pdcp（接入层 L2 三层）→ rrc（无线资源控制，3GPP TS 36.331）和 mme（NAS 消息，TS 24.301）→ security（Milenage 鉴权、EEA/EIA 加解密与完整性，TS 33.401 / 35.206）。liblte_common 和 liblte_interface 是公共基础：前者提供 bit 级的读写原语，后者提供频段、EARFCN 换算等枚举和工具函数。注意 liblte 不链接任何外部库——它是纯协议编解码，与硬件无关，这正是它可以被扫频工具和 eNodeB 同时复用的原因。

libtools 编出静态库 tools（libtools/CMakeLists.txt:2-7）：socket 封装、IPC 消息队列、scoped lock、杂项 helper。它的 include 路径里引了 liblte/hdr（libtools/CMakeLists.txt:8），方向是"工具库依赖协议库的头"，反过来不成立。

可执行程序依赖两个库。以 eNodeB 为例（LTE_fdd_enodeb/CMakeLists.txt:27）：

target_link_libraries(LTE_fdd_enodeb lte fftw3f tools pthread rt ${POLARSSL_LIBRARIES} ${UHD_LIBRARIES} ...)

依赖图一目了然：

LTE_fdd_enodeb ─┬─► lte (liblte)   ── 纯协议，无外部依赖
                └─► tools (libtools) ── 基础设施
LTE_fdd_dl_scan ──► lte + tools     （LTE_fdd_dl_scan/CMakeLists.txt:13）
LTE_file_recorder ─► lte + tools    （LTE_file_recorder/CMakeLists.txt:12）

阅读代码的顺序也可以照这张图来：先 liblte（协议是什么），再 LTE_fdd_enodeb（协议怎么跑起来），libtools 只在碰到 socket/消息队列时回头查。

1.4 构建

依赖

顶层 CMake 会强制检查这些依赖（找不到直接 FATAL_ERROR）：

依赖检查位置用途
Boost（system 组件）CMakeLists.txt:50-69通用 C++ 库
GNURadio ≥ 3.7（RUNTIME/BLOCKS/FILTER/PMT）CMakeLists.txt:91-101SDR 流图框架
GNURadio OsmosdrCMakeLists.txt:103-105osmocom SDR 源块
UHDCMakeLists.txt:107-109Ettus USRP 驱动
LibbladeRFCMakeLists.txt:111-113bladeRF 驱动
FFTW3FCMakeLists.txt:96,115-117单精度 FFT（物理层用）
PolarsslCMakeLists.txt:97加密算法底层实现

对应的 Find*.cmake 都在 cmake/Modules/ 下（如 cmake/Modules/FindPolarssl.cmake），顶层通过 CMAKE_MODULE_PATH 引入（CMakeLists.txt:37）。

编译步骤

就是标准的 out-of-source CMake 流程（README 的安装一节，README.md:156-172）：

sudo apt-get install libpolarssl-dev   # 以及上面表格里的其他依赖
mkdir build
cd build && cmake ..
make
# 可选：sudo make install

编译成功后，build/ 下各子目录里会有 LTE_fdd_enodeb、LTE_fdd_dl_scan、LTE_file_recorder 等可执行文件，liblte/、libtools/ 下是 liblte.a、libtools.a。

常见坑

  • polarssl 已改名 mbedtls。这个代码库年代较早（GNURadio 3.7 时代），新版发行版的软件源里通常没有 libpolarssl-dev，需要装旧版 polarssl 或手工处理头文件/库名差异。这是构建 OpenLTE 时最先撞到的一堵墙。
  • GNURadio 版本：CMake 要求 ≥ 3.7（CMakeLists.txt:92），但代码写的是 3.7 API；太新的 GNURadio（3.9/3.10）头文件和命名空间变化很大，直接编会报一堆错。最省事的组合是 Ubuntu 16.04/18.04 时代的 GNURadio 3.7.x。
  • bladeRF 和 osmosdr 是硬依赖：即使你没有 bladeRF，FindLibbladeRF 找不到也会直接 FATAL_ERROR（CMakeLists.txt:111-113）。不用 bladeRF 的话需要装 libbladerf-dev 或者改顶层 CMake 跳过。
  • 默认 Release 构建：没指定 CMAKE_BUILD_TYPE 时默认 Release（CMakeLists.txt:30-33）。想打断点调试记得 cmake -DCMAKE_BUILD_TYPE=Debug ..。

1.5 最小运行体验：把 eNodeB 跑起来

启动

LTE_fdd_enodeb 的 main 非常短，全部逻辑就三件事（LTE_fdd_enodeb/src/LTE_fdd_enb_main.cc:61-83）：

int main(int argc, char *argv[])
{
    LTE_fdd_enb_interface *interface = LTE_fdd_enb_interface::get_instance();
    LTE_fdd_enb_cnfg_db   *cnfg_db   = LTE_fdd_enb_cnfg_db::get_instance();
    LTE_fdd_enb_hss       *hss       = LTE_fdd_enb_hss::get_instance();

    interface->set_ctrl_port(LTE_FDD_ENB_DEFAULT_CTRL_PORT);
    interface->start_ports();

    // Read configuration
    hss->read_user_file();
    cnfg_db->read_cnfg_file();
    ...
    while(!interface->get_shutdown()) { sleep(1); }
}

逐行看：

  1. get_instance() 三次：interface（控制台）、cnfg_db（配置库）、hss（用户库）都是 singleton，后续各子系统（PHY/MAC/RLC/PDCP/RRC/MME）也是这个模式；
  2. set_ctrl_port + start_ports：起两个 TCP 监听端口；
  3. 读用户文件和配置文件（如果存在）；
  4. 主线程进入 sleep 循环，真正干活的是各子系统自己的线程。

端口号写死在头文件里：LTE_FDD_ENB_DEFAULT_CTRL_PORT 30000，调试端口是控制端口加 1（LTE_fdd_enodeb/hdr/LTE_fdd_enb_interface.h:73-74）。启动后终端打印 Please connect to control port 30000（LTE_fdd_enb_main.cc:75）。

控制台：telnet 30000

新开一个终端（README 的运行一节，README.md:174-211）：

telnet 127.0.0.1 30000

连上后会收到欢迎语 *** LTE FDD ENB *** 和 Type help to see a list of commands（发送逻辑在 LTE_fdd_enodeb/src/LTE_fdd_enb_interface.cc:743-744）。命令分发是一个巨大的 if-else 链，在 LTE_fdd_enb_interface.cc:700-733，支持的全部命令在 handle_help 里打印（LTE_fdd_enb_interface.cc:1173-1200）：

命令作用
read <param> / write <param> <value>读/写配置参数
start / stop / shutdown启动/停止/退出 eNodeB
construct_si重新生成系统消息（SIB）
add_user imsi=... imei=... k=...往 HSS 添加用户（k 是 32 位十六进制的 Ki）
del_user imsi=...删除用户
print_users列出 HSS 里所有用户
print_registered_users列出当前已附着（registered）的用户

可写的参数名定义在 LTE_fdd_enb_param_text 数组里（LTE_fdd_enodeb/hdr/LTE_fdd_enb_interface.h:202-251），常用的有：

  • band、bandwidth、dl_earfcn：频段、带宽（MHz）、下行频点号——这三者决定你的小区在哪个频率上；
  • mcc、mnc：移动国家码/网络码，测试请用 001/01，绝不要冒充真实运营商；
  • n_ant、n_id_cell：天线数、物理小区 ID（PCI）；
  • tx_gain、rx_gain：SDR 收发增益；
  • debug_type、debug_level、enable_pcap：调试输出与抓包开关。

配置库有个很贴心的设计：写 dl_earfcn 时会自动帮你算出对应的 ul_earfcn 和上下行中心频率（LTE_fdd_enodeb/src/LTE_fdd_enb_cnfg_db.cc:201-204），写 bandwidth 时会自动推导 RB 数等一组关联参数（LTE_fdd_enb_cnfg_db.cc:246-272）。所以你只需要设几个"主参数"，剩下的靠联动。

一套典型的发射配置（README 的 Tx Configuration 一节，README.md:213-226）：

write band 20
write bandwidth 5
write dl_earfcn 6300
write mcc 001
write mnc 01
write n_ant 1
write rx_gain 30
write tx_gain 86
start

start 命令会依次拉起 MAC、RLC、RRC、PHY、radio 等各子系统（handle_start，LTE_fdd_enb_interface.cc:971-986 开始）。之后手机搜网就能看到你的小区；add_user 把写好 USIM 卡的用户加进 HSS 后，手机才能真正附着。

调试口：telnet 30001

再开一个终端 telnet 127.0.0.1 30001（README.md:207-211），这是只读的日志输出口：各子系统的 debug 信息都往这里推，包括收发的 RRC/NAS 消息内容。debug_type 和 debug_level 参数控制哪些子系统、哪个级别的信息会打出来。读协议代码时把这个窗口开着，代码和日志对照着看，理解会快很多。

提醒：用 SDR 真实发射信号受当地无线电法规约束，务必在屏蔽环境或合法频段内实验。

小结

  • OpenLTE 是一个单机可跑的 LTE FDD eNodeB（含简化 MME/HSS），外加扫频、录/生成 IQ 文件的工具链和一套 Octave 离线接收机。
  • 仓库结构很规整：cmn_hdr（公共类型）+ liblte（协议库，核心）+ libtools（工具库）+ 五个 LTE_* 可执行程序 + octave/ 参考实现 + Test captures/ 测试采样。
  • 依赖关系从 CMakeLists 就能读出来：liblte 零外部依赖、可复用；可执行程序统一链接 lte + tools（LTE_fdd_enodeb/CMakeLists.txt:27）。
  • 构建是标准 CMake 流程，但要小心 polarssl（已改名 mbedtls）、GNURadio 3.7 API、bladeRF/osmosdr 硬依赖这几个坑。
  • 运行入口极简（LTE_fdd_enb_main.cc:61-83）：起 30000（控制）/30001（调试）两个 telnet 端口，write 配参数、start 启动、add_user/print_users 管理用户。
  • 建议的阅读顺序：先 liblte 摸清协议编解码，再进 LTE_fdd_enodeb 看状态机怎么跑；调试口日志是你最好的对照材料。
