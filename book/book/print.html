OpenLTE 源码精读：从入门到进阶

本书介绍

这是一本以 OpenLTE 源码为教材的 LTE 无线通信系统学习笔记， 面向有软件工程背景、刚入行无线通信的开发者。

OpenLTE 是一套用 C++ 实现的 3GPP LTE 协议栈，包含一个可运行的 FDD eNodeB（基站）、 下行扫频器、IQ 文件录制/生成/扫描工具，以及一套 Octave 离线接收机。 它的代码量不大、没有现代大型项目的层层抽象，非常适合逐行精读—— 你能在这一个仓库里看到从比特流编码（ASN.1 PER / NAS TLV）到状态机、 从 USIM 鉴权到 SDR 收发的完整链路。

本书结构

  • 入门级：不假设任何无线通信背景。先建立 LTE 网络与协议栈的整体认知， 把代码跑起来、把包抓到，最后给出一套"怎么读这套代码"的方法论。
  • 进阶级：逐模块深入源码。RRC 的 ASN.1 uPER 编解码、NAS 的 TLV 编码、 eNodeB 状态机与多线程架构、Milenage/KASME 安全体系、MAC/RLC/PDCP 实现、 物理层与 SDR 应用——每一篇都落实到具体的文件与函数。

阅读建议

  1. 入门级按顺序读；进阶级可以按兴趣挑着读，但建议先读「ASN.1 PER 与 RRC 编解码」 和「NAS 协议与 TLV 编码」这两篇，它们是理解其余一切的钥匙。
  2. 所有代码引用都标注了 文件:行号，建议打开编辑器对照着读。
  3. 文中引用的 3GPP 规范（36.331 / 24.301 / 33.401 / 35.206 等）不必通读， 遇到具体字段时按章节号查阅即可。

第 1 章 项目总览与构建运行

作为全书的第一章，这一章的目标很朴素：让你知道 OpenLTE 这个仓库每一块是干什么的，能把它编译出来，并亲眼看到 eNodeB 跑起来、用 telnet 连上它的控制台。读完后你应该能在脑子里画出一张"仓库地图"，后面每一章讲到某个文件时，你能立刻知道它在地图上的哪个位置。

1.1 这个仓库是什么

一句话：OpenLTE 是一个用 C++ 写的、可以在普通 PC + SDR（如 USRP B200/B210、bladeRF）上真实运行的 LTE FDD eNodeB，附带一套扫频、录文件、生成测试信号的工具，以及一套 Octave 写的离线物理层接收机。

用你熟悉的东西类比：如果把 LTE 网络想象成一个 Wi-Fi 热点 + 认证服务器，那么这个仓库大致相当于"hostapd + 一个极简 RADIUS，全部塞在一个进程里"，只不过协议栈从 802.11 换成了 3GPP 的 LTE。它不仅能发射信号让手机搜到并附着，还把 MME（移动性管理）、HSS（用户数据库）这些核心网网元简化后嵌进了同一个进程。

README 开宗明义：「OpenLTE is an open source implementation of the 3GPP LTE specifications」（README.md:3）。仓库是 SourceForge 上 openlte 项目的克隆（README.md:5），顶层 CMake 里标着版本 0.20.5（CMakeLists.txt:26）。

需要提前知道的一件事：OpenLTE 没有实现 S1AP。真实网络里 eNodeB 通过 S1 接口连到核心网，OpenLTE 直接把 MME/HSS 做成了进程内的子系统。这对读者反而是好事——少了一层编解码的壳，读协议代码更直接。

1.2 目录树逐层讲解

先看全局，再逐块解释。顶层 CMake 的 add_subdirectory 顺序就是仓库的"成分表"（CMakeLists.txt:160-166）：

add_subdirectory(liblte)
add_subdirectory(libtools)
add_subdirectory(LTE_fdd_dl_file_gen)
add_subdirectory(LTE_fdd_dl_file_scan)
add_subdirectory(LTE_fdd_dl_scan)
add_subdirectory(LTE_file_recorder)
add_subdirectory(LTE_fdd_enodeb)

整个仓库可以分成四类目录：

公共头文件：cmn_hdr/

cmn_hdr/typedefs.h 定义了全项目通用的 uint8、uint32 等类型别名。内容很少，但几乎每个 .cc 都会包含它——类似于你们项目里的 common/types.h。

三个库：liblte、libtools（外加 cmn_hdr）

这是仓库的"内核"，下一节详细讲它们的分工。这里先记住：

  • liblte/：LTE 协议库，RRC / NAS（MME）/ MAC / RLC / PDCP / 安全算法 / 物理层，全部在这里。这是全书精读的重点。
  • libtools/：与协议无关的工具——socket 封装、IPC 消息队列、scoped lock 之类，相当于项目里的 utils/。

五个可执行程序目录

每个目录都有自己的 hdr/、src/ 和 CMakeLists.txt，编译出一个可执行文件：

目录产物干什么用
LTE_fdd_enodeb/LTE_fdd_enodeb主程序：完整的 FDD eNodeB（含简化 MME/HSS/IP 网关）
LTE_fdd_dl_scan/LTE_fdd_dl_scan实时扫频：接 SDR 扫 LTE 下行信号，解出小区信息
LTE_fdd_dl_file_scan/Python 脚本 + 共享库离线扫频：解一个录好的 IQ 采样文件
LTE_fdd_dl_file_gen/Python 脚本 + 共享库生成 LTE 下行 IQ 采样文件（造测试数据）
LTE_file_recorder/LTE_file_recorder把 SDR 收到的原始 IQ 样本录到磁盘

后四个可以类比成抓包工具链：LTE_file_recorder 是 tcpdump（录原始数据），LTE_fdd_dl_file_scan 是离线 Wireshark，LTE_fdd_dl_scan 是在线 Wireshark，LTE_fdd_dl_file_gen 是发包器。

注意 LTE_fdd_dl_file_scan 和 LTE_fdd_dl_file_gen 这两个目录的产物形态不同：它们先把 C++ 部分编成共享库（add_library(... SHARED ...)，见 LTE_fdd_dl_file_scan/CMakeLists.txt:3 和 LTE_fdd_dl_file_gen/CMakeLists.txt:3），再通过 SWIG 包一层 Python 接口，最终用户跑的是 python/ 下的 Python 脚本（LTE_fdd_dl_file_scan/CMakeLists.txt:33）。读这两个目录时看到 .i 文件（SWIG 接口文件）不要惊讶。

octave/：离线物理层参考实现

octave/ 下有 60 多个 .m 文件，是一套 Octave/MATLAB 写的 LTE 下行物理层接收机：同步、信道估计、Turbo 译码、MIB/SIB 解包都有。它不链接任何 C++ 代码，是作者用来验证算法正确性的"参考答案"。README 末尾给了用法（README.md:469-478）：把 Test captures/LTE_test_file_int8.bin 按 int8 读进来、I/Q 交错拆成复数序列，喂给 lte_fdd_dl_receive 就能离线解出小区。

Test captures/

只有一个文件 LTE_test_file_int8.bin，是预先录好的 IQ 采样，专门给 LTE_fdd_dl_file_scan 和 Octave 接收机当输入。没有 SDR 硬件的读者可以用它体验"解出真实 LTE 信号"的过程。

1.3 三个内部库的分工：从 CMakeLists 看依赖关系

想知道一个库里装了什么、谁依赖谁，最可靠的办法不是猜，而是看 CMakeLists 里的 target_link_libraries。

liblte 编出静态库 lte，源文件清单在 liblte/CMakeLists.txt:2-12：

add_library(lte
  src/liblte_common.cc
  src/liblte_interface.cc
  src/liblte_phy.cc
  src/liblte_mac.cc
  src/liblte_rlc.cc
  src/liblte_pdcp.cc
  src/liblte_rrc.cc
  src/liblte_mme.cc
  src/liblte_security.cc
)

这份清单本身就是一张 LTE 协议栈分层图：phy（物理层）→ mac → rlc → pdcp（接入层 L2 三层）→ rrc（无线资源控制，3GPP TS 36.331）和 mme（NAS 消息，TS 24.301）→ security（Milenage 鉴权、EEA/EIA 加解密与完整性，TS 33.401 / 35.206）。liblte_common 和 liblte_interface 是公共基础：前者提供 bit 级的读写原语，后者提供频段、EARFCN 换算等枚举和工具函数。注意 liblte 不链接任何外部库——它是纯协议编解码，与硬件无关，这正是它可以被扫频工具和 eNodeB 同时复用的原因。

libtools 编出静态库 tools（libtools/CMakeLists.txt:2-7）：socket 封装、IPC 消息队列、scoped lock、杂项 helper。它的 include 路径里引了 liblte/hdr（libtools/CMakeLists.txt:8），方向是"工具库依赖协议库的头"，反过来不成立。

可执行程序依赖两个库。以 eNodeB 为例（LTE_fdd_enodeb/CMakeLists.txt:27）：

target_link_libraries(LTE_fdd_enodeb lte fftw3f tools pthread rt ${POLARSSL_LIBRARIES} ${UHD_LIBRARIES} ...)

依赖图一目了然：

LTE_fdd_enodeb ─┬─► lte (liblte)   ── 纯协议，无外部依赖
                └─► tools (libtools) ── 基础设施
LTE_fdd_dl_scan ──► lte + tools     （LTE_fdd_dl_scan/CMakeLists.txt:13）
LTE_file_recorder ─► lte + tools    （LTE_file_recorder/CMakeLists.txt:12）

阅读代码的顺序也可以照这张图来：先 liblte（协议是什么），再 LTE_fdd_enodeb（协议怎么跑起来），libtools 只在碰到 socket/消息队列时回头查。

编译步骤

就是标准的 out-of-source CMake 流程（README 的安装一节，README.md:156-172）：

sudo apt-get install libpolarssl-dev   # 以及上面表格里的其他依赖
mkdir build
cd build && cmake ..
make
# 可选：sudo make install

编译成功后，build/ 下各子目录里会有 LTE_fdd_enodeb、LTE_fdd_dl_scan、LTE_file_recorder 等可执行文件，liblte/、libtools/ 下是 liblte.a、libtools.a。

常见坑

  • polarssl 已改名 mbedtls。这个代码库年代较早（GNURadio 3.7 时代），新版发行版的软件源里通常没有 libpolarssl-dev，需要装旧版 polarssl 或手工处理头文件/库名差异。这是构建 OpenLTE 时最先撞到的一堵墙。
  • GNURadio 版本：CMake 要求 ≥ 3.7（CMakeLists.txt:92），但代码写的是 3.7 API；太新的 GNURadio（3.9/3.10）头文件和命名空间变化很大，直接编会报一堆错。最省事的组合是 Ubuntu 16.04/18.04 时代的 GNURadio 3.7.x。
  • bladeRF 和 osmosdr 是硬依赖：即使你没有 bladeRF，FindLibbladeRF 找不到也会直接 FATAL_ERROR（CMakeLists.txt:111-113）。不用 bladeRF 的话需要装 libbladerf-dev 或者改顶层 CMake 跳过。
  • 默认 Release 构建：没指定 CMAKE_BUILD_TYPE 时默认 Release（CMakeLists.txt:30-33）。想打断点调试记得 cmake -DCMAKE_BUILD_TYPE=Debug ..。

1.5 最小运行体验：把 eNodeB 跑起来

启动

LTE_fdd_enodeb 的 main 非常短，全部逻辑就三件事（LTE_fdd_enodeb/src/LTE_fdd_enb_main.cc:61-83）：

int main(int argc, char *argv[])
{
    LTE_fdd_enb_interface *interface = LTE_fdd_enb_interface::get_instance();
    LTE_fdd_enb_cnfg_db   *cnfg_db   = LTE_fdd_enb_cnfg_db::get_instance();
    LTE_fdd_enb_hss       *hss       = LTE_fdd_enb_hss::get_instance();

    interface->set_ctrl_port(LTE_FDD_ENB_DEFAULT_CTRL_PORT);
    interface->start_ports();

    // Read configuration
    hss->read_user_file();
    cnfg_db->read_cnfg_file();
    ...
    while(!interface->get_shutdown()) { sleep(1); }
}

逐行看：

  1. get_instance() 三次：interface（控制台）、cnfg_db（配置库）、hss（用户库）都是 singleton，后续各子系统（PHY/MAC/RLC/PDCP/RRC/MME）也是这个模式；
  2. set_ctrl_port + start_ports：起两个 TCP 监听端口；
  3. 读用户文件和配置文件（如果存在）；
  4. 主线程进入 sleep 循环，真正干活的是各子系统自己的线程。

端口号写死在头文件里：LTE_FDD_ENB_DEFAULT_CTRL_PORT 30000，调试端口是控制端口加 1（LTE_fdd_enodeb/hdr/LTE_fdd_enb_interface.h:73-74）。启动后终端打印 Please connect to control port 30000（LTE_fdd_enb_main.cc:75）。

控制台：telnet 30000

新开一个终端（README 的运行一节，README.md:174-211）：

telnet 127.0.0.1 30000

连上后会收到欢迎语 *** LTE FDD ENB *** 和 Type help to see a list of commands（发送逻辑在 LTE_fdd_enodeb/src/LTE_fdd_enb_interface.cc:743-744）。命令分发是一个巨大的 if-else 链，在 LTE_fdd_enb_interface.cc:700-733，支持的全部命令在 handle_help 里打印（LTE_fdd_enb_interface.cc:1173-1200）：

命令作用
read <param> / write <param> <value>读/写配置参数
start / stop / shutdown启动/停止/退出 eNodeB
construct_si重新生成系统消息（SIB）
add_user imsi=... imei=... k=...往 HSS 添加用户（k 是 32 位十六进制的 Ki）
del_user imsi=...删除用户
print_users列出 HSS 里所有用户
print_registered_users列出当前已附着（registered）的用户

可写的参数名定义在 LTE_fdd_enb_param_text 数组里（LTE_fdd_enodeb/hdr/LTE_fdd_enb_interface.h:202-251），常用的有：

  • band、bandwidth、dl_earfcn：频段、带宽（MHz）、下行频点号——这三者决定你的小区在哪个频率上；
  • mcc、mnc：移动国家码/网络码，测试请用 001/01，绝不要冒充真实运营商；
  • n_ant、n_id_cell：天线数、物理小区 ID（PCI）；
  • tx_gain、rx_gain：SDR 收发增益；
  • debug_type、debug_level、enable_pcap：调试输出与抓包开关。

配置库有个很贴心的设计：写 dl_earfcn 时会自动帮你算出对应的 ul_earfcn 和上下行中心频率（LTE_fdd_enodeb/src/LTE_fdd_enb_cnfg_db.cc:201-204），写 bandwidth 时会自动推导 RB 数等一组关联参数（LTE_fdd_enb_cnfg_db.cc:246-272）。所以你只需要设几个"主参数"，剩下的靠联动。

一套典型的发射配置（README 的 Tx Configuration 一节，README.md:213-226）：

write band 20
write bandwidth 5
write dl_earfcn 6300
write mcc 001
write mnc 01
write n_ant 1
write rx_gain 30
write tx_gain 86
start

start 命令会依次拉起 MAC、RLC、RRC、PHY、radio 等各子系统（handle_start，LTE_fdd_enb_interface.cc:971-986 开始）。之后手机搜网就能看到你的小区；add_user 把写好 USIM 卡的用户加进 HSS 后，手机才能真正附着。

调试口：telnet 30001

再开一个终端 telnet 127.0.0.1 30001（README.md:207-211），这是只读的日志输出口：各子系统的 debug 信息都往这里推，包括收发的 RRC/NAS 消息内容。debug_type 和 debug_level 参数控制哪些子系统、哪个级别的信息会打出来。读协议代码时把这个窗口开着，代码和日志对照着看，理解会快很多。

提醒：用 SDR 真实发射信号受当地无线电法规约束，务必在屏蔽环境或合法频段内实验。

小结

  • OpenLTE 是一个单机可跑的 LTE FDD eNodeB（含简化 MME/HSS），外加扫频、录/生成 IQ 文件的工具链和一套 Octave 离线接收机。
  • 仓库结构很规整：cmn_hdr（公共类型）+ liblte（协议库，核心）+ libtools（工具库）+ 五个 LTE_* 可执行程序 + octave/ 参考实现 + Test captures/ 测试采样。
  • 依赖关系从 CMakeLists 就能读出来：liblte 零外部依赖、可复用；可执行程序统一链接 lte + tools（LTE_fdd_enodeb/CMakeLists.txt:27）。
  • 构建是标准 CMake 流程，但要小心 polarssl（已改名 mbedtls）、GNURadio 3.7 API、bladeRF/osmosdr 硬依赖这几个坑。
  • 运行入口极简（LTE_fdd_enb_main.cc:61-83）：起 30000（控制）/30001（调试）两个 telnet 端口，write 配参数、start 启动、add_user/print_users 管理用户。
  • 建议的阅读顺序：先 liblte 摸清协议编解码，再进 LTE_fdd_enodeb 看状态机怎么跑；调试口日志是你最好的对照材料。

第 2 章 LTE 网络与协议栈入门

上一章你已经把仓库跑起来（或至少知道它由哪些可执行程序组成）。这一章不谈具体编码细节，只做一件事：给你一套坐标系。读完之后，你在仓库里随便点开一个 .cc 文件，都应该能回答两个问题——"这是协议栈里的哪一层？""它扮演 LTE 网络里的哪个角色？"

LTE 的协议文档浩如烟海，但它的分层思想你其实早就见过：它和 TCP/IP 一样是"每层只干一件事、对上提供统一接口"的老套路。下面我们先看网络里有谁，再看栈怎么分层，最后把两者钉到这个仓库的文件上。

2.1 网络角色：UE、eNodeB、EPC

一个 LTE 网络系统里有三大类角色：

+--------+     Uu(无线)     +---------+      S1       +-----------------+
|   UE   | <-------------> | eNodeB  | <-----------> |      EPC        |
| (手机) |                  | (基站)  |               | MME/S-GW/P-GW   |
+--------+                  +---------+               +-----------------+
                                                             | S6a
                                                             v
                                                          +-----+
                                                          | HSS |
                                                          +-----+
  • UE（User Equipment）：用户设备，就是手机或物联网模组，里面插着 USIM 卡。你熟悉的"客户端"。
  • eNodeB（evolved NodeB）：基站。所有跟"无线"沾边的事都归它：发射/接收无线电波形、每毫秒调度空口资源、加解密、维护无线连接状态。你熟悉的"接入点 + 网卡驱动 + 部分协议栈"的合体。
  • EPC（Evolved Packet Core）：核心网，基站背后的机房。内部分工：
    • MME（Mobility Management Entity）：控制面的大脑。管鉴权、附着（Attach）、移动性。它不碰用户数据。
    • S-GW（Serving Gateway）/ P-GW（PDN Gateway）：用户面的水管。UE 的 IP 包从 S-GW 流到 P-GW，再从 P-GW 出公网。P-GW 就是那个给 UE 分 IP 地址的"路由器出口"。
    • HSS（Home Subscriber Server）：用户数据库。存着每个合法用户的 IMSI、根密钥 K、算法选择。鉴权向量（RAND/AUTN/XRES/KASME）由它算出。
  • 接口名先混个脸熟：Uu = UE↔eNodeB 的空中接口；S1 = eNodeB↔EPC；S6a = MME↔HSS。

OpenLTE 的"全家桶"简化

真实网络里 MME、S-GW、P-GW、HSS 是不同机房里的不同设备，之间跑 S1AP、GTP-U、Diameter 这些协议。OpenLTE 做实验用，把 eNodeB 和整个 EPC 塞进了同一个进程 LTE_fdd_enodeb。跨网元的接口全部省掉，换成进程内的函数调用和消息队列。

2.2 控制面 vs 用户面

LTE 的空中接口同时跑两套流量，一句话区分：

控制面是"管连接本身的信令"（谁上线、密钥是什么、给多少资源）；用户面是"真正要传的 IP 数据"。

类比一台跑着 SSH 和 HTTP 的服务器：底下的网卡和 IP 栈是共用的，但上面一个是管理通道、一个是业务流量。LTE 也一样——两套流量在 PDCP/RLC/MAC/PHY 四层共用同一条管道（靠逻辑信道区分），只有顶层不同：

  • 控制面顶层是 NAS，UE 直接和 MME 对话，eNodeB 对 NAS 消息不解码、只透传（相当于帮 UE 和 MME 之间转发信封，不拆信）。
  • 用户面顶层就是普通的 IP 包。

2.3 协议栈分层：从波形到信令

这一节是全章的主干。LTE 空口协议栈从下到上是 PHY → MAC → RLC → PDCP → RRC，RRC 之上再"搭"一层端到端的 NAS。每层先说人话，再给代码锚点。

上行接收方向 ↑                      下行发送方向 ↓
NAS (MME)      ← RRC 透传 →        liblte_mme.cc
RRC            连接管理/系统广播      liblte_rrc.cc
PDCP           加密/完整性/头压缩     LTE_fdd_enb_pdcp.cc
RLC            分段/重组/ARQ         liblte_rlc.cc
MAC            调度/HARQ/复用        liblte_mac.cc
PHY            波形 ⇄ 比特           liblte_phy.cc

仓库的结构很工整：liblte/ 是协议编解码库（纯 C 函数，pack/unpack，相当于"序列化层"），LTE_fdd_enodeb/ 是各层子系统（C++ 类，带线程、消息队列和状态机，相当于"业务逻辑层"）。每层都成对出现，下面按此格式逐层介绍。

PHY（物理层）：波形 ⇄ 比特的 codec

  • 接收什么 / 产出什么：下行把 MAC 层给的传输块编码、调制成 IQ 采样送 SDR；上行把 SDR 采到的波形解调成字节流还给 MAC。
  • 上下层：上接 MAC，下接射频前端（SDR）。
  • 类比：网卡的 PHY 芯片 + DSP 固件——上层只见以太网帧，这里上层只见 MAC PDU。
  • 代码：编解码库 liblte/src/liblte_phy.cc（约 1.4 万行，Turbo 编解码、OFDM、同步全在这里），入口如 liblte_phy_init（liblte/hdr/liblte_phy.h:606）、PDSCH 信道编码 liblte_phy_pdsch_channel_encode（liblte/hdr/liblte_phy.h:888）；子系统是类 LTE_fdd_enb_phy（LTE_fdd_enodeb/hdr/LTE_fdd_enb_phy.h:76），按 1 ms 一拍的 TTI 节拍驱动这些 codec。
  • 本章和本书都不深入 PHY，你只要记住"它是字节流与波形之间的转换器"。

MAC（媒体访问控制层）：每 1 ms 一拍的调度器

  • 职责：调度（这 1 ms 的空口资源分给哪个 UE）、HARQ 混合自动重传、把多条逻辑信道的数据复用进一个 MAC PDU、随机接入（PRACH/RAR）。
  • 类比：一个硬实时的链路层调度器 + 组包器。TTI = 1 ms 是它的死线，每毫秒必须出调度决定。
  • 代码：PDU 组包/解包入口 liblte_mac_pack_mac_pdu / liblte_mac_unpack_mac_pdu（liblte/hdr/liblte_mac.h:374,376），随机接入响应 liblte_mac_pack_random_access_response_pdu（liblte/hdr/liblte_mac.h:455）；子系统是类 LTE_fdd_enb_mac（LTE_fdd_enodeb/hdr/LTE_fdd_enb_mac.h:102）。

RLC（无线链路控制层）：分段与重传

  • 职责：把上层的大 SDU 切成 MAC 调度允许的 PDU 大小（分段/重组），AM 模式下负责确认与重传（ARQ）。
  • 三种模式，类比直接拉满：
    • TM（Transparent）：透传 ≈ 直连，用于广播（MIB/SIB 走它）。
    • UM（Unacknowledged）：分段重组但不确认 ≈ UDP。
    • AM（Acknowledged）：分段重组 + 确认重传 ≈ TCP，信令和大多数数据走它。
  • 代码：liblte_rlc_pack_amd_pdu（liblte/hdr/liblte_rlc.h:308）、liblte_rlc_unpack_umd_pdu（liblte/hdr/liblte_rlc.h:278）；子系统是类 LTE_fdd_enb_rlc（LTE_fdd_enodeb/hdr/LTE_fdd_enb_rlc.h:69）。

PDCP（分组数据汇聚层）：LTE 的"TLS 层"

  • 职责：加密（EEA 算法）、完整性保护（EIA 算法，仅信令）、头压缩（ROHC，OpenLTE 未实现）、顺序交付。一句话：从这层往上（RRC/NAS/IP）全是明文，从这层往下全是密文。
  • 代码：数据 PDU 组包 liblte_pdcp_pack_data_pdu_with_long_sn（liblte/hdr/liblte_pdcp.h:170）；加解密与完整性算法本体在 liblte/src/liblte_security.cc；子系统是类 LTE_fdd_enb_pdcp（LTE_fdd_enodeb/hdr/LTE_fdd_enb_pdcp.h:67）。注意它的 start 签名（同文件 :75）同时挂着 RLC、RRC、GW 六个消息队列——这正是"PDCP 是控制面和用户面交汇点"在代码里的样子。

RRC（无线资源控制层）：无线连接的大管家

  • 职责：广播系统信息（MIB/SIB）、寻呼、RRC 连接的建立/重配/释放、替上层配置下四层（密钥、承载、定时器）、透传 NAS。
  • 类比：一台 PC 和路由器之间的连接管理状态机。它只有两个大状态：RRC_IDLE（没连上，只能听广播）和 RRC_CONNECTED（有专用资源，才能跑 NAS 和数据）。
  • 代码：RRC 消息按逻辑信道分类打包，入口函数成对出现：
// liblte/hdr/liblte_rrc.h:6604-6607  MIB 走 BCH
LIBLTE_ERROR_ENUM liblte_rrc_pack_bcch_bch_msg(LIBLTE_RRC_MIB_STRUCT *mib,
                                               LIBLTE_BIT_MSG_STRUCT *msg);
LIBLTE_ERROR_ENUM liblte_rrc_unpack_bcch_bch_msg(LIBLTE_BIT_MSG_STRUCT *msg,
                                                 LIBLTE_RRC_MIB_STRUCT *mib);

SIB 走 DL-SCH（liblte_rrc_pack_bcch_dlsch_msg，liblte/hdr/liblte_rrc.h:6623），专用信令走 DCCH（liblte_rrc_pack_ul_dcch_msg，liblte/hdr/liblte_rrc.h:6865）。子系统是类 LTE_fdd_enb_rrc（LTE_fdd_enodeb/hdr/LTE_fdd_enb_rrc.h:80）。

  • 看个具体例子感受一下"结构体 ⇄ 比特流"。MIB 的结构体定义只有三个字段：
// liblte/hdr/liblte_rrc.h:6598-6602
typedef struct{
    LIBLTE_RRC_PHICH_CONFIG_STRUCT phich_config;  // PHICH 信道配置
    LIBLTE_RRC_DL_BANDWIDTH_ENUM   dl_bw;         // 下行带宽
    uint8                          sfn_div_4;     // 系统帧号 SFN 的高 8 位

它在空口上的编码布局（3GPP 36.331，MasterInformationBlock）：

字段比特宽度含义
dl-Bandwidth3 bit下行带宽档位（1.4/3/5/10/15/20 MHz）
phich-Config3 bitPHICH 时长 1 bit + 资源 2 bit

这就是 LTE 里最小的广播信息：UE 同步后第一件事就是解出这 24 bit，知道自己所在小区的带宽和帧号。后面的章节会带你从 liblte_rrc_pack_bcch_bch_msg 一路读到比特。

NAS（非接入层）：UE 和 MME 的端到端信令

  • 职责：附着/分离、鉴权、安全模式、跟踪区更新、EPS 承载建立。规范是 3GPP 24.301。
  • 关键特征：NAS 的对话双方是 UE 和 MME，eNodeB 只是透传——前面说过"不拆信的邮差"。这就是为什么 RRC 消息里会有 dedicatedInfoNAS 这种"信封里套信封"的字段。
  • 类比：RRC 是"我和路由器的 PPPoE 会话"，NAS 是"我和运营商认证服务器的 802.1X 对话"。
  • 代码：编解码在 liblte/src/liblte_mme.cc，消息头解析入口 liblte_mme_parse_msg_header（liblte/hdr/liblte_mme.h:2675），Attach Request 的组包/解包 liblte_mme_pack_attach_request_msg（liblte/hdr/liblte_mme.h:2855）；MME 侧的状态机是类 LTE_fdd_enb_mme（LTE_fdd_enodeb/hdr/LTE_fdd_enb_mme.h:77），看它的私有方法列表（parse_attach_request、attach_sm、send_authentication_request，同文件 :108-133）就能直接读出附着流程长什么样。

2.5 无线电承载：SRB 与 DRB

最后补一个贯穿全栈的概念。RRC 配置下层时，不是一句"给这个 UE 开条通道"，而是建一个个 Radio Bearer（无线承载）——每个承载 = 一套 PDCP 配置 + 一套 RLC 配置 + 一条逻辑信道的组合，信令用的叫 SRB，数据用的叫 DRB：

承载RLC 模式用途
SRB0TMCCCH 上的公共信令：RRCConnectionRequest/Setup（建连初期，还没有专用配置）
SRB1AM专用 RRC 信令 + 早期的 NAS 透传
SRB2AMNAS 透传专用（安全激活后才建）
DRB1/2AM/UM用户面 IP 数据

OpenLTE 把"承载"直接建模成一个类 LTE_fdd_enb_rb（LTE_fdd_enodeb/hdr/LTE_fdd_enb_rb.h:195），承载枚举写得很直白：

    LTE_FDD_ENB_RB_SRB2,
    LTE_FDD_ENB_RB_DRB1,
    LTE_FDD_ENB_RB_DRB2,
    LTE_FDD_ENB_RB_N_ITEMS,

每个 rb 对象内部挂着 PDCP/RLC 的配置和 PDU/SDU 队列（如同文件 :240-248 的 queue_pdcp_pdu、get_next_pdcp_sdu 等）。后面读 RRC 建连流程时你会反复看到"为某 UE 新建 SRB1 → SRB2 → DRB1"的调用顺序——那就是 36.331 标准流程在代码里的投影。

小结

  • LTE 网络三大角色：UE、eNodeB、EPC（MME/S-GW/P-GW/HSS）；OpenLTE 把 eNodeB 和整个 EPC 塞进 LTE_fdd_enodeb 一个进程（LTE_fdd_enb_interface.cc:1007-1009），MME、HSS、GW 各有对应类。
  • 控制面管连接（顶层 NAS），用户面管数据（顶层 IP），两者在 PDCP/RLC/MAC/PHY 共用管道。
  • 空口栈自下而上 PHY→MAC→RLC→PDCP→RRC+NAS；仓库里 liblte/ 是 pack/unpack 编解码库，LTE_fdd_enodeb/ 是带状态机的层子系统，每层成对出现。
  • 用你熟悉的栈类比：PHY≈网卡，MAC≈链路层调度，RLC-AM≈TCP，PDCP≈TLS，RRC≈连接管理状态机，NAS≈EAP 认证。
  • SRB0/1/2 传信令、DRB 传数据，代码里统一建模为 LTE_fdd_enb_rb（LTE_fdd_enodeb/hdr/LTE_fdd_enb_rb.h:85-91,195）。

第 3 章 信令面入门：RRC 与 NAS

前两章我们看了仓库结构和协议栈分层。这一章正式开始碰协议本身：LTE 控制面（信令面）上最重要的两个协议——RRC 和 NAS。

先给你一张地图，免得在后面的消息名词里迷路：

  • RRC（Radio Resource Control，36.331）：UE 和 eNodeB 之间的协议。管的是"连接"——小区怎么选、无线信道怎么配、什么时候加密。
  • NAS（Non-Access Stratum，24.301）：UE 和核心网 MME 之间的协议。管的是"身份和业务"——你是谁（IMSI）、是不是合法用户（鉴权）、给你分什么 IP 承载。

一个粗略但有用的类比：RRC 像 TCP，负责把"连接"这条管道架起来；NAS 像跑在这条管道上的 HTTP+OAuth，负责登录、发 token、开通业务。NAS 消息没有自己的空口通道，它被 RRC 消息当货物一样驮着走——这一点本章会反复看到。

OpenLTE 里这两个协议的编解码分别在两份头文件里定义：

  • RRC：liblte/hdr/liblte_rrc.h（6870 行，所有 RRC 消息的结构体和 pack/unpack 函数声明）
  • NAS：liblte/hdr/liblte_mme.h（4252 行，所有 NAS 消息的结构体和函数声明）

一、广播阶段：MIB 和 SIB 是基站的"开门招牌"

UE 一开机，还谁都不认识，它做的第一件事是扫频、同步，然后被动地听广播。基站不停循环广播两类系统消息：

  • MIB（Master Information Block）：每 40 ms 在 PBCH 上播一次，只有 24 个比特。内容是"我是 LTE 小区、下行带宽多少、PHICH 怎么配、当前帧号是多少"。
  • SIB1（System Information Block Type 1）：内容是"我属于哪些运营商（PLMN）、跟踪区码（TAC）是多少、允不允许接入"。UE 靠它做小区选择——相当于看到招牌上写着运营商名字，决定要不要进这家店。

MIB 的结构体定义在 liblte/hdr/liblte_rrc.h:6598：

typedef struct{
    LIBLTE_RRC_PHICH_CONFIG_STRUCT phich_config;  // PHICH 配置
    LIBLTE_RRC_DL_BANDWIDTH_ENUM   dl_bw;         // 下行带宽
    uint8                          sfn_div_4;     // 系统帧号 / 4
}LIBLTE_RRC_MIB_STRUCT;

字段布局（3GPP 36.331）：

字段比特宽度含义
dl_bw3 bit下行带宽枚举：n6/n15/n25/n50/n75/n100 对应 1.4/3/5/10/15/20 MHz
phich_config3 bitPHICH 时长（1 bit）+ PHICH 资源（2 bit）
sfn_div_48 bit系统帧号 SFN 的高 8 位
spare10 bit预留，填 0

加起来正好 24 bit。它的打包函数 liblte_rrc_pack_bcch_bch_msg 在 liblte/src/liblte_rrc.cc:12966，你可以看到代码就是把上表逐字段写进比特流，没有任何"类型标签"：

liblte_rrc_pack_phich_config_ie(&mib->phich_config, &msg_ptr);   // 行 12979

SIB1 比 MIB 信息量大多了，结构体 LIBLTE_RRC_SYS_INFO_BLOCK_TYPE_1_STRUCT 在 liblte/hdr/liblte_rrc.h:5736，里面装着 plmn_id（运营商列表）、tracking_area_code、cell_barred（是否禁止接入）、q_rx_lev_min（最低接入电平）这些小区选择的依据。对应的打包函数声明在 liblte/hdr/liblte_rrc.h:5758，实现在 liblte/src/liblte_rrc.cc:10758。

这一阶段 UE 完全是"听众"，没发过一个比特。听懂了 MIB + SIB1，它才知道该往哪儿喊话。

二、RRC 连接建立：LTE 版三次握手

UE 决定接入某个小区后，要先把 RRC 连接建起来。三步，和 TCP 三次握手几乎一一对应：

步骤消息方向类比 TCP
1RRCConnectionRequestUE → eNodeBSYN
2RRCConnectionSetupeNodeB → UESYN+ACK
3RRCConnectionSetupCompleteUE → eNodeBACK

第 1 步，RRCConnectionRequest：UE 自报家门。结构体在 liblte/hdr/liblte_rrc.h:5976：

typedef struct{
    LIBLTE_RRC_CON_REQ_UE_ID_UNION     ue_id;       // S-TMSI 或随机数
    LIBLTE_RRC_CON_REQ_UE_ID_TYPE_ENUM ue_id_type;  // 用哪种 ID
    LIBLTE_RRC_CON_REQ_EST_CAUSE_ENUM  cause;       // 建立原因
}LIBLTE_RRC_CONNECTION_REQUEST_STRUCT;
  • ue_id：一个二选一——老用户给 S-TMSI（上次附着时网络发的临时身份证），新用户只能给一个 40 bit 随机数。选哪种由 ue_id_type 标记（枚举定义在 liblte/hdr/liblte_rrc.h:5945）。
  • cause：建立原因，比如 MO_SIGNALLING（我要发信令）、MO_DATA（我要传数据）、EMERGENCY（紧急呼叫），枚举在 liblte/hdr/liblte_rrc.h:5952。

整条消息只有 64 bit，打包函数在 liblte/src/liblte_rrc.cc:11596。

第 2 步，RRCConnectionSetup：基站答应接入，并给 UE 配置好 SRB1（Signaling Radio Bearer，信令无线承载——你可以理解为"信令专用的管道配置"）。结构体 LIBLTE_RRC_CONNECTION_SETUP_STRUCT 在 liblte/hdr/liblte_rrc.h:5925，核心就是一个 rr_cnfg（无线资源配置）。

第 3 步，RRCConnectionSetupComplete：UE 确认。重点来了——这条消息里夹带了第一条 NAS 消息。结构体在 liblte/hdr/liblte_rrc.h:5902：

typedef struct{
    LIBLTE_RRC_REGISTERED_MME_STRUCT registered_mme;   // 上次注册的 MME
    LIBLTE_BYTE_MSG_STRUCT           dedicated_info_nas; // ← NAS 消息塞在这
    uint8                            rrc_transaction_id;
    uint8                            selected_plmn_id;
    bool                             registered_mme_present;
}LIBLTE_RRC_CONNECTION_SETUP_COMPLETE_STRUCT;

注意 dedicated_info_nas 的类型是 LIBLTE_BYTE_MSG_STRUCT——一个字节容器（定义在 liblte/hdr/liblte_common.h:76），而 RRC 自己用的是比特容器 LIBLTE_BIT_MSG_STRUCT（liblte/hdr/liblte_common.h:71）。这个类型差异就是两种编码风格在代码里的投影，本章最后会展开。

到这里，"连接"架好了，接下来的戏全是 NAS 的。

三、NAS 附着：类比 OAuth 颁 token

附着（Attach）是 UE 向核心网"注册开机"的完整流程。把它类比成 OAuth 很好懂：

Attach 步骤OAuth 类比
Attach Request（报 IMSI）用户点"用 XX 登录"，带上身份
Authentication Request/Response（RAND/AUTN 挑战应答）输入密码/验证码，证明你是你
Security Mode Command/Complete握手完成，切到 HTTPS，后续全加密
Attach Accept（发 GUTI + 建默认承载）颁发 token + 开通会话

NAS 消息的类型编号在 liblte/hdr/liblte_mme.h:2619 起的一整段 #define 里，挑本条主线的几条：

#define LIBLTE_MME_MSG_TYPE_ATTACH_REQUEST            0x41  // 行 2619
#define LIBLTE_MME_MSG_TYPE_ATTACH_ACCEPT             0x42  // 行 2620
#define LIBLTE_MME_MSG_TYPE_ATTACH_COMPLETE           0x43  // 行 2621
#define LIBLTE_MME_MSG_TYPE_AUTHENTICATION_REQUEST    0x52  // 行 2633
#define LIBLTE_MME_MSG_TYPE_AUTHENTICATION_RESPONSE   0x53  // 行 2634
#define LIBLTE_MME_MSG_TYPE_SECURITY_MODE_COMMAND     0x5D  // 行 2639
#define LIBLTE_MME_MSG_TYPE_SECURITY_MODE_COMPLETE    0x5E  // 行 2640

对应的消息结构体也都在同一个文件里：

  • LIBLTE_MME_ATTACH_REQUEST_MSG_STRUCT：liblte/hdr/liblte_mme.h:2819。里面装着 eps_mobile_id（IMSI 或 GUTI）、ue_network_cap（UE 支持的加密算法清单）、esm_msg（嵌套的一条 ESM PDN Connectivity Request），外加十几个带 _present 标志的可选字段——是 NAS 里最复杂的消息。
  • LIBLTE_MME_AUTHENTICATION_REQUEST_MSG_STRUCT：liblte/hdr/liblte_mme.h:2914。极简，只有三样：nas_ksi（密钥序号）、rand[16]、autn[16]——后两个就是网络发给 UE 的"挑战"，UE 用 USIM 卡里的密钥算出应答。
  • LIBLTE_MME_SECURITY_MODE_COMMAND_MSG_STRUCT：liblte/hdr/liblte_mme.h:3252。网络告诉 UE"从这条消息之后，我们改用这套算法加密 + 完整性保护"。
  • LIBLTE_MME_ATTACH_ACCEPT_MSG_STRUCT：liblte/hdr/liblte_mme.h:2707。核心是 guti（新发的临时身份，以后不用明着报 IMSI 了）和 tai_list（跟踪区列表），还有嵌套的 esm_msg（激活默认承载，相当于"给你分 IP"）。

还有一个细节值得现在就知道：每条 NAS 消息的第一个字节同时装着安全头类型和协议鉴别符，定义在 liblte/hdr/liblte_mme.h:2611-2618。鉴权完成前是明文（PLAIN_NAS），完成后头字节标记改为"加密 + 完整性保护"——这就是上面"切 HTTPS"在字节层面的体现。

四、全景：UE 从开机到能上网

把前面三节串起来，完整时序如下（OpenLTE 的 eNodeB 把 MME/HSS 的角色也模拟在进程内部）：

 UE                          eNodeB (OpenLTE 进程)
  │                               │
  │◄══ MIB / SIB1 (广播，一直发) ══│   ① 选小区：听"招牌"
  │                               │
  │── RRCConnectionRequest ──────►│   ② RRC 三次握手
  │◄───── RRCConnectionSetup ─────│     （类比 TCP SYN/SYN+ACK/ACK）
  │── RRCConnectionSetupComplete ►│     内嵌 NAS: Attach Request
  │     {NAS: AttachRequest}      │
  │                               │   ③ 鉴权：挑战-应答
  │◄═ DLInformationTransfer ══════│     （类比 OAuth 验证身份）
  │   {NAS: AuthenticationReq}    │
  │═ ULInformationTransfer ══════►│
  │   {NAS: AuthenticationResp}   │
  │                               │   ④ NAS 安全模式：切"HTTPS"
  │◄═ {NAS: SecurityModeCommand} ═│
  │═ {NAS: SecurityModeComplete} ►│
  │                               │   ⑤ RRC 重配置：建数据承载 DRB
  │◄═ RRCConnectionReconfig ══════│     内嵌 NAS: Attach Accept
  │   {NAS: AttachAccept}         │     （发 GUTI ≈ 颁 token）
  │═ RRCConnectionReconfigCompl ► │
  │═ {NAS: AttachComplete} ══════►│   ⑥ 附着完成确认
  │                               │
  │◄══════ IP 数据包（用户面）════►│   可以上网了

注意 DL/UL Information Transfer 这两条 RRC 消息：它们是 NAS 的"快递箱"——NAS 消息没有自己的空口通道，在空口上全靠这两条 RRC 消息里的 dedicated_info_nas 字段透传，RRC 层只看箱子不拆包裹。

五、RRC 和 NAS 的分工

一句话总结：RRC 管"连接"，NAS 管"身份和业务"。

维度RRC（36.331）NAS（24.301）
对端UE ↔ eNodeBUE ↔ MME（核心网）
管什么小区选择、无线承载、空口加密附着、鉴权、身份、IP 承载
状态机IDLE / CONNECTEDDeregistered / Registered
消息载体直接走空口逻辑信道被 RRC 消息透传
类比TCP（连接管理）HTTP + OAuth（会话与身份）

在 OpenLTE 里这条分界线非常清晰：liblte_rrc.cc 是纯 RRC 编解码，liblte_mme.cc 是纯 NAS 编解码，两者只通过 dedicated_info_nas 这个字节缓冲区交接。

六、预告：两套编码风格

最后留个钩子。RRC 和 NAS 虽然都是"结构体 → 字节流"，但用了两套截然不同的编码：

  • RRC 用 ASN.1 uPER：比特对齐，没有 tag、没有 length，字段一个挨一个按比特塞进流里。原因一句话：空口上每个比特都占频谱、耗功率，省到极致是刚需。所以 MIB 能压到 24 bit，RRCConnectionRequest 只有 64 bit。
  • NAS 用 TLV/IEI：字节对齐，可选字段前带一字节类型标签（IEI），变长字段带一字节长度。原因一句话：NAS 的消息体是驮在 RRC 里的，不直接占用"按比特计费"的空口资源，不必抠到比特级，换取的是好解析、好扩展。

这就是为什么本章前面看到 dedicated_info_nas 用字节容器而 RRC 自己用比特容器。两套编码怎么逐字段写、怎么逐字段拆，是**进阶级第 1 章（ASN.1 uPER）和第 2 章（NAS TLV）**的主菜。

小结

  • RRC（36.331）管 UE 与 eNodeB 之间的"连接"，NAS（24.301）管 UE 与 MME 之间的"身份和业务"；NAS 消息由 RRC 消息透传。
  • 广播阶段 UE 只听不说：MIB（24 bit，liblte/hdr/liblte_rrc.h:6598）给带宽和帧号，SIB1（liblte/hdr/liblte_rrc.h:5736）给 PLMN 和接入门槛。
  • RRC 连接建立是三条消息（Request / Setup / SetupComplete），类比 TCP 三次握手；第三条里已经夹带了 NAS Attach Request。
  • NAS 附着 = Attach Request → Authentication → Security Mode → Attach Accept，类比 OAuth 的验证身份、加密、颁 token；消息类型编号集中在 liblte/hdr/liblte_mme.h:2619 起。
  • RRC 用比特对齐的 ASN.1 uPER，NAS 用字节对齐的 TLV；容器类型 LIBLTE_BIT_MSG_STRUCT / LIBLTE_BYTE_MSG_STRUCT 就是这个差异在代码里的投影，细节见进阶级第 1、2 章。

2. 实验二（无硬件）：把 eNodeB 起起来，玩转 telnet 控制台

这是本章的正菜。先泼一点冷水也说一点好消息：没有 SDR，eNodeB 不仅能起控制台，整个协议栈都能 start——因为 radio 层内置了一个"假电台"。

启动

终端 A：

./LTE_fdd_enodeb/LTE_fdd_enodeb

预期输出（见 LTE_fdd_enodeb/src/LTE_fdd_enb_main.cc:74-75）：

*** LTE FDD ENB ***
Please connect to control port 30000

main 函数干的事很少：设置控制端口、启动端口监听、读用户文件和配置文件，然后就进 while(!shutdown) sleep(1) 主循环（LTE_fdd_enb_main.cc:67-80）。端口号是写死的常量：控制口 30000，调试口是它的偏移 +1，即 30001（LTE_fdd_enodeb/hdr/LTE_fdd_enb_interface.h:73-74）。

没有 SDR 时能走到哪一步？看源码，不猜

radio 层在枚举设备时，永远把 no_rf 放在第一位（LTE_fdd_enodeb/src/LTE_fdd_enb_radio.cc:1213-1215），然后才是 USRP（find_usrps，第 1218 行）和 bladeRF（第 1221 行）。一台什么设备都没有的机器上只有 1 个 radio，于是默认选中 no_rf（第 1226-1232 行）。

no_rf 的 setup() 直接返回成功（第 173-176 行），receive() 里用 nanosleep 按 1ms 的节奏驱动 PHY——相当于一个打拍子的节拍器，让协议栈空转（第 183-199 行）。所以结论是：没有 SDR，start 命令可以成功，RRC/MME/PDCP/RLC/MAC/PHY 各层线程全部拉起，只是没有任何信号真的发出去。

控制台练习

终端 B：

telnet 127.0.0.1 30000

连上后会收到 *** LTE FDD ENB *** 和 Type help to see a list of commands 两行欢迎语（LTE_fdd_enb_interface.cc:743-744）。所有命令的分发都在 handle_ctrl_msg 里（LTE_fdd_enb_interface.cc:690-734），就是一串 msg.find(...) 匹配——你完全可以把它当成命令的"权威清单"。help 打印的完整命令表在第 1191-1200 行：

  • start / stop / shutdown / construct_si / help
  • add_user imsi=<imsi> imei=<imei> k=<k> / del_user imsi=<imsi> / print_users / print_registered_users

参数读写是 read <param> 和 write <param> <value> 两种格式，可写参数注册在构造函数的 var_map 里（LTE_fdd_enb_interface.cc:155-188）。依次练这几条（与 README 的 Tx Configuration 一致，README.md:215-226）：

write band 20
write bandwidth 5
write dl_earfcn 6300
write mcc 001
write mnc 01
write tx_gain 86
read band
read dl_earfcn
help

每条命令成功返回 ok，失败返回 fail "..."。几个有校验逻辑、值得知道的细节：

  • bandwidth 只接受 1.4/3/5/10/15/20 六个值（LTE_fdd_enb_interface.cc:1383-1389），输个 7 试试，会吃 fail。
  • dl_earfcn 必须在当前 band 的 EARFCN 范围内（第 1449-1455 行），所以先 write band 再 write dl_earfcn，顺序反了会被拒。
  • mcc 必须正好 3 位、mnc 是 2 或 3 位数字（第 1476-1480 行）。
  • 有些参数是只读的（比如 ul_earfcn、dl_center_freq，var_map 里 read_only 标记，第 158-160 行），对它们 write 会得到 fail。

注册用户到内置 HSS（README 的样例，README.md:450）：

add_user imsi=001010000000001 imei=000000000000001 k=00112233445566778899AABBCCDDEEFF
print_users
del_user imsi=001010000000001

add_user 会严格校验：IMSI/IMEI 必须 15 位十进制、K 必须 32 位十六进制（LTE_fdd_enb_interface.cc:1298-1318），格式不对直接 fail "invalid param"。

最后输入 start——因为选中的是 no_rf，它会返回 ok，handle_start 把 13 条层间消息队列和全部协议层拉起来（LTE_fdd_enb_interface.cc:991-1028）。stop 收起，shutdown 退出整个程序。

日志端口

终端 C（可选）：

telnet 127.0.0.1 30001

连上即收到 *** LTE FDD ENB DEBUG INTERFACE ***（LTE_fdd_enb_interface.cc:776-780）。之后协议栈的调试消息会持续刷在这里，每行带时间戳、级别（radio/phy/mac/.../iface）和 文件名:行号（格式拼装在第 368-384 行）——这个行号就是你跳回源码的钩子，看到不懂的日志，按图索骥即可。

失败了去哪查：

  • telnet: Unable to connect —— eNodeB 进程没在跑，或 30000 被占用。
  • write 返回 fail "out of bounds" / fail "invalid param" —— 对照上面列的校验分支找原因。
  • start 返回 fail 且你确实没插 SDR —— 用 read selected_radio_name 确认选中的是不是 no_rf；不是就 write selected_radio_idx 0。

法律红线：只在屏蔽箱/屏蔽线缆环境或合法许可频段内发射。绝不要使用商用运营商的 MCC/MNC 和频段对外发射（README 也明确警告了这一点，README.md:466）。

4. 实验四：Wireshark 看基站内部消息

eNodeB 运行期间会把 MAC 层 PDU 以 mac-lte-framed 格式写进本地 pcap 文件 /tmp/LTE_fdd_enodeb.pcap（DLT=147，即 DLT_USER 的 User 0；LTE_fdd_enb_interface.cc:506-534），前提是把 pcap 开关打开：

write enable_pcap 1

每条记录前会拼一个 15 字节的 mac-lte-framed 上下文头——方向、RNTI 类型（P-RNTI/RA-RNTI/SI-RNTI/C-RNTI 的判定在第 595-610 行）、子帧号、CRC 状态——然后才是 payload（LTE_fdd_enb_interface.cc:564-661）。配置 Wireshark（README，README.md:228-231）：

  1. Edit → Preferences → Protocols → DLT_USER → Edit…
  2. 点 +，设置 DLT = User 0 (DLT=147)，Payload protocol = mac-lte-framed
  3. 打开 /tmp/LTE_fdd_enodeb.pcap（或 tail 这个文件实时看）

有 UE（真手机或 srsUE）附着上来后，你能逐层展开：MAC PDU → 内嵌 RLC PDU → 内嵌 PDCP PDU → RRC / NAS 消息。Wireshark 自带 LTE-RRC 和 NAS-EPS 解析器，会把 ASN.1 PER 解码成字段树——这就是把第 3、4 章纸上读的字段，在真实数据流里用眼睛过一遍。哪怕没有 UE，只要 eNodeB start 了，广播的 SIB 也会以 SI-RNTI 出现在抓包里。

失败了去哪查：抓不到包先看 read enable_pcap 是否为 1；Wireshark 里显示成乱码，多半是 DLT 映射没配（User 0 ↔ mac-lte-framed）；pcap 文件在程序每次启动时被重写，注意先 start 再看。

小结

  • 离线实验零门槛：LTE_fdd_dl_file_scan.py（GNU Radio 流图）或 octave/lte_fdd_dl_receive.m，用 Test captures/LTE_test_file_int8.bin 就能看到 PSS → SSS → MIB → SIB1 全过程。
  • 没有 SDR 也能完整练习 eNodeB 控制台：radio 层的 no_rf 假电台让 start 都能成功，协议栈空转（LTE_fdd_enb_radio.cc:1213-1215）。
  • 控制台命令的权威清单在 handle_ctrl_msg（LTE_fdd_enb_interface.cc:690-734）：read/write/start/stop/shutdown/construct_si/help/add_user/del_user/print_users/print_registered_users，参数校验细节也在同一文件里。
  • 30000 口是控制、30001 口是日志；日志行尾的 文件名:行号 是跳回源码的捷径。
  • Wireshark 配置只有一步关键操作：DLT_USER 的 User 0 映射到 mac-lte-framed，配合 write enable_pcap 1 和 /tmp/LTE_fdd_enodeb.pcap。
  • 真发射只在屏蔽环境进行，永远不用商用 MCC/MNC。

第 5 章 源码阅读指南：拿到任何一条消息，知道从哪下手

前面四章你已经在协议层面认识了 LTE，也跑过实验。这一章不讲新协议，只讲方法：面对 OpenLTE 这样一个 C 风格 C++、多线程、横跨物理层到核心网的代码库，怎样才能"拿到任何一条消息，就知道从哪断点、往哪追"。这是入门级和进阶级之间的桥——进阶级各章会深入某个模块，但找路的工具全在这一章。

5.1 代码风格速览：先适应作者的"方言"

OpenLTE 是 2012 年起由 Ben Wojtowicz 个人维护的项目，风格非常统一，统一到你读完一个文件就能猜中其他文件长什么样：

  • C 风格 C++。类几乎只当命名空间用，真正的数据全是 typedef struct 和 typedef enum，函数之间靠指针传结构体。你熟悉的"对象持有状态、方法操作状态"在这里变成了"Singleton 持有状态、自由函数搬数据"。
  • 固定宽度类型不用 <stdint.h>，而是自己定义。打开 cmn_hdr/typedefs.h:50-57，全仓库的整数类型就这几行：
typedef char               int8;
typedef unsigned char      uint8;
typedef short              int16;
typedef unsigned short     uint16;
typedef int                int32;
typedef unsigned int       uint32;
typedef long long          int64;
typedef unsigned long long uint64;

所以看到 uint32 不要去找标准头文件，它就是这里的"本地话"。

  • 命名约定非常机械，这对你反而是好事：
    • 结构体 / 枚举类型名全大写加 _STRUCT / _ENUM 后缀，如 LIBLTE_BIT_MSG_STRUCT、LTE_FDD_ENB_MESSAGE_TYPE_ENUM；
    • 变量名走匈牙利式简写：N_bits（比特数）、N_plmn_ids（PLMN 个数）、msg_ptr（游标指针），N_ 开头一律表示"数量"；
    • 每个枚举末尾都有一个 XXX_N_ITEMS 哨兵值，紧跟一个同名 xxx_text[][] 字符串表用于打印日志，例如 LTE_fdd_enb_message_type_text（LTE_fdd_enodeb/hdr/LTE_fdd_enb_msgq.h:130）。调试时看到 [N_ITEMS] 字样就知道那是数组长度而不是合法取值。
  • 头文件注释里常见 Document Reference: 36.101 v11.2.0 Section 5.5 这样的规范指针（如 liblte/hdr/liblte_interface.h:62）。读代码时优先信这个注释，直接翻到对应 3GPP 文档对照，比猜字段含义快得多。

5.2 两个核心数据结构：全仓库的消息都装在它们里面

整个仓库，比特级的协议消息只有两种"集装箱"，定义在 liblte/hdr/liblte_common.h:68-76：

typedef struct{
    uint32 N_bits;
    uint8  msg[LIBLTE_MAX_MSG_SIZE];
}LIBLTE_BIT_MSG_STRUCT;

typedef struct{
    uint32 N_bytes;
    uint8  msg[LIBLTE_MAX_MSG_SIZE];
}LIBLTE_BYTE_MSG_STRUCT;

三行看明白：

  1. msg 是一个定长数组（LIBLTE_MAX_MSG_SIZE 为 5512，见 liblte/hdr/liblte_common.h:54），不是动态分配——这很嵌入式，换来的是无内存碎片、无生命周期管理问题；
  2. LIBLTE_BIT_MSG_STRUCT 里 msg 的每个字节只装一个比特（0 或 1），N_bits 记录有效比特数。RRC、MAC 这类按比特打包的协议用它；
  3. LIBLTE_BYTE_MSG_STRUCT 则是普通字节流，NAS、IP 数据用它。

你可以把它类比成 Linux 内核的 sk_buff：内核里所有网络包都装在 sk_buff 里流动，各层只管往头上加/剥自己的头；这里所有空口消息都装在 BIT/BYTE_MSG_STRUCT 里流动，各层只管 pack/unpack 自己那一段。区别是 sk_buff 是链式动态结构，这里是定长数组加长度字段——更简单，也更浪费内存，但教学友好。

配套的"螺丝刀"只有两把，也在同一个头文件里声明（liblte/hdr/liblte_common.h:87-97）：liblte_value_2_bits() 把一个整数按指定比特数写进缓冲区并推进游标，liblte_bits_2_value() 反向读出。看一个真实用法——SIB1 的打包（liblte/src/liblte_rrc.cc:10774-10780）：

// Optional indicators
liblte_value_2_bits(sib1->p_max_present, &msg_ptr, 1);
liblte_value_2_bits(sib1->tdd,           &msg_ptr, 1);
liblte_value_2_bits(non_crit_ext_opt,    &msg_ptr, 1);

// Cell Access Related Info
liblte_value_2_bits(csg_id_opt,           &msg_ptr, 1);
liblte_value_2_bits(sib1->N_plmn_ids - 1, &msg_ptr, 3);

注意第二个参数是 uint8 **——函数内部会推进 msg_ptr，所以一连串调用天然按顺序排列出 ASN.1 PER 编码的比特流。这就是为什么 OpenLTE 的 RRC 编解码能手写：PER 对齐规则被简化成"一个字段一次调用"。这段对应 36.331 中 SystemInformationBlockType1 的开头字段，进阶级第 1 章会完整拆解。

实用结论：想追一条消息的生命周期，先问它装在哪个集装箱里。凡是函数签名里出现 LIBLTE_BIT_MSG_STRUCT *msg 的，就是空口比特消息的打包/解包点；出现 LIBLTE_BYTE_MSG_STRUCT *msg 的，就是 NAS 或用户面数据的出入口。

5.3 架构三件套：Singleton + 消息队列 + 每模块一线程

eNodeB 进程内部的组织方式只有三条规则，记住它们就拿到了全图的钥匙。

规则一：每个模块一个 Singleton

所有模块类都长一个样：get_instance() 拿全局唯一实例，cleanup() 销毁。以配置数据库为例，LTE_fdd_enodeb/hdr/LTE_fdd_enb_cnfg_db.h:111-113：

// Singleton
static LTE_fdd_enb_cnfg_db* get_instance(void);
static void cleanup(void);

构造函数是私有的（同文件 142 行），实例指针是静态成员（141 行）。实现侧的懒加载加锁模式在 LTE_fdd_enodeb/src/LTE_fdd_enb_interface.cc:111-120，所有模块照抄这份。后果是：任何函数想摸任何模块，随时 XXX::get_instance() 就行，不存在依赖注入，也没有构造顺序问题——你在代码里看到一长串 get_instance() 调用（比如 LTE_fdd_enb_interface.cc:973-979 一次领了 mac/rlc/rrc/phy/radio/timer_mgr 六家的实例），不要惊讶，这就是本仓库的"依赖注入容器"。

cnfg_db 值得单独记住：它是全基站的"配置中心"，MIB/SIB1~SIB8 全存在它里面（LTE_fdd_enb_cnfg_db.h:68-102 的 LTE_FDD_ENB_SYS_INFO_STRUCT）。任何"这个参数哪来的"的问题，答案几乎都在它身上。

规则二：模块之间只通过消息队列通信

层与层之间没有函数调用，全部走 LTE_fdd_enb_msgq。消息的类型系统是教科书式的"tagged union"，在 LTE_fdd_enodeb/hdr/LTE_fdd_enb_msgq.h：

  • LTE_FDD_ENB_MESSAGE_TYPE_ENUM（80-129 行）：消息类型枚举，注释按"谁→谁"分组，比如 LTE_FDD_ENB_MESSAGE_TYPE_PUSCH_DECODE 标着 // PHY -> MAC Messages——这张枚举表就是整张协议栈的数据流向图；
  • LTE_FDD_ENB_MESSAGE_UNION（324-370 行）：所有消息体的 union；
  • LTE_FDD_ENB_MESSAGE_STRUCT（372-376 行）：信封 = 类型 + 目的层 + union。

队列本身极其朴素（LTE_fdd_enodeb/src/LTE_fdd_enb_msgq.cc）：一个容量 100 的 boost::circular_buffer（95 行），send() 就是加锁 push 再 post 信号量（154-157 行），接收侧是每个队列一条 receive_thread，sem_wait 阻塞等消息、取出后回调（207-224 行）：

// Wait for a message
sem_wait(&msgq->msg_sem);
sem_wait(&msgq->sync_sem);
...
msg = msgq->circ_buf->front();
msgq->circ_buf->pop_front();
...
switch(msg.type)
{
case LTE_FDD_ENB_MESSAGE_TYPE_KILL:
    not_done = false;
    break;
default:
    msgq->callback(msg);
    break;
}

类比一下：这就是你熟悉的消息总线/actor 模型，只是用 POSIX 信号量徒手实现——每条队列一个 actor 线程，消息按值拷贝进环形缓冲区，发完即忘。

规则三：用启动顺序把三件套串起来

进程入口 LTE_fdd_enodeb/src/LTE_fdd_enb_main.cc:61-82 短得可以全文背诵：拿三个 Singleton（interface、cnfg_db、hss），开控制端口，读配置，然后 while(!interface->get_shutdown()) sleep(1); 睡死。main 线程什么都不干，真正的启动在用户连上控制端口敲 start 之后，进入 LTE_fdd_enb_interface::handle_start()（LTE_fdd_enb_interface.cc:971）。它的顺序是：

  1. 先建 13 条消息队列，每条都有名字（LTE_fdd_enb_interface.cc:992-1004）：phy_to_mac、mac_to_rlc、rrc_to_mme……名字即拓扑；
  2. 构造不走 Singleton 的三个类 pdcp、mme、gw（1007-1009 行）；
  3. cnfg_db->construct_sys_info() 生成 MIB/SIB（1012 行）；
  4. 逐层 start()，把队列指针发下去（1021-1027 行）：phy->start(mac_to_phy_comm, phy_to_mac_comm, ...)、rrc->start(pdcp_to_rrc_comm, mme_to_rrc_comm, ...)——每个模块 start 时 attach_rx 挂回调，自己的线程就跑起来了；
  5. 最后 radio->start() 开 SDR 射频（1028 行）。

读完这段，你已经能默写整张架构图：每个模块一条线程，线程之间是带名字的队列，队列里流动的是第 5.2 节的两种集装箱。追任何一条消息的路线因此是机械动作：在枚举表里找到消息类型 → 看注释里的"谁→谁" → 去发送方搜 send(LTE_FDD_ENB_MESSAGE_TYPE_XXX → 去接收方搜对应的 handle_xxx 回调。

ASN.1 PER 与 RRC 编解码

这是全书最重的一章。入门级第三章你已经知道"RRC 消息在空口上是按比特紧凑编码的"；本章我们直接打开 liblte_rrc.cc 这个一万三千行的文件，把它的编码原理、骨架结构和三条代表性消息全部拆开。读完你应该能做到两件事：拿一支笔在纸上把一条 MIB 或 RRCConnectionRequest 逐比特拆出来；改代码给某条 RRC 消息加一个字段而不破坏整条消息。

1. uPER 规则速成：把它当成"超紧凑的 protobuf"

36.331 用 ASN.1 描述 RRC 消息的结构，但空口上传的是 PER（Packed Encoding Rules） 编码后的比特流，OpenLTE 处理的是其中的 unaligned 变种（uPER）——字段之间不向字节边界对齐，一个 3 比特字段紧跟着一个 5 比特字段，正好填满一字节，零浪费。

你熟悉的 protobuf 是 (tag, type, length, value) 的字节流：每个字段都要自报家门。uPER 的思路完全相反——schema（ASN.1 定义）双方都有，凡是能从 schema 推断的信息全部不传输：

protobuf 里要传的东西uPER 里怎么办
tag（字段编号）不传。字段顺序由 ASN.1 定义固定，按顺序读
length（字段长度）多数不传。有界整数 INTEGER (a..b) 直接用 ⌈log2(b−a+1)⌉ 比特
字段类型不传。双方都知道
oneof 选了哪一支传一个 ⌈log2(分支数)⌉ 比特的 choice 选择子
optional 字段在不在传 1 比特的存在标志（preamble 位图）

额外的三条规则，后面代码里会反复出现：

  • extension bit（扩展位）：ASN.1 类型带 ...（可扩展标记）时，PER 先写 1 个比特表示"本条消息是否使用了扩展形态"。OpenLTE 永远写 0，即只用 Release 8/9 的基础形态。
  • optional bitmap（可选位图）：一个 SEQUENCE 里有 N 个 OPTIONAL/DEFAULT 字段，就在正文字段之前先连续写 N 个比特，每个比特是一个字段的"在不在"。
  • 有界整数直接用最短比特数：比如 ENUMERATED {n6, n15, n25, n50, n75, n100, spare2, spare1} 共 8 个值，3 比特搞定，没有填充。

一句话记忆：uPER = 双方共享 schema 的前提下，按定义顺序往一根比特流里塞值，能省的全省。代价是解码方必须严格按同一顺序读——错一位，后面全错位。这也是为什么本章后面要反复强调"pack 和 unpack 必须逐行对称"。

OpenLTE 没有用 asn1c 这类代码生成器，整个 PER 编解码是手工写的 C 代码。对读代码的人这是好事：所有规则都摊在你面前，没有生成器的黑盒。

2. 比特工具层：整个 codec 的"加法器"

2.1 容器：一个字节存一个比特

RRC 消息的容器定义在 liblte/hdr/liblte_common.h:68-71：

typedef struct{
    uint32 N_bits;
    uint8  msg[LIBLTE_MAX_MSG_SIZE];   // LIBLTE_MAX_MSG_SIZE = 5512，见 liblte_common.h:54
}LIBLTE_BIT_MSG_STRUCT;

注意一个反直觉的设计：msg 数组里一个字节只存一个比特（值是 0 或 1）。也就是说一条 24 比特的 MIB 在内存里占 24 个字节。这浪费内存，但换来极大的编码便利：第 i 个比特就是 msg[i]，不用做位运算定位。与之对照，NAS 层用的 LIBLTE_BYTE_MSG_STRUCT（liblte/hdr/liblte_common.h:73-76）才是"一字节就是一字节"的字节容器。在 OpenLTE 里看到 BIT_MSG 就是空口/RRC，看到 BYTE_MSG 就是 NAS——这个习惯能让你在读代码时立刻定位自己在协议栈的哪一层。

2.2 value_2_bits / bits_2_value：MSB-first 怎么落进数组

整个 liblte_rrc.cc 一万三千行，本质上就是反复调用这两个函数。先纠正一个容易找错的地方：它们不在 liblte_interface.cc（那个文件只有 205 行，装的是 EARFCN 与频率互转的查表函数），而是在 liblte/src/liblte_common.cc:62-93：

// liblte/src/liblte_common.cc:62-73
void liblte_value_2_bits(uint32   value,
                         uint8  **bits,
                         uint32   N_bits)
{
    uint32 i;
    for(i=0; i<N_bits; i++)
        (*bits)[i] = (value >> (N_bits-i-1)) & 0x1;   // ①
    *bits += N_bits;                                   // ②
}

// liblte/src/liblte_common.cc:80-93
uint32 liblte_bits_2_value(uint8  **bits,
                           uint32   N_bits)
{
    uint32 value = 0, i;
    for(i=0; i<N_bits; i++)
        value |= (*bits)[i] << (N_bits-i-1);           // ③
    *bits += N_bits;
    return(value);
}

逐行拆这三个关键点：

  • ① MSB-first：value >> (N_bits-i-1) 先取最高位。value=0b101, N_bits=3 写出来是 [1,0,1]，最高有效位在数组低下标处。uPER 规范就是 MSB-first 的，这里严丝合缝。
  • ② 游标前进：参数是 uint8 **bits——指针的指针。函数写完 N 个比特后把调用者的指针向前推 N 格，下一次调用天然接着写。你可以把它理解成 fwrite 内部维护的文件偏移：pack 函数从头到尾不需要自己算偏移量。
  • ③ 镜像操作：unpack 侧用同样的 MSB-first 顺序把比特拼回整数，同样推进游标。

理解了这两个函数，你就拿到了整个 RRC codec 的钥匙：后面所有的 pack 函数都是"按 schema 顺序，对结构体每个字段调一次 value_2_bits（或调用更小的 IE pack 函数）"，unpack 完全镜像。

还有一个全局变量要认识：liblte/src/liblte_rrc.cc:94 的 LIBLTE_BIT_MSG_STRUCT global_msg;。信道级 pack 函数先把具体消息 pack 进这个全局缓冲区，再 memcpy 拼到外层比特流——后面第 4 节会看到它怎么用。

3. 实战一：MIB——24 比特逐字段手工拆解

MIB（Master Information Block）是 eNodeB 每 40 ms 在 PBCH 上广播一次的最小消息，总共 24 比特，是 PER 编码的"Hello World"。

3.1 结构体

liblte/hdr/liblte_rrc.h:6598-6602：

typedef struct{

    LIBLTE_RRC_DL_BANDWIDTH_ENUM   dl_bw;

带宽枚举在 liblte/hdr/liblte_rrc.h:6583-6593：LIBLTE_RRC_DL_BANDWIDTH_6/15/25/50/75/100 分别对应 1.4/3/5/10/15/20 MHz（数字是 RB 数），外加两个 spare，共 8 个值 → 3 比特。PHICH 配置结构体在 liblte/hdr/liblte_rrc.h:2589-2592，两个字段：dur（1 比特，Normal=0/Extended=1）和 res（2 比特，1/6、1/2、1、2 倍四选一）。

3.2 pack 代码逐行讲

liblte/src/liblte_rrc.cc:12966-12994 的 liblte_rrc_pack_bcch_bch_msg：

// DL Bandwidth
liblte_value_2_bits(mib->dl_bw, &msg_ptr, 3);              // ① 3 bit

// PHICH Config
liblte_rrc_pack_phich_config_ie(&mib->phich_config, &msg_ptr); // ② 1+2=3 bit

// SFN/4
liblte_value_2_bits(mib->sfn_div_4, &msg_ptr, 8);          // ③ 8 bit

// Spare
liblte_value_2_bits(0, &msg_ptr, 10);                      // ④ 10 bit

msg->N_bits = msg_ptr - msg->msg;                          // ⑤ 收尾
  • ① 带宽枚举直接落 3 比特。这正是"有界整数最短比特数"规则：8 个枚举值，3 比特，没有别的开销。
  • ② PHICH 是个小 SEQUENCE，复用 IE 级 pack 函数 liblte_rrc_pack_phich_config_ie（liblte/src/liblte_rrc.cc:6470-6485），内部就两行：dur 写 1 比特、res 写 2 比特。注意 IE 函数的签名是 uint8 **ie_ptr——游标照样被推进。
  • ③ sfn_div_4 是系统帧号 SFN 的高 8 位（SFN 共 10 位，低 2 位由 PBCH 的 40 ms 周期隐式给出，这是物理层的事，RRC 只管这 8 位）。
  • ④ 规范里 MIB 固定 24 比特，前面只用了 14 比特，剩下 10 比特是 spare，写 0。
  • ⑤ msg_ptr - msg->msg 得到用过的总比特数填回 N_bits。3+3+8+10 = 24，恒等。

unpack（liblte/src/liblte_rrc.cc:12995-13017）是完全镜像：bits_2_value(&msg_ptr, 3) 读带宽、调 liblte_rrc_unpack_phich_config_ie（liblte/src/liblte_rrc.cc:6486-6501）读 PHICH、再读 8 比特 SFN。注意 unpack 根本不读那 10 个 spare 比特——反正恒为 0，游标推不推到底无所谓，调用方只看前 14 比特。

4. 实战二：BCCH-DL-SCH——SIB1 与 systemInformation 的 choice

4.1 信道级容器是一个 CHOICE

MIB 之上，广播消息走 BCCH-DL-SCH 信道，容器是 LIBLTE_RRC_BCCH_DLSCH_MSG_STRUCT——它在 liblte/hdr/liblte_rrc.h:6621 直接 typedef 成 LIBLTE_RRC_SYS_INFO_MSG_STRUCT，即一个 SIB 数组（sibs[] + N_sibs，见 liblte/hdr/liblte_rrc.h:5811-5818）。

ASN.1 里 BCCH-DL-SCH-Message 的 message 是个二选一 CHOICE：systemInformationBlockType1 或 systemInformation。看 pack 的分发逻辑，liblte/src/liblte_rrc.cc:13028-13074：

{

    liblte_value_2_bits(1, &msg_ptr, 1);            // ② choice 选择子：SIB1 分支
    err = liblte_rrc_pack_sys_info_block_type_1_msg(... &global_msg);  // ③
    ...
    memcpy(msg_ptr, global_msg.msg, global_msg.N_bits);                // ④
    msg->N_bits = global_msg.N_bits + 2;
}else{
    // SIB1 Choice
    liblte_value_2_bits(0, &msg_ptr, 1);            // choice 选择子：SI 分支
    err = liblte_rrc_pack_sys_info_msg(bcch_dlsch_msg, &global_msg);
    ...
}
  • ① 扩展位：BCCH-DL-SCH-Message 的 ASN.1 定义带 ...，所以先写 1 比特，恒 0。
  • ② choice 选择子：两个分支 → 1 比特。这里有个容易看晕的细节：SIB1 分支写 1，SI 分支写 0。原因是 ASN.1 里这个 CHOICE 的第二个分支（systemInformation）是扩展组外的常规分支但 SIB1 排在 choice 的扩展区之后……不必纠结，你只要记住代码里用 sibs[0].sib_type 判分支、比特值与 36.331 的 CHOICE 索引一致即可。这也是手工 PER 的典型坑：选择子比特值必须和规范的分支顺序严格对应。
  • ③ 具体消息先 pack 进全局缓冲 global_msg。
  • ④ 再 memcpy 拼到外层，总比特数 = 内层比特数 + 2（扩展位 + 选择子各 1 比特）。前面还有边界检查：global_msg.N_bits <= LIBLTE_MAX_MSG_SIZE - 2，防止溢出。

unpack（liblte/src/liblte_rrc.cc:13075-13114）镜像：先读 2 个比特判分支，然后把剩余比特整个拷进 global_msg 交给对应的 unpack 函数。SIB1 的 unpack 还会通过 N_bits_used 出参告诉外层"我用了多少比特"（liblte/src/liblte_rrc.cc:13098-13101），方便外层推进游标——这是处理"消息嵌套消息"时的通用手法。

这条消息把嵌套选择展现得很清楚：

  • ① RRC Transaction Identifier，INTEGER (0..3) → 2 比特（:897）。它是 RRC 层的"请求-响应配对序号"，作用类似你熟悉的 RPC request id。
  • ②③ criticalExtensions 先写 1 比特扩展标志，内部的 c1 CHOICE 有 8 个分支（rrcConnectionSetup-r8 只是其一）→ 3 比特选择子，恒写 0。注意选择子宽度跟着分支数走：UL-CCCH 顶层 2 分支用 1 比特，这里 8 分支用 3 比特。
  • ④ r8 分支 SEQUENCE 里唯一的 OPTIONAL 字段是 nonCriticalExtension，所以位图只有 1 比特，恒 0。
  • ⑤ 正文 radioResourceConfigDedicated 是整个无线承载配置（SRB1 的 RLC/MAC/物理层参数），本身又是一个庞大的 IE，pack 在 :7382 附近调用同一批工具函数展开——你现在已经能自己读下去了。

到这里你可以把三层壳穿起来：DL-CCCH 头（ext 1 + 选择子 2）→ RRCConnectionSetup 头（事务 id 2 + ext 1 + c1 选择子 3 + 位图 1）→ RadioResourceConfigDedicated 正文。每一层都是同一个套路的递归。

6. 新增/修改一条 RRC 消息的 checklist

假设你要给某条消息加一个字段，或者新增一条消息类型。按这个顺序做，每步都有明确的落点：

  1. 改头文件结构体：liblte/hdr/liblte_rrc.h。找到对应的 ..._STRUCT（用消息名搜，整个头文件按消息分节，每节有 Document Reference: 36.331 v10.0.0 Section X.X.X 注释）。加字段时注意：如果是新枚举值，同步更新旁边的 ..._text[] 打印表（如 liblte_rrc_dl_bandwidth_text，:6594），否则调试打印会错位。
  2. 改 pack：liblte/src/liblte_rrc.cc 里对应的 pack_..._msg/ie。严格按 36.331 的 ASN.1 字段顺序插入 liblte_value_2_bits 调用；有界整数算好比特数 ⌈log2(b−a+1)⌉；SIZE(m..n) 记得写 (N−m)；OPTIONAL 字段先加位图比特、再在正文加 if(present) 分支。
  3. 改 unpack：与 pack 逐行镜像，同一个位置、同样的比特数、+1/−1 偏移成对出现。改完把两个函数并排看一遍，行数应当几乎相同。
  4. 若新增了消息类型：更新信道容器的 MSG_TYPE_ENUM（加枚举项 + _text 表），重新算 choice 选择子宽度（⌈log2(分支数)⌉），同步改信道级 pack/unpack 的 liblte_value_2_bits(msg_type, ...) 比特数和 if/else if 分发链（参考 :13199、:13242）。
  5. 测试：写一个 pack→unpack 往返用例：填满结构体 → pack → 检查 N_bits 是否符合手算 → unpack 进另一个结构体 → 逐字段 memcmp。liblte/tests/ 与 liblte/manual_tests/ 下有现成的测试骨架可仿。能过往返，再抓真实空口数据（用 Wireshark 的 LTE-RRC 解析结果做 golden reference）验证字段顺序没搞反。

7. 常见坑

都是这份代码里真实存在或极易踩的：

  • 比特序：value_2_bits 是 MSB-first（liblte_common.cc:70）。如果你想当然按 LSB-first 在纸上拆，所有字段都是反的。抓包对照 Wireshark 时，Wireshark 展示的也是 MSB-first，先拿 MIB 这种 24 比特的小消息对齐手感。
  • "一字节一比特"≠线上字节流：LIBLTE_BIT_MSG_STRUCT.msg 里一个 uint8 是一个比特（liblte_common.h:68-71）。把它 hex dump 出来和抓包字节流直接比是对不上的——要先 8 个一组拼回字节。别在联调时被这个坑一下午。
  • 扩展位遗漏：凡是 ASN.1 定义带 ... 的类型，第一层就是 1 比特扩展标志。漏写/漏读 1 比特，后面所有字段错位，而且解码往往不报错——只是值全是垃圾。看代码时数清楚每个 if(!ext) 包住了什么（如 :11609）。
  • choice 选择子宽度算错：宽度是 ⌈log2(分支数)⌉，不是"写 1 比特意思一下"。DL-DCCH 12 个分支用 4 比特（:13275 之后），UL-CCCH 2 个分支用 1 比特（:13440）。加分支时忘记加宽选择子，unpack 直接把正文头几个比特当类型读。
  • −1/+1 偏移不对称：SIZE(1..N)、INTEGER(1..64) 这类下界非 0 的类型，pack 减下界、unpack 加下界（如 SIB1 的 :10811 与 :10914）。只改一边，字段恒差 1。
  • >32 比特字段：value_2_bits 只接受 uint32。40 比特的 randomValue 分两段写（:11620-11621），64 比特的 IMSI 类字段同理。unpack 记得用 uint64 移位拼回（:11660），直接赋给 32 位变量就丢高位。
  • 可选位图与正文脱节：位图里标了"在"，正文 if 里忘了写（或反之），之后字段整体漂移。改代码时位图行和正文 if 行必须一起改——这也是 checklist 第 2、3 步强调"同一位置"的原因。

小结

  • uPER 的本质：双方共享 schema，字段按固定顺序、最短比特数写入，不传 tag/length；... 类型先写 1 比特扩展位，OPTIONAL 字段用前置位图。
  • 整个 OpenLTE RRC codec 建立在 liblte_common.cc:62-93 的 liblte_value_2_bits/liblte_bits_2_value 之上：MSB-first、游标自动前进、一字节存一比特。注意它们不在 liblte_interface.cc。
  • 所有信道级 pack 共享同一骨架：扩展位 → choice 选择子（⌈log2(分支数)⌉ 比特）→ 内层消息 pack 进 global_msg → memcpy 拼装。UL/DL-CCCH/DCCH 四个分发器只有选择子宽度不同。
  • MIB（24 比特）和 RRCConnectionRequest（正文 46 比特）是最适合纸上练习的两条消息；SIB1 是 optional bitmap 与嵌套位图的完整样本。
  • 改消息的口诀：hdr 结构体 → pack → unpack 逐行镜像 → 选择子宽度与 _text 表 → pack/unpack 往返测试。
  • 最容易出事的三个点：比特序（MSB-first）、扩展位漏 1 比特导致全线错位、−1/+1 偏移只改一边。

NAS 协议与 TLV 编码：liblte_mme 全线精读

RRC 那一套 ASN.1 PER 如果你已经啃下来了，NAS 会让你松一口气：没有比特级的对齐折磨，没有扩展位和长度子集，就是一套字节对齐的 TLV 编码。如果你写过 protobuf 的 wire format 解析，或者手工拆过 TCP 选项字段，NAS 的消息体对你来说就是"显式带 tag 的二进制结构体"。

本章把 liblte/hdr/liblte_mme.h 和 liblte/src/liblte_mme.cc 通读一遍，目标有两个：

  • 给你一条 NAS 抓包字节流，你能手工解出来；
  • 你要给 OpenLTE 加一个新的 IE 或新消息时，知道该改哪几处。

NAS 的规范是 3GPP 24.301，TLV 编码的通用规则在 24.007。源码里每个函数头上都有 Document Reference 注释标明对应的规范小节，读代码时可以顺手对照。

NAS = EMM + ESM

NAS（Non-Access Stratum）是 UE 和 MME 之间的控制面协议，eNodeB 对它只转发、不解释（但 OpenLTE 把 eNodeB 和 MME 做在了一起，所以我们能在 LTE_fdd_enodeb 里直接看到 MME 侧的处理）。NAS 内部分两块：

  • EMM（EPS Mobility Management）：移动性管理——附着、分离、鉴权、安全模式、跟踪区更新；
  • ESM（EPS Session Management）：会话管理——PDN 连接、默认/专用承载的激活与释放。

类比一下：EMM 相当于"户籍科"（你是谁、你在哪），ESM 相当于"业务科"（给你办哪条数据通道）。两类消息共用一套帧格式，靠第一个字节的 Protocol Discriminator（PD） 区分，定义在 liblte/hdr/liblte_mme.h:2611：

#define LIBLTE_MME_PD_EPS_SESSION_MANAGEMENT    0x2   // ESM
#define LIBLTE_MME_PD_EPS_MOBILITY_MANAGEMENT   0x7   // EMM

整个 liblte_mme.cc 有 12412 行，但结构极其规整：前半部分（liblte/src/liblte_mme.cc:97 起）是每个 IE 的 pack/unpack 函数对，后半部分（liblte/src/liblte_mme.cc:5681 起）是每条消息的 pack/unpack 函数对。消息的 pack/unpack 就是把若干 IE 的 pack/unpack 按顺序串起来——和你在应用层写 serialize() 时挨个字段写流是同一个套路。

帧头：第一个字节干两件事

NAS 帧的第一个字节同时装两个字段：

  7 6 5 4 | 3 2 1 0
+---------+---------+
|   SHT   |   PD    |
+---------+---------+
 高 4 位     低 4 位

低 4 位是上面说的 PD；高 4 位是 Security Header Type（SHT），定义在 liblte/hdr/liblte_mme.h:2613 起：

SHT 值宏（LIBLTE_MME_SECURITY_HDR_TYPE_*）含义
0x0PLAIN_NAS明文 NAS，无保护
0x1INTEGRITY仅完整性保护
0x2INTEGRITY_AND_CIPHERED完整性 + 加密
0x3INTEGRITY_WITH_NEW_EPS_SECURITY_CONTEXT仅完整性，且启用新安全上下文
0x4INTEGRITY_AND_CIPHERED_WITH_NEW_EPS_SECURITY_CONTEXT完整性 + 加密，且启用新安全上下文
0xCSERVICE_REQUESTService Request 专用紧凑格式

实际抓包里你基本只会见到 0（鉴权前的 Attach Request、Authentication Request/Response）、3（Security Mode Command）、2（安全建立之后的一切）。

再往下是 Message Type 字节，一长串 LIBLTE_MME_MSG_TYPE_* 宏（liblte/hdr/liblte_mme.h:2619 起），常用的：

全仓库唯一的消息头解析入口是 liblte_mme_parse_msg_header（liblte/src/liblte_mme.cc:5632），它把上面三种情况的分支写得很清楚：

// Security Header Type
sec_hdr_type = (msg->msg[0] & 0xF0) >> 4;
// Protocol Discriminator
*pd = msg->msg[0] & 0x0F;
if(LIBLTE_MME_SECURITY_HDR_TYPE_SERVICE_REQUEST == sec_hdr_type) {
    *msg_type = LIBLTE_MME_SECURITY_HDR_TYPE_SERVICE_REQUEST;
}else{
    if(LIBLTE_MME_PD_EPS_SESSION_MANAGEMENT == *pd) {
        *msg_type = msg->msg[2];            // ESM：第 3 字节才是类型
    }else{
        if(LIBLTE_MME_SECURITY_HDR_TYPE_PLAIN_NAS == sec_hdr_type) {
            *msg_type = msg->msg[1];        // 明文 EMM：第 2 字节
        }else{
            *pd = msg->msg[6] & 0x0F;       // 受保护：跳过 6 字节外壳
            *msg_type = msg->msg[7];        // （ESM 则再 +1）
        }
    }
}

注意 msg_type 的位置随消息形态漂移：明文 EMM 在字节 1，受保护 EMM 在字节 7，ESM 还要再加 1。这正是下一节要讲的"三种形态"。

三种消息形态

形态一：plain NAS

SHT = 0，整帧就是 [SHT|PD] [MsgType] [IE...]。鉴权完成之前的消息（Attach Request、Authentication Request/Response、Identity Request/Response）都是明文。

形态二：security protected NAS

SHT ≠ 0 时，在真正的 NAS 消息外面套一个 6 字节的外壳：

+----------+----------------+--------+---------------------------+
| SHT | PD |  MAC (4 字节)  | Seq(1) | 内层完整 plain NAS 消息   |
+----------+----------------+--------+---------------------------+
   1 字节        4 字节        1 字节

MAC 是完整性校验值（33.401 定义的 EIA 算法，OpenLTE 用的是 EIA2 = AES-CMAC），Seq 是 NAS 序列号（COUNT 的低 8 位）。注意内层是一条完整的 plain NAS——它有自己的 [SHT=0|PD] [MsgType] 头。

封包侧的统一实现是 liblte_mme_pack_security_protected_nas_msg（liblte/src/liblte_mme.cc:5681）：

if(LIBLTE_MME_SECURITY_HDR_TYPE_PLAIN_NAS != sec_hdr_type)
{
    *msg_ptr = (sec_hdr_type << 4) | (LIBLTE_MME_PD_EPS_MOBILITY_MANAGEMENT);
    msg_ptr++;
    msg_ptr += 4;               // 给 MAC 留 4 字节，稍后回填
    *msg_ptr = count & 0xFF;    // 序列号
    msg_ptr++;
}
// 原样拷贝内层 NAS 消息 ...
// 最后算 MAC，覆盖从 Seq 字节（msg[5]）开始的全部内容
liblte_security_128_eia2(&key_256[16], count, 0, direction,
                         &sec_msg->msg[5], sec_msg->N_bytes-5,
                         &sec_msg->msg[1]);   // MAC 写回字节 1..4

解包侧没有这个函数对应的 unwrap——每个消息的 unpack 自己处理外壳，套路完全一样，以 liblte_mme_unpack_attach_request_msg 为例（liblte/src/liblte_mme.cc:6427）：

sec_hdr_type = (msg->msg[0] & 0xF0) >> 4;
if(LIBLTE_MME_SECURITY_HDR_TYPE_PLAIN_NAS == sec_hdr_type)
{
    msg_ptr++;        // 明文：跳 1 字节
}else{
    msg_ptr += 7;     // 受保护：跳 1 + 4(MAC) + 1(Seq) + 内层头 1 字节
}
msg_ptr++;            // 跳过内层 Message Type

"明文跳 1、加密跳 7"这个写法在全文出现了几十次，你读到第三次就会背了。

形态三：Service Request 特例

Service Request 为了省字节，不用通用格式。SHT = 0xC，整帧只有 4 字节，见 liblte_mme_pack_service_request_msg（liblte/src/liblte_mme.cc:8487）：

*msg_ptr = (LIBLTE_MME_SECURITY_HDR_TYPE_SERVICE_REQUEST << 4)
         | (LIBLTE_MME_PD_EPS_MOBILITY_MANAGEMENT);   // 字节 0：0xC7
liblte_mme_pack_ksi_and_sequence_number_ie(&service_req->ksi_and_seq_num, &msg_ptr); // 字节 1
liblte_mme_pack_short_mac_ie(service_req->short_mac, &msg_ptr);                      // 字节 2-3

字节 1 是 KSI（高 3 位）+ 序列号（低 5 位），见 liblte_mme_pack_ksi_and_sequence_number_ie（liblte/src/liblte_mme.cc:2636）；后 2 字节是 Short MAC。它没有 Message Type 字节——parse_msg_header 里那个 *msg_type = SHT 的特判（liblte/src/liblte_mme.cc:5649）就是为这种情况准备的。

TLV/IEI 编码规则

从消息体开始，内容就是一串 IE（Information Element）。每个 IE 有四种格式（24.007）：

格式布局长度有无 IEI
V值固定无
LV长度 + 值可变无
TVIEI + 值固定有（1 字节）
TLVIEI + 长度 + 值可变有（1 字节）

外加一个特殊形态 Type-1（half octet）：IEI 和值各 4 位挤在一个字节里。帧头那个 [SHT|PD] 字节本身就是 Type-1 的写法。

对照 protobuf 理解：TLV ≈ protobuf 的 (tag, length, value)；V/LV ≈ 定长 packed 字段；Type-1 没有对应物。

关键规则是强制 IE 与可选 IE 的分工：

  • Mandatory IE：必须出现、按 schema 定义的顺序排列、不带 IEI——靠位置识别，所以是 V 或 LV；
  • Optional IE：可出可不出、必须带 IEI——靠 IEI 识别，所以是 TV 或 TLV。

这就是为什么 NAS 敢字节对齐：所有定位信息（IEI、长度）本身就占整字节。RRC 的 PER 追求空口上的极致压缩，连 IEI 这几个字节都舍不得花，才退到比特对齐；NAS 消息量小、频率低，用可读性和可扩展性换几个字节完全值得。你熟悉的对比就是：RRC 像 Cap'n Proto（零拷贝、无 tag、靠 schema），NAS 像 protobuf（带 tag、可自描述解析）。

IEI 的具体取值是消息相关的常量。以 Attach Request 为例，它的可选 IEI 定义在 liblte/hdr/liblte_mme.h:2804 起：

IEI宏格式
0x19P_TMSI_SIGNATURE_IEITV
0x50ADDITIONAL_GUTI_IEITLV
0x52LAST_VISITED_REGISTERED_TAI_IEITV
0x5CDRX_PARAMETER_IEITV
0x31MS_NETWORK_CAPABILITY_IEITLV
0x9（半字节）TMSI_STATUS_IEIType-1
0xE（半字节）GUTI_TYPE_IEIType-1

Type-1 的 IEI 只占高 4 位，所以解码端的判断写法不一样（见下节代码里的 << 4 再比高半字节）。

UE Network Capability 是 LV：长度字节之后，第 1 字节是 EEA0..EEA7 的支持位图、第 2 字节是 EIA0..EIA7 位图（liblte/src/liblte_mme.cc:3692 和 :3701 的 pack 侧是 8 行 << 7 到 << 0，一位一个算法）。eNodeB 侧收到后逐位存起来（LTE_fdd_enodeb/src/LTE_fdd_enb_mme.cc:540），后面 Security Mode Command 要选算法时就用这份位图。

ESM 如何嵌在 EMM 里

Attach 流程里，UE 在 Attach Request 里捎带一条 PDN Connectivity Request，网络在 Attach Accept 里捎带一条 Activate Default EPS Bearer Context Request。承载工具就是 ESM Message Container IE，它的编解码在 liblte/src/liblte_mme.cc:2370：

esm_msg->N_bytes  = (*ie_ptr)[0] << 8;     // 长度是 2 字节、大端
esm_msg->N_bytes |= (*ie_ptr)[1];
for(i=0; i<esm_msg->N_bytes; i++)
    esm_msg->msg[i] = (*ie_ptr)[2+i];      // 原样拷贝内层 ESM 帧
*ie_ptr += esm_msg->N_bytes + 2;

注意两点：一是这个 LV 的长度域是 2 字节（多数 LV 是 1 字节，这是例外）；二是容器对内容完全透明——就是一段字节，递归地装了一条完整 ESM 消息。类比 HTTP：EMM 是外层请求的 body，ESM container 相当于 body 里又塞了一段 Content-Type: application/x-esm 的完整报文。

ESM 消息的帧头和 EMM 略有不同。看 PDN Connectivity Request 的 pack（liblte/src/liblte_mme.cc:12099）：

// 字节 0：高 4 位是 EPS Bearer ID（不是 SHT！），低 4 位是 PD=2
*msg_ptr = (pdn_con_req->eps_bearer_id << 4) | (LIBLTE_MME_PD_EPS_SESSION_MANAGEMENT);
// 字节 1：Procedure Transaction ID（一次流程的事务号）
*msg_ptr = pdn_con_req->proc_transaction_id;
// 字节 2：Message Type = 0xD0
*msg_ptr = LIBLTE_MME_MSG_TYPE_PDN_CONNECTIVITY_REQUEST;
// 字节 3：PDN Type（高 4 位）| Request Type（低 4 位）

这就是 parse_msg_header 里"PD 是 ESM 时 msg_type 在字节 2"的原因——ESM 多了个事务 ID 字节。

接收端把这两层拆开的代码在 LTE_fdd_enodeb/src/LTE_fdd_enb_mme.cc:512：

liblte_mme_unpack_attach_request_msg(msg, &attach_req);          // 解外层 EMM
liblte_mme_parse_msg_header(&attach_req.esm_msg, &pd, &msg_type); // 看内层是什么
switch(msg_type)
{
case LIBLTE_MME_MSG_TYPE_PDN_CONNECTIVITY_REQUEST:
    parse_pdn_connectivity_request(&attach_req.esm_msg, (*user), (*rb));
    break;

发送端反过来：先把 Activate Default EPS Bearer Context Request pack 进 attach_accept.esm_msg（LTE_fdd_enodeb/src/LTE_fdd_enb_mme.cc:1343），再 pack 整个 Attach Accept。你要加新的 ESM 携带关系，照这个两段式写法抄就行。

常见坑

1. MCC/MNC 的半字节交换。 PLMN ID 的编码是 BCD + nibble 反序：MCC=460、MNC=00 在线缆上是 64 F0 00。看 GUTI 的 pack（liblte/src/liblte_mme.cc:2103）：

**ie_ptr = (((eps_mobile_id->guti.mcc/10) % 10) << 4)
         | ((eps_mobile_id->guti.mcc/100) % 10);   // MCC 第 2 位放在高半字节！
...
**ie_ptr = 0xF0 | (eps_mobile_id->guti.mcc % 10);  // MNC 只有 2 位时高 4 位补 F

规律：每个字节里"第奇数位数字放低半字节、第偶数位放高半字节"，两位 MNC 要在第三字节高半位填 0xF。手工对抓包时 PLMN 解出来数字顺序是反的，十有八九是忘了这个交换。

2. Type-1 IEI 只占高半字节。 可选 IE 循环里，整字节 IEI 直接 == *msg_ptr 比较；Type-1 必须先 << 4 再和高半字节比（liblte/src/liblte_mme.cc:6513 的 TMSI Status、:6583 的 GUTI Type）。混用两种写法会要么误匹配要么漏匹配。

3. 长度域的宽度不统一。 多数 LV 是 1 字节长度；ESM Message Container 是 2 字节大端（liblte/src/liblte_mme.cc:2379）；EPS Mobile ID 的长度字节不把自己算进去但把 type_of_id 所在字节算进去。照抄某个 IE 的写法前，先看清楚它的 L 是几字节、算不算自己。

4. unpack 不做边界检查。 所有 unpack 都假设输入是合法的——msg_ptr += 7 之前不看 N_bytes 够不够 7。喂畸形报文进去就是越界读。如果你要给 OpenLTE 加模糊测试或者对接不可信输入，这层校验得自己补。

5. IEI 不是全局唯一的。 比如 0x50 在 Attach Accept 里是 GUTI（liblte/hdr/liblte_mme.h:2694），在 Attach Request 里是 Additional GUTI（:2805）。IEI 表永远要绑着"当前在解哪条消息"来看。

6. 受保护消息里"跳 7"只对 EMM 成立。 内层若是 ESM，Message Type 还在第 8 字节（liblte/src/liblte_mme.cc:5668）。自己写解析器时别把 ESM 的偏移套到 EMM 上。

小结

  • NAS 一帧 = [SHT|PD] 头 + Message Type + IE 序列；PD 区分 EMM（0x7）/ESM（0x2），SHT 决定外壳形态。
  • 三种形态：明文（跳 1 字节）、安全保护（跳 7 字节，含 4 字节 MAC + 1 字节 Seq，内层是完整 plain NAS）、Service Request 特例（4 字节定帧）。
  • 消息体是 TLV/IEI 编码：强制 IE 靠位置（V/LV），可选 IE 靠 IEI（TV/TLV/Type-1）；字节对齐是它区别于 RRC PER 的本质特征。
  • liblte_mme.cc 的结构 = IE 编解码函数 + 消息编解码函数，消息函数就是按 schema 顺序调用 IE 函数；加新 IE 的完整路径是：hdr 里加 struct 和 IEI 宏 → 写 IE 的 pack/unpack → 在消息的 pack/unpack 里挂上调用。
  • OpenLTE 的 NAS 安全只做下行 MAC（EIA2），上行 MAC 校验与 NAS 加密未实现，读代码时别把这部分当完整参考。
  • 手工解包三大陷阱：PLMN 的 nibble 反序、Type-1 IEI 的半字节比较、各 IE 长度域宽度不一。

eNodeB 状态机与多线程架构

入门级部分我们逐层读了 PHY/MAC/RLC/PDCP 的编解码。这一章换一个视角：把 LTE_fdd_enodeb 当作一个普通的并发服务器进程来解剖——它有哪些线程、线程之间怎么通信、控制面（RRC/EMM）的状态机挂在哪个对象上。读完这一章，给你任意一条信令（比如 Attach Request），你应该能自己把它在代码里从比特流一直追到 HSS 再追回来。

本章是全书的枢纽：前面各章讲的"每一层干什么"，在这里被一条消息队列总线串成了"整个进程怎么转"。

进程启动：main 里发生了什么

LTE_fdd_enodeb/src/LTE_fdd_enb_main.cc 的 main() 只有不到 25 行有效代码（LTE_fdd_enb_main.cc:61-83）：

LTE_fdd_enb_interface *interface = LTE_fdd_enb_interface::get_instance();
LTE_fdd_enb_cnfg_db   *cnfg_db   = LTE_fdd_enb_cnfg_db::get_instance();
LTE_fdd_enb_hss       *hss       = LTE_fdd_enb_hss::get_instance();

interface->set_ctrl_port(LTE_FDD_ENB_DEFAULT_CTRL_PORT);
interface->start_ports();

// Read configuration
hss->read_user_file();
cnfg_db->read_cnfg_file();

逐行看（LTE_fdd_enb_main.cc:63-72）：

  1. 三个 get_instance() 拿出全进程最早存在的三个 Singleton：interface（对外控制/调试接口）、cnfg_db（配置数据库）、hss（本地用户数据库）。注意此刻协议栈一层都还没起来。
  2. start_ports() 打开两个 TCP server socket：控制端口和调试端口（LTE_fdd_enb_interface.cc:234-277）。你之后 telnet localhost 30000 敲的 start、write bandwidth 10 这些命令，都是进到这个 socket 里的。
  3. hss->read_user_file()（LTE_fdd_enb_hss.cc:506）读用户文件（IMSI/IMEI/K 三元组），cnfg_db->read_cnfg_file()（LTE_fdd_enb_cnfg_db.cc:959）读配置文件。
  4. 最后 main 进入 while(!interface->get_shutdown()) sleep(1); 的空转循环（LTE_fdd_enb_main.cc:77-80）。主线程从此只是个看门人，真正的戏都在别的线程里。

真正的协议栈启动发生在你在控制端口敲下 start 命令之后。控制消息由 handle_ctrl_msg()（LTE_fdd_enb_interface.cc:690）分发到 handle_start()（LTE_fdd_enb_interface.cc:971），它干了三件大事：

第一件：创建 13 条消息队列（LTE_fdd_enb_interface.cc:992-1004）。每一对相邻模块之间一条单向队列，名字直白得像管道名：

第三件：按自顶向下再到底层的顺序 start 各层（LTE_fdd_enb_interface.cc:1015-1028）：gw → phy → mac → timer_mgr → rlc → pdcp → rrc → mme → radio。每个 start() 做的事高度同构，以 RRC 为例（LTE_fdd_enb_rrc.cc:141-163）：保存队列指针，然后对两条输入队列各调一次 attach_rx()——每调一次 attach_rx 就 pthread_create 出一条接收线程（LTE_fdd_enb_msgq.cc:121-135）。所以这个进程的并发模型是：一条消息队列 = 一条专属消费线程，模块本身几乎不持有线程（例外是 GW 的 socket 收包线程 LTE_fdd_enb_gw.cc:184 和 Radio 的采样线程 LTE_fdd_enb_radio.cc:1161）。

消息队列：msgq 封装与消息类型

一条队列的实现

LTE_fdd_enb_msgq（LTE_fdd_enodeb/hdr/LTE_fdd_enb_msgq.h:400-433）的实现朴素得出乎意料：一个 boost::circular_buffer（容量 100，LTE_fdd_enb_msgq.cc:95）加两个 POSIX 信号量。发送侧（LTE_fdd_enb_msgq.cc:140-158）：

msg.type       = type;
msg.dest_layer = dest_layer;
if(msg_content != NULL)
{
    memcpy(&msg.msg, msg_content, msg_content_size);
}

sem_wait(&sync_sem);
circ_buf->push_back(msg);
sem_post(&sync_sem);
sem_post(&msg_sem);
  • sync_sem 保护环形缓冲区的互斥访问；
  • msg_sem 是"有消息了"的事件信号——接收线程在 receive_thread() 里 sem_wait(&msgq->msg_sem) 阻塞等待（LTE_fdd_enb_msgq.cc:207），被唤醒后清空缓冲区，逐条回调 msgq->callback(msg)（LTE_fdd_enb_msgq.cc:211-226）。

两个值得注意的细节：

  • 收到 LTE_FDD_ENB_MESSAGE_TYPE_KILL 就退出线程循环（LTE_fdd_enb_msgq.cc:220-222）。停机时 handle_stop() 给全部 13 条队列各发一条 KILL（LTE_fdd_enb_interface.cc:1085-1136），这是整个进程的"安全停机"机制。
  • 接收线程会把自己的 CPU 亲和性设置为"避开最后一个核"（LTE_fdd_enb_msgq.cc:199-202），注释写明最后一个核留给 PHY/Radio——实时信号处理要独占一个核，这是 SDR 系统的常见手法。

消息信封：type + dest_layer + union

所有消息共用同一个信封结构（LTE_fdd_enb_msgq.h:372-376）：

typedef struct{
    LTE_FDD_ENB_MESSAGE_TYPE_ENUM type;
    LTE_FDD_ENB_DEST_LAYER_ENUM   dest_layer;
    LTE_FDD_ENB_MESSAGE_UNION     msg;
}LTE_FDD_ENB_MESSAGE_STRUCT;

dest_layer 是目的层（PHY/MAC/RLC/PDCP/RRC/MME/GW/TIMER_MGR/ANY，枚举在 LTE_fdd_enb_msgq.h:150-161）。每个模块的入口函数第一件事就是检查 dest_layer：是自己的就处理，不是自己的就原样转发给下一个模块——比如 RRC 的 handle_pdcp_msg() 里，dest 不是 RRC 的消息直接 msgq_to_mme->send(msg) 转发（LTE_fdd_enb_rrc.cc:196-199）。这就是为什么 NAS 消息能"穿过"RRC 到达 MME 而不被 RRC 拆开。

RLC_PDU_READYMAC→RLC（user, rb）指针对
TIMER_TICKMAC→TIMER_MGR1ms 滴答
RLC_SDU_READYPDCP→RLC（user, rb）指针对
PDCP_PDU_READYRLC→PDCP（user, rb）指针对
PDCP_SDU_READYRRC→PDCP（user, rb）指针对
RRC_PDU_READYPDCP→RRC（user, rb）指针对
RRC_NAS_MSG_READYMME→RRC（user, rb）；下行 NAS 已入队
RRC_CMD_READYMME→RRC（user, rb, cmd）；cmd 枚举见下
MME_NAS_MSG_READYRRC→MME（user, rb）；上行 NAS 已入队
MME_RRC_CMD_RESPRRC→MME（user, rb, cmd_resp）
PDCP_DATA_SDU_READYGW→PDCP用户面下行 IP 包
GW_DATA_READYPDCP→GW用户面上行 IP 包

注意一个贯穿始终的设计惯例：MAC 以上的 *_READY 系列消息本身不带数据，只带 (user, rb) 两个指针（PHY→MAC 的解码消息例外，比特流直接装在消息里）。数据在哪？在 rb 对象内部的队列里——发送方先 rb->queue_rrc_pdu(...) 把数据塞进 rb，再发消息"通知"对端来取；接收方 rb->get_next_rrc_pdu(&pdu) 取出。你熟悉的"队列里传 buffer"在这里变成了"队列里传句柄，buffer 挂在句柄上"。好处是消息定长、memcpy 一次搞定；代价是 user/rb 对象被所有线程共享，靠 rb 内部的信号量保护。

RRC_CMD_READY 里的命令枚举（LTE_fdd_enb_msgq.h:279-285）是 MME 指挥 RRC 的四条指令：RELEASE（释放连接）、SECURITY（起 RRC 安全）、SETUP_DEF_DRB（建默认承载）、SETUP_DED_DRB（建专用承载）。

RRC 状态机

状态枚举

OpenLTE 的 RRC 状态不是全局的，而是挂在每个 UE 的每条 Radio Bearer（rb）对象上。枚举定义在 LTE_fdd_enodeb/hdr/LTE_fdd_enb_rb.h:152-158：

状态含义类比
IDLE尚无 RRC 连接TCP 的 CLOSED/LISTEN
SRB1_SETUP已收到 ConnectionRequest，SRB1 建好了SYN_RCVD 的前半拍
WAIT_FOR_CON_SETUP_COMPLETE已发 RRCConnectionSetup，等 UE 回 CompleteSYN_RCVD
RRC_CONNECTEDRRC 连接建立ESTABLISHED
WAIT_FOR_CON_REEST_COMPLETE重建流程中，等 ReestablishmentComplete类似 TCP 的重连恢复

配套的还有"过程"枚举 LTE_FDD_ENB_RRC_PROC_ENUM（LTE_fdd_enb_rb.h:142-146）：IDLE / RRC_CON_REQ / RRC_CON_REEST_REQ。"过程 + 状态"两维合起来才是完整的状态机位置——这和你写 Web 服务器时"连接状态 + 当前在处理哪个请求"是同一个套路。

两条入口状态机：ccch_sm 与 dcch_sm

RRC 收到 PDU 后按承载分流（LTE_fdd_enb_rrc.cc:259-267）：SRB0 走 ccch_sm()，SRB1/SRB2 走 dcch_sm()。

ccch_sm()（LTE_fdd_enb_rrc.cc:434-510） 处理连接建立。核心迁移在 LTE_fdd_enb_rrc.cc:448-457：

case LTE_FDD_ENB_RRC_PROC_RRC_CON_REQ:
    switch(loc_rb->get_rrc_state())
    {
    case LTE_FDD_ENB_RRC_STATE_IDLE:
        loc_user->setup_srb1(&srb1);
        if(NULL != srb1)
        {
            loc_rb->set_rrc_state(LTE_FDD_ENB_RRC_STATE_SRB1_SETUP);
            send_rrc_con_setup(loc_user, loc_rb);
            srb1->set_rrc_procedure(LTE_FDD_ENB_RRC_PROC_RRC_CON_REQ);
            srb1->set_rrc_state(LTE_FDD_ENB_RRC_STATE_WAIT_FOR_CON_SETUP_COMPLETE);

即：SRB0 上收到 RRCConnectionRequest 且当前 IDLE → 建 SRB1 → SRB0 转 SRB1_SETUP → 发 RRCConnectionSetup（send_rrc_con_setup()，LTE_fdd_enb_rrc.cc:1010，消息字段按 36.331 组包，还会顺便给 UE 配 SR 的 PUCCH 资源，LTE_fdd_enb_rrc.cc:1043-1045）→ 新的 SRB1 转入 WAIT_FOR_CON_SETUP_COMPLETE。注意状态是记录在 SRB0 和 SRB1 两条 rb 上的，接力棒从 SRB0 交到 SRB1。重建请求走对称的另一支（LTE_fdd_enb_rrc.cc:476-486），失败则发 ReestablishmentReject。

dcch_sm()（LTE_fdd_enb_rrc.cc:511-546） 处理已建立连接后的消息。它只在 WAIT_FOR_CON_SETUP_COMPLETE / WAIT_FOR_CON_REEST_COMPLETE / RRC_CONNECTED 三个状态下受理消息（LTE_fdd_enb_rrc.cc:521-526），然后转给 parse_ul_dcch_message()。

真正的状态推进在 parse_ul_dcch_message()（LTE_fdd_enb_rrc.cc:631-724），关键的三个分支：

  • 收到 RRCConnectionSetupComplete：rb->set_rrc_state(LTE_FDD_ENB_RRC_STATE_RRC_CONNECTED)（LTE_fdd_enb_rrc.cc:657），同时把消息里捎带的 NAS（就是 Attach Request）queue_mme_nas_msg() 入队，并发 MME_NAS_MSG_READY 给 MME（LTE_fdd_enb_rrc.cc:660-668）。RRC 层到此为止，接力棒交给 MME。
  • 收到 ULInformationTransfer（后续所有上行 NAS 的载体）：同样入队 + 通知 MME（LTE_fdd_enb_rrc.cc:670-682）。RRC 对 NAS 永远只当搬运工，从不拆包——这就是 36.331 里 dedicatedInfoNAS 字段的"透传"语义。
  • 收到 SecurityModeComplete：发 MME_RRC_CMD_RESP 告知 MME"你要的 RRC 安全建好了"（LTE_fdd_enb_rrc.cc:693-701）。

下行方向，MME 通过两类消息驱动 RRC（handle_mme_msg()，LTE_fdd_enb_rrc.cc:201-227）：

  • RRC_NAS_MSG_READY → handle_nas_msg()（LTE_fdd_enb_rrc.cc:294）→ send_dl_info_transfer()（LTE_fdd_enb_rrc.cc:729）：把 NAS 包进 DLInformationTransfer，经 PDCP_SDU_READY 发给 PDCP。
  • RRC_CMD_READY → handle_cmd()（LTE_fdd_enb_rrc.cc:322）：RELEASE 发 RRCConnectionRelease（LTE_fdd_enb_rrc.cc:977）；SECURITY 发 UECapabilityEnquiry + SecurityModeCommand（LTE_fdd_enb_rrc.cc:343-346）；SETUP_DEF_DRB 建 SRB2+DRB1 后发 RRCConnectionReconfiguration，并把 MME 已入队的 NAS（Attach Accept）捎带进去（LTE_fdd_enb_rrc.cc:347-370）。

EMM 状态机与 MME 模块

MME 模块（LTE_fdd_enodeb/src/LTE_fdd_enb_mme.cc）是这个进程里的"迷你核心网"：EMM 状态机、鉴权、IP 分配都在这。它的 EMM 状态同样挂在 rb 上，枚举在 LTE_fdd_enb_rb.h:112-125：

状态含义

ID_REQUEST_IMSIUE 报的 GUTI 本地不认识，发 Identity Request 要 IMSI

MME 的消息入口是 handle_nas_msg()（LTE_fdd_enb_mme.cc:180）：先 liblte_mme_parse_msg_header() 取出 NAS 消息类型（LTE_fdd_enb_mme.cc:198），按类型分派给 parse_attach_request / parse_authentication_response / parse_security_mode_complete 等一大堆 parse 函数（LTE_fdd_enb_mme.cc:199-365）；parse 函数只负责改状态（set_mme_state(...)），随后统一按"过程"调对应的状态机函数 attach_sm() / service_req_sm() / detach_sm()（LTE_fdd_enb_mme.cc:374-383）执行动作（发消息）。这个"parse 改状态、sm 执行动作"的两段式结构非常清晰，值得学。

attach_sm()（LTE_fdd_enb_mme.cc:1183-1233）就是一张纯粹的"状态 → 发送函数"映射表：

case LTE_FDD_ENB_MME_STATE_AUTHENTICATE:
    send_authentication_request(user, rb);
    break;
...
case LTE_FDD_ENB_MME_STATE_RRC_SECURITY:
    send_rrc_command(user, rb, LTE_FDD_ENB_RRC_CMD_SECURITY);
    break;
case LTE_FDD_ENB_MME_STATE_ATTACH_ACCEPT:
    send_attach_accept(user, rb);
    break;

Attach Request 的处理链

以 IMSI 方式 attach 为例，parse_attach_request()（LTE_fdd_enb_mme.cc:489-657）依次做：

  1. 解包 NAS（liblte_mme_unpack_attach_request_msg，LTE_fdd_enb_mme.cc:512），把内嵌的 ESM 消息（PDN Connectivity Request）也解析掉（LTE_fdd_enb_mme.cc:515-519）。
  2. 把 rb 的 MME 过程置为 ATTACH（LTE_fdd_enb_mme.cc:532），存下 UE 的 EEA/EIA 安全能力（LTE_fdd_enb_mme.cc:538-542）。
  3. 查 HSS：hss->is_imsi_allowed(imsi_num)（LTE_fdd_enb_mme.cc:614，实现就是遍历本地用户链表，LTE_fdd_enb_hss.cc:224-240）。没有 S6a 接口、没有真实 HSS——就是一个内存数据库，你在控制端口 add_user 加进去的三元组就在这。
  4. 查到了且 UE 支持 EEA0/EIA2：set_mme_state(AUTHENTICATE) 并从 HSS 取出用户身份 set_id(hss->get_user_id_from_imsi(imsi_num))（LTE_fdd_enb_mme.cc:616-619）；查不到就 REJECT（LTE_fdd_enb_mme.cc:624-627）。

随后 attach_sm 在 AUTHENTICATE 态调 send_authentication_request()（LTE_fdd_enb_mme.cc:1472）：先 hss->generate_security_data(...) 用 Milenage f1/f2345 算出 RAND/AUTN/XRES/KASME 一 whole 鉴权向量（LTE_fdd_enb_mme.cc:1483-1485，Milenage 实现在 LTE_fdd_enb_hss.cc:327-332，算法对应 35.206，鉴权框架见 33.401），打包 Authentication Request 后经 RRC_NAS_MSG_READY 发回 RRC（LTE_fdd_enb_mme.cc:1506-1514）。

之后的状态迁移链：

  • UE 回 Authentication Response → parse_authentication_response()（LTE_fdd_enb_mme.cc:694）比对 XRES，通过则转 ENABLE_SECURITY（LTE_fdd_enb_mme.cc:742）→ 发 NAS Security Mode Command。
  • UE 回 NAS 层 Security Mode Complete → parse_security_mode_complete()（LTE_fdd_enb_mme.cc:883）转 RRC_SECURITY（LTE_fdd_enb_mme.cc:935）→ attach_sm 发 RRC_CMD_SECURITY 命令 RRC 起 AS 安全。
  • UE 回 RRC 层 SecurityMode Complete → RRC 回 MME_RRC_CMD_RESP → handle_rrc_cmd_resp()（LTE_fdd_enb_mme.cc:402）转 ATTACH_ACCEPT（或先 ESM_INFO_TRANSFER，LTE_fdd_enb_mme.cc:409-417）。
  • send_attach_accept()（LTE_fdd_enb_mme.cc:1284）：分配 IP（get_next_ip_addr()，LTE_fdd_enb_mme.cc:1889）、组 GUTI、把"Activate Default EPS Bearer Context Request"嵌进 Attach Accept（LTE_fdd_enb_mme.cc:1343-1344，消息格式见 24.301），入队后经 RRC_CMD_SETUP_DEF_DRB 发给 RRC（LTE_fdd_enb_mme.cc:1394-1398）——RRC 那边建 SRB2+DRB1 并把这条 NAS 捎进 RRCConnectionReconfiguration。
  • UE 回 Attach Complete → parse_attach_complete()（LTE_fdd_enb_mme.cc:447）转 ATTACHED（LTE_fdd_enb_mme.cc:470），再补一条 EMM Information。收工。

定时器：timer_mgr 与 T3xx

定时器模块的结构很直白：LTE_fdd_enb_timer_mgr（LTE_fdd_enodeb/src/LTE_fdd_enb_timer_mgr.cc）内部是 std::map<uint32, LTE_fdd_enb_timer*>，start_timer(毫秒, 回调, &id) 注册（LTE_fdd_enb_timer_mgr.cc:149-174），stop_timer/reset_timer 配套（:175-203）。

驱动节拍来自 MAC：PHY 每 TTI 发 READY_TO_SEND，MAC 的 handle_ready_to_send() 顺手往 mac_to_timer 队列丢一个 TIMER_TICK（LTE_fdd_enb_mac.cc:376-389）。timer_mgr 收到后 handle_tick() 遍历所有定时器加 1ms，超时的逐个 call_callback() 并从 map 删除（LTE_fdd_enb_timer_mgr.cc:236-265）。tick 精度就是 1 个 TTI（1ms），够用但谈不上精确——这是拿协议节拍当时钟源的典型做法。

一个反直觉的事实要先说清楚：T300/T310/T311 这些 36.331 的 T3xx 定时器是 UE 侧的，eNodeB 不跑它们。OpenLTE 里它们只作为 SIB2 的广播参数出现（LTE_fdd_enb_cnfg_db.cc:672-674，t310 = 1000ms、t311 = 30000ms）。eNodeB 侧实际跑的定时器有三个：

  • C-RNTI 预留定时器：user_mgr->add_user() 时启动，5000ms（LTE_fdd_enb_user_mgr.cc:300）。RACH 建了 user 但 UE 迟迟不完成连接建立，超时后 handle_c_rnti_timer_expiry()（LTE_fdd_enb_user_mgr.cc:610）回收 C-RNTI。
  • 用户不活动定时器：user->start_inactivity_timer()（LTE_fdd_enb_user.cc:753）；每次收到该 UE 的 PUSCH 都 reset（LTE_fdd_enb_mac.cc:619）。超时回调 handle_timer_expiry()（LTE_fdd_enb_user.cc:726-742）直接构造一条 RRC_CMD_RELEASE 调 rrc->handle_cmd() 释放 RRC 连接——相当于真实网络里的"用户面不活动释放"。
  • RLC t-pollretransmit：AM 模式轮询重传，100ms（LTE_fdd_enb_rb.cc:791），36.322 定义的标准定时器。

所以"超时了往哪发消息"的答案是：多数情况下不发消息，直接在回调里调目标模块的公开接口（比如 rrc->handle_cmd()）。这是 msgq 规则的一个例外，值得注意——它成立的前提是这些回调都很短，不会阻塞 timer_mgr 的消费线程。

设计点评

优点：

  • 极致的可读性。一个模块一个类、一条链路一条队列、消息类型一目了然。控制面"parse 改状态 / sm 执行动作"的两段式写法，让状态机代码没有任何藏起来的副作用。作为教学代码，这是它最大的价值。
  • 模块间零共享内存（除了 user/rb）。每层只摸自己的队列指针，崩溃影响面小，gdb 里栈也干净。
  • CPU 亲和性、pcap 落盘（LTE_fdd_enb_interface.cc:506-563）这些细节都是真刀真枪做 SDR 才会想到的。

缺点：

  • Singleton 满天飞。interface、cnfg_db、hss、user_mgr、各协议层全是全局单例，单元测试几乎没法做——你没法"新建一个 RRC 实例喂假消息"。作者自己也意识到了，MME/PDCP/GW 已经改回普通类（LTE_fdd_enb_mme.h:44 的修订记录写着 "Moved away from singleton pattern"），但改了一半。
  • user/rb 是隐式共享状态。消息只传指针，意味着十几条线程并发读写同一批 user 对象，全靠对象内部的信号量自觉保护，死锁和竞态的风险都压在"大家都守规矩"上。
  • 队列满即丢。boost::circular_buffer 容量写死 100，满了 push_back 静默覆盖最老的消息，没有任何背压或告警。
  • 控制面与用户面同优先级。所有消息挤同一种队列，没有 QoS 区分；RRC 信令不会因为队列前面堆了 100 个用户面消息而加塞。

和生产级实现的差距： 以 srsRAN 为例——它有真正的 S1AP 接口接外部核心网（OpenLTE 把 MME/HSS 合进进程里，出不了实验室）、有 SCTP、有完整的多 UE 调度与测量上报、RRC 状态机覆盖切换/重建/寻呼全场景，任务模型上也是按"协议栈线程池 + 精确 TTI 时钟"组织而不是一层一线程。OpenLTE 的定位从来都不是"能商用"，而是"能让你把 LTE 协议栈从头到尾看懂"——从这个目标看，Singleton + msgq 这套朴素架构反而是优点：每一跳都看得见摸得着。

小结

  • main() 只起三个 Singleton 和两个 TCP 端口（LTE_fdd_enb_main.cc:63-72）；协议栈由控制端口的 start 命令触发 handle_start()（LTE_fdd_enb_interface.cc:971）装配：13 条 msgq + 8 个模块按序启动。
  • 并发模型 = 每条消息队列一条消费线程；消息信封是 (type, dest_layer, union)，类型全集在 LTE_fdd_enb_msgq.h:80-129；数据不进队列，挂在共享的 (user, rb) 对象上。
  • RRC 状态机挂在 rb 上（LTE_fdd_enb_rb.h:152-158），入口 ccch_sm/dcch_sm（LTE_fdd_enb_rrc.cc:434、:511），主线 IDLE → SRB1_SETUP → WAIT_FOR_CON_SETUP_COMPLETE → RRC_CONNECTED。
  • EMM 状态机（LTE_fdd_enb_rb.h:112-125）在 MME 模块，"parse 改状态、attach_sm 执行动作"两段式；HSS 只是本地内存数据库，鉴权用 Milenage（35.206）。
  • 追信令的标准方法：在 LTE_fdd_enb_msgq.h 查消息类型 → grep 发送点 → 按 dest_layer 找接收方的 handle_*_msg()。
  • 定时器由 MAC 每 TTI 发的 TIMER_TICK 驱动；T3xx 是 UE 侧定时器，eNodeB 只在 SIB2 里广播，本地只跑 C-RNTI 预留、不活动释放、t-pollretransmit 三个。

第 4 章 LTE 安全与鉴权：Milenage、密钥层级与 EEA/EIA

安全是 LTE 协议栈里"工程味"最重的一部分：它不像物理层那样全是数学，也不像 RRC 那样全是状态机，而是一条从 USIM 卡到 PDCP 层的、环环相扣的密钥派发流水线。你熟悉 HTTPS 的话，可以把整章读成"LTE 版的 TLS"：PSK 预共享（K）、握手换 nonce（RAND）、双向校验（RES/XRES）、派生会话密钥（KASME 及子孙）、然后进入加密传输（EEA/EIA）。区别只在于 LTE 的这套东西被拆进了 USIM、HSS、MME、eNodeB 四个实体，而且每一环都有 3GPP 规范编号背书。

本章按数据流向组织：先看密钥全景，再精读 Milenage 的每一个函数，然后跟着 eNodeB 代码走一遍真实鉴权流程，最后盘点 OpenLTE 的简化与攻击面。涉及的规范主要是 33.401（EPS 安全架构与 KDF）、35.206（Milenage 算法）、33.102（AKA 与 SQN 管理）、24.301（NAS 安全）、36.323/36.331（AS 侧安全）。

4.1 密钥全景：USIM 里只有 K 和 OP

先建立一个关键认知：整套 LTE 密钥体系里，真正的"秘密"只有两个——烧在 USIM 卡里的 128 bit 根密钥 K，和运营商常量 OP。其余所有密钥（CK、IK、KASME、KNASenc、KeNB、KRRCenc……）全部是运行时派生出来的。USIM 和 HSS 各存一份 K 和 OP，K 永远不离开这两个地方；网络上跑的全是派生密钥。

这和你熟悉的 TLS PSK 模式几乎同构：预共享密钥不出手，握手里只交换随机数，双方各自算出相同的会话密钥。LTE 只是把这个"各自算"的链条拉长了：

4.2 Milenage 精读：f1–f5 与 OP 的作用

4.2.1 输入、输出与 OP 的角色

Milenage（35.206）不是一个算法，而是一组以 AES-128 为核心构件的函数族 f1–f5、f1*、f5*。输入输出一览：

函数输入输出用途
f1K, RAND, SQN, AMFMAC-A（8 字节）网络侧自证：让 USIM 验证 AUTN 合法
f1*K, RAND, SQN, AMFMAC-S（8 字节）重同步时校验 AUTS
f2K, RANDRES（8 字节）UE 应答："我证明我有 K"
f3K, RANDCK（16 字节）派生 KASME 的原料
f4K, RANDIK（16 字节）派生 KASME 的原料
f5K, RANDAK（6 字节）匿名密钥，异或掩盖 SQN 防窃听关联
f5*K, RANDAK（6 字节）重同步路径上解 AUTS 里的 SQN

几个公共输入的含义：

字段宽度含义规范
K128 bitUSIM/HSS 共享根密钥35.206
OP128 bit运营商常量（Operator Variant）35.206
RAND128 bit网络侧随机挑战33.102
SQN48 bit序列号，防重放33.102
AMF16 bit鉴权管理字段33.102

OP 是干什么的？ 这是新人最容易卡住的点。Milenage 本身只有 K 是秘密，但运营商希望"即使别人拿到我的算法实现和 K 的泄露样本，也不能直接拿去攻击别家网络"。做法是在所有函数里混入一个运营商自定义的 128 bit 常量 OP，更准确地说，先算一次 OPc = AES_K(OP) ⊕ OP，之后所有运算用 OPc 而不是直接用 OP。这样：

  • 不同运营商的 f1–f5 输出空间被 OP 隔离开，互不相通；
  • 手机丢了不用换 K 的"换"，换的是 OP 维度——更实际的说法是：运营商可以在不换算法的前提下通过 OP 定制自己的安全域；对烧卡实验来说，USIM 里写的 OP 必须和 HSS 侧代码里的 OP 一致，否则 MAC 校验永远失败。

本仓库的 OP 硬编码在 liblte/src/liblte_security.cc:63-64：

static const uint8 OP[16] = {0x11,0x11,0x11,0x11,0x11,0x11,0x11,0x11,
0x11,0x11,0x11,0x11,0x11,0x11,0x11,0x11};

即全 0x11。README 里说明了这个 fork 把上游默认值（63bfa50e…，见 README.md:405-407）改成了这个值（README.md:416-423），所以你自己烧卡时必须用 --set-op 写入同一个 OP，两边对得上才能鉴权成功。

4.2.2 AES（Rijndael）是怎么被复用的

liblte_security.cc 没有依赖外部库来实现 Milenage 的 AES，而是自带了一份教科书式的 Rijndael 参考实现，和 35.206 附录里的伪代码逐行对应：

  • S 盒 S[256]：liblte/src/liblte_security.cc:66；GF(2^8) 乘 2 查表 X_TIME[256]：同文件 83 行。
  • rijndael_key_schedule（1057 行）：把 16 字节 K 展开成 11 组轮密钥，存进 ROUND_KEY_STRUCT（51-53 行）。
  • rijndael_encrypt（1098 行）：标准 10 轮——第 0 轮只做 key_add，第 1–9 轮做 byte_sub/shift_row/mix_column/key_add，第 10 轮去掉 mix_column（1113-1125 行）。你熟悉 AES 结构的话，这就是一份没有查表优化、没有抗侧信道防护的"教学版" AES。
  • compute_OPc（1037-1048 行）：op_c = AES_K(OP) ⊕ OP，每次调用 f1/f2345 都现场重算（真实 USIM 会把它预计算固化）。

注意这里的 AES 和 EIA2 用的 AES 不是同一份代码：EIA2 走的是 PolarSSL（liblte/src/liblte_security.cc:38-39 的 include，以及 490-491 行的 aes_setkey_enc/aes_crypt_ecb）。一个文件里两套 AES 并存，读代码时别搞混。

4.2.3 f1：MAC-A 的生成

liblte_security_milenage_f1（liblte/src/liblte_security.cc:697）的流程是两次 AES 的"加掩码链"：

        // Compute temp
        for(i=0; i<16; i++)
        {
            rijndael_input[i] = rand[i] ^ op_c[i];          // 727 行：RAND ⊕ OPc
        }
        rijndael_encrypt(rijndael_input, &round_keys, temp); // 729 行：TEMP = AES_K(RAND⊕OPc)
        ...
        for(i=0; i<16; i++)
        {
            rijndael_input[(i+8) % 16] = in1[i] ^ op_c[i];   // 746 行：SQN‖AMF 块旋转 8 字节再 ⊕OPc
        }
        for(i=0; i<16; i++)
        {
            rijndael_input[i] ^= temp[i];                    // 750 行：再 ⊕ TEMP
        }
        rijndael_encrypt(rijndael_input, &round_keys, out1);
        for(i=0; i<16; i++)
        {
            out1[i] ^= op_c[i];                              // 755 行：输出再 ⊕ OPc
        }

逐行说：先把 RAND 与 OPc 异或后过一遍 AES 得到 TEMP；然后把 in1（SQN 出现两次、AMF 出现两次，共 16 字节，见 731-741 行的构造）旋转 8 字节、异或 OPc、再异或 TEMP，过第二遍 AES，输出再异或一次 OPc。最终取 OUT1 的前 8 字节就是 MAC-A（759-762 行）。这一大串异或/旋转常量全部来自 35.206，属于"照规范抄"型代码——读它不是为了学设计，而是为了在排查鉴权失败时能逐字节对账。

liblte_security_milenage_f2345（863 行）把 f2/f3/f4/f5 合并在一个函数里，因为它们共享同一个 TEMP = AES_K(RAND⊕OPc)（892-896 行），之后只是旋转量和常数不同：

输出代码位置旋转量末尾异或常数取值
RES / AK899-920 行01（903 行）RES = out[8..15]，AK = out[0..5]
CK923-938 行12（(i+12)%16，925 行）2（927 行）全 16 字节

4.2.5 KDF：HMAC-SHA256 套一层模板

过了 Milenage 拿到 CK/IK 之后，再往下的密钥派生全部换成 33.401 Annex A 定义的 KDF，本质是 HMAC-SHA256。以 liblte_security_generate_k_asme（213 行）为例，核心是构造一个 14 字节的输入串 S：

        s[0] = 0x10; // FC                                        // 233 行：区分算法用途
        s[1] = (((mcc/10) % 10) << 4) | ((mcc/100) % 10);         // 234 行起：P0 = PLMN id（MCC/MNC）
        ...
        s[4] = 0x00; s[5] = 0x03;                                 // 243-244 行：L0 = P0 长度
        for(i=0; i<6; i++)
        {
            s[6+i] = sqn[i] ^ ak[i]; // P1                        // 247 行：SQN⊕AK
        }
        s[12] = 0x00; s[13] = 0x06;                               // 249-250 行：L1 = P1 长度
        ...
        sha2_hmac(key, 32, s, 14, k_asme, 0);                     // 260 行：key = CK‖IK

S 的通用模板是 FC ‖ P0 ‖ L0 ‖ P1 ‖ L1 …，FC（Function Code）区分派生的是哪种密钥。对比着看整份文件你会发现所有 KDF 都是同一个模子：

函数FCP0P1
k_asme（213 行）0x10SN-id（MCC/MNC）SQN⊕AK
k_enb（275 行）0x11UL NAS COUNT—
k_nas（310 行）0x15算法类型（0x01=enc / 0x02=int）算法 ID
k_rrc（360 行）0x15算法类型（0x03/0x04）算法 ID
k_up（411 行）0x15算法类型（0x05/0x06）算法 ID

把算法 ID 混进 KDF 输入是 33.401 的明确要求：同一根密钥在不同算法下派生出不同的子密钥，防止"算法降级时密钥可复用"这类攻击。

4.3 鉴权流程实战：跟着 eNodeB 代码走一遍

OpenLTE 没有独立的核心网，HSS 和 MME 都是 eNodeB 进程里的一个单例类。下面按时间顺序走一遍 attach 时的 EPS AKA。

第 0 步：用户入库。 K 存在 HSS 的用户表里。LTE_fdd_enb_hss::add_user（LTE_fdd_enodeb/src/LTE_fdd_enb_hss.cc:126）接收 15 位 IMSI、15 位 IMEI 和 32 个十六进制字符的 K，转成 16 字节存进 stored_data.k（141 行），并把 SQN 相关计数清零（143-145 行）。数据结构就是 LTE_fdd_enodeb/hdr/LTE_fdd_enb_hss.h:66-87：stored_data 里只有 K，generated_data 里是每次鉴权现算的 auth_vec、SQN、KASME、KeNB 等。用户表还可以落盘到 /tmp/LTE_fdd_enodeb.user_db（LTE_fdd_enodeb/src/LTE_fdd_enb_hss.cc:536）——注意这是明文存根密钥的调试便利，不是安全设计。

第 1 步：Attach Request 触发鉴权。 MME 收到 Attach Request（parse_attach_request，LTE_fdd_enodeb/src/LTE_fdd_enb_mme.cc:489），先存下 UE 的 EEA/EIA 能力位图（538-542 行），查 HSS 确认 IMSI 在白名单里，然后检查 UE 必须支持 EEA0 和 EIA2（616 行），通过就把状态机拨到 LTE_FDD_ENB_MME_STATE_AUTHENTICATE（618 行）。

第 2 步：生成鉴权向量。 状态机走到 send_authentication_request（1472 行），第一件事是调 hss->generate_security_data（1483 行）。这个函数（LTE_fdd_enodeb/src/LTE_fdd_enb_hss.cc:290）就是整个 AKA 的"厨房"：

            // Generate MAC, RES, CK, IK, and AK
            liblte_security_milenage_f1((*iter)->stored_data.k, ...     // 327 行：MAC-A
                                        (*iter)->generated_data.mac);
            liblte_security_milenage_f2345((*iter)->stored_data.k, ..., // 332 行：RES/CK/IK/AK
                                           (*iter)->generated_data.auth_vec.res,
                                           (*iter)->generated_data.auth_vec.ck,
                                           (*iter)->generated_data.auth_vec.ik,
                                           (*iter)->generated_data.ak);
            // Construct AUTN
            for(i=0; i<6; i++)
            {
                (*iter)->generated_data.auth_vec.autn[i] = sqn[i] ^ (*iter)->generated_data.ak[i];  // 342 行
            }

在它之前，306-314 行按 33.102 的 SEQ‖IND 结构递增 SQN，316-324 行生成 RAND，299 行固定 AMF = 0x8000。AUTN 的拼装（339-351 行）严格按规范布局：

第 3 步：下发 Authentication Request。 回到 send_authentication_request，把 AUTN 和 RAND 拷进 NAS 消息（1488-1492 行），KSI 置 0 并标记 native 安全上下文（1493-1494 行），打包下发（1495 行）。RES 和 KASME 留在 HSS 侧等比对。

4.4 SQN 同步与 resync：代码实现了多少

SQN 存在的意义是防重放：USIM 只接受"比上次新且落在窗口内"的 SQN。但两端计数会跑偏（比如 UE 在别的网络鉴权过），于是 AKA 设计了重同步：UE 回 Authentication Failure（cause = synch failure）并携带 AUTS = (SQN_MS ⊕ AK*) ‖ MAC-S，网络侧用 f5* 解出 UE 的真实 SQN，用 f1* 验证 MAC-S，然后以 UE 的 SQN 为基准重新生成向量。

OpenLTE 实现了这条链路的一半。上行处理在 parse_authentication_failure（LTE_fdd_enodeb/src/LTE_fdd_enb_mme.cc:658）：识别出 synch failure 且带 AUTS 参数后，调 hss->security_resynch（680 行）。后者（LTE_fdd_enodeb/src/LTE_fdd_enb_hss.cc:397）做的事是：

            liblte_security_milenage_f5_star((*iter)->stored_data.k,     // 413 行：算 AK*
                                             (*iter)->generated_data.auth_vec.rand,
                                             (*iter)->generated_data.ak);
            (*iter)->generated_data.sqn_he = 0;
            for(i=0; i<6; i++)
            {
                sqn[i] = auts[i] ^ (*iter)->generated_data.ak[i];        // 419 行：解出 SQN_MS
                ...
            }

解出 SQN_MS、拆回 SEQ/IND、把 IND 减一（424-427 行，让下一次递增后恰好接上 UE 的序号）。

要如实指出的是两个缺口：其一，resynch 路径没有用 f1* 校验 MAC-S——liblte_security_milenage_f1_star 这个函数在整个仓库里没有任何调用方（可以自己 grep 确认），意味着攻击者理论上可以伪造 AUTS 篡改 HSS 侧的 SQN 计数；其二，resynch 之后状态机没有自动重发 Authentication Request 的分支，parse_authentication_failure 走完 security_resynch 就结束了，下一次向量何时生成依赖流程再次被触发。属于"能跑通正常场景、异常路径没闭环"的研究代码典型状态。

4.5 NAS 安全：Security Mode Command 之后

鉴权通过只说明"双方都算得出 KASME"，NAS 消息真正进入保护态要等 Security Mode Command 握手完成。

下行：选算法。 send_security_mode_command（LTE_fdd_enodeb/src/LTE_fdd_enb_mme.cc:1646）把选定算法写死为 EEA0 + EIA2（1654-1655 行），把 UE 之前在 Attach Request 里上报的能力位图原样回放进去（1658-1665 行，这是 24.301 要求的防降级措施——UE 会比对回放的能力和自己发的是否一致），然后用新生成的 KNASint 给整条消息算 MAC，安全头类型为"新安全上下文完整性保护"（1688-1693 行）。KNASenc/KNASint 早在 §4.3 第 2 步就由 liblte_security_generate_k_nas（liblte/src/liblte_security.cc:310）派生好了，这里只是取用。

上行：收到 Security Mode Complete。 parse_security_mode_complete（883 行）解包、可选地比对 IMEISV（902-922 行），然后把状态拨到 RRC_SECURITY（935 行），接下来才轮到 AS 安全。

MAC 怎么算。 所有 NAS 安全消息的 MAC 都走同一个函数：liblte_mme_pack_security_protected_nas_msg（liblte/src/liblte_mme.cc:5681）。受保护的 NAS 消息头部布局（24.301）：

字段宽度含义
Security header type ‖ PD1 字节高 4 bit 安全头类型，低 4 bit 协议鉴别符
MAC4 字节EIA 输出的截断值
Sequence number1 字节NAS COUNT 的低 8 bit
NAS message变长真正的 EMM/ESM 消息

打包时先把 MAC 的 4 字节留空、填好序号和消息体，最后调 EIA2 把 MAC 回填（liblte/src/liblte_mme.cc:5723-5729）：

            // Calculate MAC
            liblte_security_128_eia2(&key_256[16],        // 后 16 字节作 128-bit 密钥
                                     count,               // NAS COUNT
                                     0,                   // bearer：NAS 固定为 0
                                     direction,
                                     &sec_msg->msg[5],    // 被保护的消息体
                                     sec_msg->N_bytes-5,
                                     &sec_msg->msg[1]);   // MAC 写回头部 1-4 字节

EIA2 本身是 AES-CMAC（RFC4493）：先用 AES_K(0) 生成子密钥 L，再左移派生 K1/K2（liblte/src/liblte_security.cc:490-513），把 COUNT‖BEARER‖DIRECTION 拼在消息前当 CMAC 输入（516-525 行，其中 521 行 M[4] = (bearer << 3) | (direction << 2) 就是那个 1 字节的 bearer/direction 字段），CBC-MAC 式迭代后取前 4 字节作为 MAC-I（559-562 行）。

MAC 怎么验？——如实说：没有验。 这是 OpenLTE 最重要的简化之一。库里所有 liblte_mme_unpack_*_msg 都只解包不校验：安全头被直接跳过（如 liblte_mme_unpack_attach_accept_msg，liblte/src/liblte_mme.cc:5915-5921 对非明文消息直接 msg_ptr += 7），没有任何地方重算 MAC 与消息里的值比对。eNodeB 侧收到上行 NAS 后，handle_nas_msg 只是分发消息并把 nas_count_ul 加一（LTE_fdd_enodeb/src/LTE_fdd_enb_mme.cc:368）。也就是说：下行方向 MAC 算得一丝不苟，上行方向照单全收。读代码时如果你发现"篡改过的 NAS 消息也能过"，这不是 bug 复现了，是根本没实现。

另一个相关细节在 Service Request 路径：parse_service_request 会拿 UE 上报的 NAS 序号和本地 nas_count_ul 比对，不一致时直接以 UE 的值为准调 regenerate_enb_security_data 重派 KeNB 系列密钥（LTE_fdd_enb_mme.cc:1006-1026）——因为 MAC 不验，这里只能靠序号对账兜底。

4.6 AS 安全：RRC 与 PDCP

NAS 安全搞定后，MME 经 RRC_SECURITY 状态让 RRC 层发 AS 侧的 SecurityModeCommand（LTE_fdd_enodeb/src/LTE_fdd_enb_rrc.cc:1068）：算法同样写死 EEA0 + EIA2（1076-1077 行），发完后立刻把该 RB 的 PDCP 切到安全配置（1089 行）。UE 回 SecurityModeComplete 后 RRC 通知 MME（693-701 行），attach 流程继续往下走。

AS 安全的执行点是 PDCP 层（36.323 规定加密和完整性都在 PDCP 做，RRC 消息作为 PDCP 的 SDU 被保护）。OpenLTE 里下行 SRB 的完整性在 LTE_fdd_enodeb/src/LTE_fdd_enb_pdcp.cc:391-398：PDCP 配置为 SECURITY 时，调 liblte_pdcp_pack_control_pdu 并传入用户的 k_rrc_int。这个打包函数（liblte/src/liblte_pdcp.cc:128-148）在 PDU 尾部留 4 字节，调 liblte_security_128_eia2 算 MAC-I 回填——和 NAS 那套是同一个 EIA2，只是 COUNT 换成 PDCP COUNT、bearer 换成 RB id 减一。上行方向与 NAS 同病：liblte_pdcp_unpack_control_pdu（liblte/src/liblte_pdcp.cc:158-186）直接忽略 MAC-I 字段，不验证。

至于加密：EEA0 等于不加密，而 OpenLTE 全线选的就是 EEA0，所以整条代码路径里不存在任何真实的加密动作——KRRCenc、KUPenc 被老老实实派生出来（LTE_fdd_enodeb/src/LTE_fdd_enb_hss.cc:380-391），然后就没有然后了。库里 EEA1/EEA2 的枚举值在 liblte/hdr/liblte_security.h:98-106 里躺着，但没有对应的实现函数。想在 OpenLTE 上验证"加密后的空口流量"，是验证不了的。

4.7 OpenLTE 的安全简化与已知攻击面

把前面散落的简化集中列一下，这也是你拿 OpenLTE 做任何安全实验前必须知道的边界：

  • OP 硬编码、K 明文落盘：OP 是编译期常量（liblte/src/liblte_security.cc:63），改 OP 要重新编译；用户数据库 /tmp/LTE_fdd_enodeb.user_db 明文存 K（LTE_fdd_enodeb/src/LTE_fdd_enb_hss.cc:536）。
  • RAND 不随机：HSS 用 rand() 生成 RAND（LTE_fdd_enodeb/src/LTE_fdd_enb_hss.cc:319），不是密码学安全的随机源，且未见 srand 播种的保障——两次运行可能产生可预测的挑战序列。
  • 只算不验：上行 NAS MAC 不验、上行 PDCP MAC-I 不验（§4.5、§4.6）；resync 不验 MAC-S（§4.4）。
  • EEA0 裸奔：没有实现任何加密算法，空口全是明文。
  • 能力检查形同虚设：只查 UE 是否支持 EEA0/EIA2（LTE_fdd_enodeb/src/LTE_fdd_enb_mme.cc:616），而 EEA0 本身就是"不加密"。

正因为主线这么"裸"，这个仓库（更准确地说，它背后的 fork 生态）衍生出了一批攻击分支。README 的 "Attack implementations" 一节（README.md:26-37）列出了 @onkarmumbrekar 实现的攻击，分布在各自的 git 分支里：akabypass、attach_reject、dos_tau_reject、dos_tau_reject_dualcase、malformed_detach、numb_attack、service_reject_on_tau、tau_numb_attack。注意：这些分支不在你当前这份代码里（本地只有 master），需要到对应 fork 的分支上去看。按分支名和这类研究的公开背景，它们大致是：

  • akabypass：跳过/旁路 AKA 鉴权流程的变种——主线状态机里鉴权是强制一站，这个分支演示绕过它之后 UE 和网络各自还能走到哪里；
  • attach_reject / service_reject_on_tau / dos_tau_reject(_dualcase)：利用恶意 eNodeB 在 Attach/TAU/Service Request 阶段回带特定 EMM cause 的 Reject 消息，让 UE 把网络或 USIM 标记为不可用，实现拒绝服务；
  • malformed_detach：发送畸形 Detach 消息试探 UE 协议栈的健壮性；
  • numb_attack / tau_numb_attack：借 TAU 流程让 UE"失联"（numb）的攻击变体。

把它们当作主线的反面教材来读效果最好：每一个攻击分支能成立，几乎都对应主线里的一个"简化"——不验 MAC、明文、异常路径不闭环。读攻击代码时对照本章的行号问自己"这步要是验了 MAC 还会成功吗"，是消化本章最好的练习。

4.8 小结

  • LTE 密钥体系里唯一的秘密是 USIM/HSS 共享的 K 和运营商常量 OP；CK/IK→KASME→KNAS/KeNB→KRRC/KUP 全部是运行时经 Milenage 和 HMAC-SHA256 KDF 派生的，代码集中在 liblte/src/liblte_security.cc。
  • Milenage f1–f5 共享同一个 AES 核心（自带 Rijndael 参考实现，1057/1098 行），各函数的区别只在输入块的旋转量和异或常数；f1 产 MAC-A 供 USIM 验网，f2345 产 RES/CK/IK/AK。
  • eNodeB 侧鉴权全流程：HSS generate_security_data（LTE_fdd_enodeb/src/LTE_fdd_enb_hss.cc:290）算向量并派生全密钥树 → send_authentication_request（LTE_fdd_enodeb/src/LTE_fdd_enb_mme.cc:1472）下发 RAND/AUTN → parse_authentication_response（694 行）比对 RES。
  • NAS 完整性用 EIA2（AES-CMAC），打包时统一在 liblte_mme_pack_security_protected_nas_msg（liblte/src/liblte_mme.cc:5681）算 MAC；AS 侧 SRB 完整性在 PDCP（liblte/src/liblte_pdcp.cc:140）。但上行方向 MAC 一律不验，且全线 EEA0 无加密。
  • SQN 重同步只实现了一半：f5* 解 SQN 有（LTE_fdd_enodeb/src/LTE_fdd_enb_hss.cc:397），f1* 验 MAC-S 无人调用。
  • README 列出的 akabypass、attach_reject 等攻击分支不在本仓库 master 上，它们是对"主线安全简化"的活体演示，适合对照本章逐条反查。

第5章 MAC / RLC / PDCP：L2 三层在 OpenLTE 里的实现

前面几章把 RRC、NAS 这些"信令内容"讲清楚了。这一章往下走一层：一条消息编码成比特流之后，并不是直接扔给 PHY 的，它要先穿过 L2 的三个子层——PDCP、RLC、MAC，每层给它"戴一顶帽子"（加上自己的头）。读完本章，你应该能回答一个具体问题：一条 RRC 消息从 LTE_fdd_enb_rrc.cc 出来，到交给 PHY 之前，字节流到底长什么样，每一层分别加上了什么。

先建立一个整体印象：OpenLTE 把"协议格式"和"协议行为"拆成了两半。

  • liblte/src/liblte_mac.cc、liblte_rlc.cc、liblte_pdcp.cc 是纯函数式的 pack/unpack 库：给它一个结构体，它帮你按 3GPP 规范把比特摆好；反过来把字节流解析回结构体。这里没有任何状态。
  • LTE_fdd_enodeb/src/LTE_fdd_enb_mac.cc、LTE_fdd_enb_rlc.cc、LTE_fdd_enb_pdcp.cc 是 eNodeB 侧的 运行时层：维护序号、窗口、重传 buffer、调度队列这些状态，通过消息队列（LTE_fdd_enb_msgq）互相驱动。

你可以把 liblte 想成"编解码器"，把 enodeb 那一组文件想成"状态机 + 流水线"。

L2 总览：SDU/PDU 与串起三层的 rb 对象

先统一词汇。每一层从上层拿到的数据叫 SDU（Service Data Unit），加工后交给下层的叫 PDU（Protocol Data Unit）。本层的 PDU 就是下一层的 SDU，仅此而已。三层各自的职责一句话：

  • PDCP（36.323）：给控制面消息做完整性保护（MAC-I）、维护 COUNT 序号；用户面本应有头压缩（ROHC）和加密。
  • RLC（36.322）：分段/级联与重组，AM 模式下提供 ARQ 重传，保证按序、不丢。
  • MAC（36.321）：把多条逻辑信道的数据复用进一个传输块（TB），做调度，HARQ 也挂在它头上。

eNodeB 这边三层之间不是函数直接调用，而是"队列 + 消息通知"的异步流水线。承载这条流水线的核心对象是 LTE_fdd_enb_rb（radio bearer），定义在 LTE_fdd_enodeb/hdr/LTE_fdd_enb_rb.h:195。一个 rb 实例对应一条无线承载（SRB0/SRB1/SRB2/DRB1/DRB2，枚举见 LTE_fdd_enodeb/hdr/LTE_fdd_enb_rb.h:85），它内部为每一层都准备了一对 FIFO 队列，例如下行方向的 pdcp_sdu_queue → rlc_sdu_queue → mac_sdu_queue（声明见 LTE_fdd_enb_rb.h:337-373）。

数据流动的固定套路是：

  1. 上层把数据 queue_* 进 rb 的队列；
  2. 通过 msgq 给下层发一个 *_SDU_READY 通知；
  3. 下层的 handler 被回调，从 rb 队列里 get_next_* 取出数据，加工后再 queue_* 给更下层，并发新的通知。

rb 构造函数 LTE_fdd_enodeb/src/LTE_fdd_enb_rb.cc:94-178 是全章最值得记住的一段代码，因为它直接回答了"每条承载用什么配置"：

{

}else if(LTE_FDD_ENB_RB_DRB1 == rb){
    pdcp_config = LTE_FDD_ENB_PDCP_CONFIG_LONG_SN;

对照规范（36.331）：SRB0 走 CCCH，RLC 必须是 TM；SRB1/SRB2 走 DCCH，RLC 用 AM——代码和规范是一致的。值得注意的是 UM（非确认模式）在 eNodeB 侧是死代码：LTE_fdd_enb_rlc.cc 里有完整的 handle_um_pdu/handle_um_sdu（LTE_fdd_enb_rlc.cc:330、:667），但全仓库没有任何地方把某个 rb 的 rlc_config 设成 LTE_FDD_ENB_RLC_CONFIG_UM（构造函数里只有 TM 和 AM 两种赋值，见 LTE_fdd_enb_rb.cc:109-133）。liblte 里的 UMD pack/unpack 因此只有库层面的意义。

MAC：subheader 结构与"够用就行"的调度

MAC PDU 的头：一串 subheader

MAC PDU 的结构是"一串 subheader + 对应的 payload（SDU 或控制单元 CE）"。每个 subheader 第一个字节的布局（36.321）：

字段比特宽含义
R1保留位，置 0
R1保留位，置 0
E1Extension：1 = 后面还有 subheader，0 = 这是最后一个
LCID5逻辑信道号或 CE 类型
F1（仅需要长度字段时）L 字段是 7 还是 15 比特
L7/15（非最后一个 subheader 时）对应 payload 的字节数

LCID 的取值表定义在 liblte/hdr/liblte_mac.h:320-343，常用的几个：DL-SCH 上 0x00=CCCH、0x01..0x0A=DCCH（也就是 SRB1/SRB2/DRB）、0x1C=UE Contention Resolution Identity CE、0x1D=TA Command CE、0x1F=Padding；UL-SCH 上 0x1D/0x1E=Short/Long BSR。

打包逻辑在 liblte_mac_pack_mac_pdu（liblte/src/liblte_mac.cc:666）。写 subheader 的核心循环：

// liblte/src/liblte_mac.cc:679-689
for(i=0; i<pdu->N_subheaders; i++)
{
    liblte_value_2_bits(0, &msg_ptr, 1); // R
    liblte_value_2_bits(0, &msg_ptr, 1); // R
    if(i != pdu->N_subheaders-1)
        liblte_value_2_bits(1, &msg_ptr, 1); // E：后面还有
    else
        liblte_value_2_bits(0, &msg_ptr, 1); // E：最后一个
    liblte_value_2_bits(pdu->subheader[i].lcid, &msg_ptr, 5);

随后按 LCID 判断要不要写 F/L 字段（固定长度的 CE 和最后一个 subheader 不写 L，见 liblte_mac.cc:690-709）。解包侧 liblte_mac_unpack_mac_pdu（liblte/src/liblte_mac.cc:859）则是靠 E 比特驱动一个 while(e_bit) 循环把 subheader 链读完（liblte_mac.cc:874-878），最后一个 SDU 的长度用"剩余比特数"倒推（liblte_mac.cc:979-981）。控制单元（BSR、TA Command、Power Headroom 等）各自的 pack/unpack 都在同一个文件里，比如 TA Command 是 2 个 R 比特 + 6 比特 TA 值（liblte_mac.cc:338-348）。

eNodeB 侧的 MAC：复用、调度、HARQ

下行方向，MAC 收到 RLC 的 SDU 后的入口是 LTE_fdd_enb_mac::handle_sdu_ready（LTE_fdd_enodeb/src/LTE_fdd_enb_mac.cc:679）。它做的事非常直白：

  1. 填好 PHY 分配参数（QPSK、tx_mode、NDI 翻转等，:699-717）；
  2. 组 LIBLTE_MAC_PDU_STRUCT：如果该 rb 需要发竞争解决 ID，就塞两个 subheader（一个 UE Con Res ID CE + 一个 SDU），否则只有一个 SDU subheader，LCID 直接用 rb 编号（:720-733）；
  3. 把整个 PDU 挂进 dl_sched_queue，目标 TTI 是"当前 + 4"（:736-739）——这就是 LTE FDD 里下行调度提前 4ms 的惯例。

真正的调度器是 scheduler()（LTE_fdd_enb_mac.cc:1150），每个子帧被 handle_ready_to_send（:376）触发一次，依次处理 RAR 队列、下行队列、上行队列。下行部分（:1325-1467）的流程是：取队首 PDU → liblte_mac_pack_mac_pdu 打出比特流（:1342）→ 按可用 PRB 查 TBS/MCS（:1344）→ 如果 TBS 比实际比特数大，插 Padding subheader 后重新打包（:1361-1388）→ 写进子帧结构并给 PHY。

上行调度 sched_ul（:1087）同样朴素：收到 BSR 或 SR 后按请求的比特数查 TBS/MCS/N_prb（:1111），把 grant 排进队列。

这里要如实说：OpenLTE 没有逻辑信道优先级（LCP）算法。36.321 里的优先级、PBR、prioritisedBitRate 这些概念在代码里完全没有出现——handle_sdu_ready 来一个 SDU 就组一个 PDU 排队，FIFO 出队，调度资源检查只有"PRB 够不够、CCE 够不够"（:1401-1402）。MCS 也不是链路自适应的：DL 每用户每子帧上限写死 325 字节、UL 写死 50 字节，注释里直接标着 FIXME（LTE_fdd_enodeb/src/LTE_fdd_enb_user.cc:743-752）。HARQ 有一个简化实现：收到 PUCCH 上的 NACK 后，handle_pucch_ack_nack（LTE_fdd_enb_mac.cc:511）把存起来的 PDU 原样重新排进调度队列（重传次数有上限 LTE_FDD_ENB_MAX_HARQ_RETX，:541），没有增量冗余，rv_idx 恒为 0（:703）。

UMD PDU 头（36.322）

UMD 头第一字节（5 bit SN 时）：

*pdu_ptr |= umd->hdr.sn & 0x1F;          // SN 低 5 位
pdu_ptr++;

如果一个 PDU 里级联了多个 SDU，头里还要追加 E+LI（Length Indicator，11 bit）列表，pack/unpack 里那段按奇偶交替处理 LI 的循环（liblte_rlc.cc:99-124、:214-236）就是在做这件事。

AMD PDU 头

AMD 头固定部分两字节（36.322）：

字段比特宽含义
D/C10=控制 PDU（STATUS），1=数据 PDU
RF10=AMD PDU，1=AMD PDU segment（重传时再分段）
P1Poll：请求对端回 STATUS 报告
FI2同 UM
E1是否有 E+LI 扩展
SN10序号（跨前两字节）

打包见 liblte_rlc.cc:346-354；如果是 segment（RF=1），还要再补两字节 LSF+SO（segment 在原 PDU 里的字节偏移），见 liblte_rlc.cc:355-361。解包侧在 liblte_rlc.cc:388-407。

AM 的控制 PDU 是 STATUS PDU：D/C=0 + 3 bit CPT + 10 bit ACK_SN（第一个没收到的 SN）+ 若干 NACK_SN 列表，pack 见 liblte_rlc.cc:503-521。注意 SOstart/SOend（按字节粒度 NACK segment）没有实现，代码里是两个 FIXME（liblte_rlc.cc:547、:615）。

eNodeB 侧 RLC 的 ARQ：实现了多少

状态变量都在 rb 对象里：接收侧 VR(R)/VR(MR)/VR(H)，发送侧 VT(A)/VT(MS)/VT(S)（LTE_fdd_enb_rb.h:358-363），AM 窗口 512（liblte/hdr/liblte_rlc.h:51）。

发送路径：handle_am_sdu（LTE_fdd_enb_rlc.cc:763）拿到 SDU 后按 325 字节上限分段、打 SN（VT(S) 递增）、设 FI；PDU 先存进 rlc_am_transmission_buffer（LTE_fdd_enb_rb.cc:731）再交给 MAC，同时启动 t-PollRetransmit 定时器（100ms，LTE_fdd_enb_rb.cc:784-792）。

接收路径：handle_am_pdu（LTE_fdd_enb_rlc.cc:452）解包后做窗口检查（VR(R) <= SN < VR(MR)，:482-483），在窗内就进 reception buffer、更新 VR(H)、尝试按 SN 重组 SDU 上交 PDCP，然后无条件回 STATUS PDU（:534-539——注意 if(p) 被注释掉了，这是作者的简化：不等 Poll 位，每个 AMD PDU 都触发状态报告）。

重传：收到 STATUS PDU 后 rlc_update_transmission_buffer（LTE_fdd_enb_rb.cc:743）把被 ACK 的 PDU 从发送 buffer 删掉、推进 VT(A)；t-PollRetransmit 超时就取 VT(A) 处最老的 PDU 重发并把 P 位置 1（LTE_fdd_enb_rb.cc:801-812、LTE_fdd_enb_rlc.cc:220-259）。

没实现的部分也要说清楚：AMD PDU segment 的接收被显式拒绝（LTE_fdd_enb_rlc.cc:471-478，"Not handling AMD PDU segments"）；t-Reordering、t-StatusProhibit 这两个定时器不存在；VR(MS) 的更新标着 FIXME（LTE_fdd_enb_rlc.cc:511）。所以这是一个"能跑通基本 ARQ 闭环"的教学级实现，不是完整的 36.322。

PDCP：序号、完整性，以及没有实现的加密和 ROHC

头格式

控制面 PDCP Data PDU（SRB 用，36.323）的头极简：1 字节，低 5 位是 SN，高 3 位保留。PDU 尾部再挂 4 字节 MAC-I。打包在 liblte/src/liblte_pdcp.cc:89-157：

// liblte_pdcp.cc:106-107
*pdu_ptr = contents->count & 0x1F;   // 头部 = COUNT 的低 5 位（即 PDCP SN）
pdu_ptr++;

MAC-I 的计算（:139-147）：如果调用方给了密钥，就调 liblte_security_128_eia2 算 4 字节认证码；没给密钥就填占位值 0（LIBLTE_PDCP_CONTROL_MAC_I，liblte/hdr/liblte_pdcp.h:70）。

用户面 Data PDU 头：D/C 位 1 + 12 bit 长 SN（两字节，pack 见 liblte_pdcp.cc:210-213）或 7 bit 短 SN（一字节，:279）。

安全在哪里被调用

eNodeB 侧的发送入口是 LTE_fdd_enb_pdcp::handle_sdu_ready（LTE_fdd_enodeb/src/LTE_fdd_enb_pdcp.cc:325）。对 SRB1/SRB2：

// LTE_fdd_enb_pdcp.cc:390-403
contents.count = sdu_ready->rb->get_pdcp_tx_count();
if(LTE_FDD_ENB_PDCP_CONFIG_SECURITY == sdu_ready->rb->get_pdcp_config())
    liblte_pdcp_pack_control_pdu(&contents, sdu,
        sdu_ready->user->get_auth_vec()->k_rrc_int,   // KRRCint
        LIBLTE_SECURITY_DIRECTION_DOWNLINK,
        sdu_ready->rb->get_rb_id()-1,                 // RB id = SRB id - 1
        &pdu);
else
    liblte_pdcp_pack_control_pdu(&contents, sdu, &pdu);  // 不带密钥，MAC-I 填 0

pdcp_config 什么时候变成 SECURITY？在 RRC 发出 SecurityModeCommand 的那一刻（LTE_fdd_enodeb/src/LTE_fdd_enb_rrc.cc:1089）。这就和安全章串起来了：密钥层级推导出 KRRCint 之后，真正使用它的地方就是这里，算法固定为 128-EIA2（SecurityModeCommand 里写死 EIA2，见 LTE_fdd_enb_rrc.cc:1077）。

两个"如实写"的事实：

  • 加密（ciphering）没有实现。整个 liblte_security 库里只有密钥生成、128-EIA2 和 Milenage，没有任何 EEA 函数；RRC 层选的就是空算法 EEA0（LTE_fdd_enb_rrc.cc:1076）。所以 OpenLTE 的空口消息只做了完整性保护，没有机密性。
  • ROHC 没有实现。库里只有"穿插 ROHC 反馈包"控制 PDU 的壳（liblte_pdcp.cc:327），没有压缩/解压缩逻辑；头压缩在 enodeb 侧从未被调用。
  • 接收侧连 SN 校验和 MAC-I 验证都没做，handle_pdu_ready 里一行 FIXME 直接承认（LTE_fdd_enb_pdcp.cc:245）。

端到端走一遍：一条下行 RRC 消息的旅程

以 SRB1 上的一条 DL-DCCH 消息（比如 DLInformationTransfer）为例，跟在代码后面走：

第 0 步 · RRC 层（LTE_fdd_enb_rrc.cc:730-759）：填好 dl_dcch_msg 结构体，liblte_rrc_pack_dl_dcch_msg 用 ASN.1 PER 编成比特流（LIBLTE_BIT_MSG_STRUCT，单位是比特，不一定是整字节），然后 rb->queue_pdcp_sdu() + 发 PDCP_SDU_READY（:751、:756）。

第 1 步 · PDCP（LTE_fdd_enb_pdcp.cc:387-429）：把比特流字节对齐（补零，liblte_pdcp.cc:110-117），前面加 1 字节 SN 头，尾部加 4 字节 MAC-I。字节布局：

 +--------+-----------------------------+-----------+
 | PDCP头  |  RRC PDU（PER 编码，字节对齐）|  MAC-I    |
 | SN(5b) |                             |  4 字节   |
 +--------+-----------------------------+-----------+

这就是交给 RLC 的 SDU（queue_rlc_sdu，LTE_fdd_enb_pdcp.cc:418）。

第 2 步 · RLC（LTE_fdd_enb_rlc.cc:763-782）：SRB1 是 AM。若 SDU ≤ 325 字节则不分段，加 2 字节 AMD 头（D/C=1、RF=0、P=1、FI=00、E=0、SN=VT(S)）：

 +------------------+-----------------------------+
 | AMD 头 2 字节      | PDCP PDU（= RLC SDU）        |
 | D/C RF P FI E SN   |                             |
 +------------------+-----------------------------+

存入发送 buffer、启动 t-PollRetransmit，交给 MAC（queue_mac_sdu，LTE_fdd_enb_rlc.cc:889）。

第 3 步 · MAC（LTE_fdd_enb_mac.cc:679-766 → :1342）：组一个单 subheader 的 MAC PDU，LCID=1（SRB1 对应的 DCCH LCID），因为只有一个 subheader，所以 E=0 且不写 L 字段（长度靠"包剩余"倒推）：

 +-----------------+-----------------------------+
 | MAC subhdr 1B    | RLC PDU（= MAC SDU）         |
 | R R E=0 LCID=1   |                             |
 +-----------------+-----------------------------+
          （若 TBS 有富余，调度器还会插 Padding subheader，mac.cc:1361-1388）

调度器在目标 TTI 把这个比特流写进 dl_subfr->dl_allocations（LTE_fdd_enb_mac.cc:1419-1422），PHY 按 alloc 里的 TBS/MCS/PRB 发出去。至此，一条 RRC 消息总共被加了三顶帽子：1 字节 PDCP 头 + 4 字节 MAC-I、2 字节 AMD 头、1 字节 MAC subheader——开销共 8 字节。

上行接收：反向简走一遍

上行是镜像的"摘帽子"过程，从 PHY 解出 PUSCH 比特流开始：

  1. MAC：handle_pusch_decode（LTE_fdd_enb_mac.cc:605）按 RNTI 找到 user，liblte_mac_unpack_mac_pdu 解出 subheader 链（:639），按 LCID 分发：CCCH→SRB0（顺带把 SDU 存为竞争解决 ID，:795-802）、DCCH→对应的 SRB/DRB、BSR→更新上行 buffer 并触发 sched_ul。
  2. RLC：handle_pdu_ready（LTE_fdd_enb_rlc.cc:264）按 rb 的 rlc_config 分发到 TM/UM/AM 处理；AM 路径即上一节的窗口检查 + 重组 + 回 STATUS（:452-539）。
  3. PDCP：handle_pdu_ready（LTE_fdd_enb_pdcp.cc:223）按 rb 类型解头：SRB0 直接比特化交 RRC；SRB1/2 用 liblte_pdcp_unpack_control_pdu 剥掉 1 字节头和 4 字节 MAC-I（不验证，:245 FIXME）交 RRC；DRB 解长 SN 头后把 IP 包交给 GW（:293-305）。

每层依然是"从 rb 队列取、加工、queue 给上层、发 msgq 通知"同一个套路，看一遍下行再看上行几乎不用学新东西。

常见坑

  • SN 位宽三家各不相同：PDCP 控制面 SN 5 bit（liblte_pdcp.cc:106）、用户面 7/12 bit；RLC UMD 5/10 bit、AMD 固定 10 bit；PDCP 头上写的是 COUNT 的低几位，COUNT 本身 32 bit 存在 rb 里（LTE_fdd_enb_rb.cc:152-153）。看抓包时别把不同层的 SN 混为一谈。
  • FI 字段的语义是"数据区边界 vs SDU 边界"：FI 高位管"首字节是否是 SDU 开头"，低位管"末字节是否是 SDU 结尾"。分段首段是 01、末段是 10，初学者很容易记反；而且 unpack_amd_pdu 在级联 PDU 拆包后会改写每个子 PDU 的 FI（liblte_rlc.cc:458-489），调试时看到 FI 变了不要惊讶。
  • MAC subheader 顺序 ≠ payload 顺序的错觉：subheader 链在 PDU 开头连续排列，payload 依次跟在后面，第 N 个 subheader 对应第 N 个 payload；E 比特只表达"后面还有没有 subheader"。最后一个 subheader 没有 L 字段，长度靠包总长倒推（liblte_mac.cc:979-981）——自己写解析器时最常见的 off-by-one 就出在这里。
  • 比特流 vs 字节流：RRC 给 PDCP 的是 LIBLTE_BIT_MSG_STRUCT（比特粒度），PDCP 往下都是 LIBLTE_BYTE_MSG_STRUCT。字节对齐补零发生在 PDCP（liblte_pdcp.cc:110-117），抓包时 RRC PDU 末尾那几个 0 比特就是这么来的。
  • AM 窗口与模运算：SN 10 bit、窗口 512（liblte_rlc.h:51），但代码里 SN 回绕处理并不一致（比如 LTE_fdd_enb_rb.cc:776 用 % 1024，而接收 buffer 的 key 是 sn*10 这种自制编码，:582-592），改这块代码要格外小心。

小结

  • OpenLTE 把 L2 拆成"无状态编解码库（liblte）+ 有状态流水线（enodeb）"，两侧通过 rb 对象上的队列和 msgq 通知串起来。
  • 承载配置写在 rb 构造函数里：SRB0=TM，SRB1/SRB2/DRB=AM；UM 代码存在但从未启用。
  • 一条下行 RRC 消息的完整开销：PDCP 1 字节头 + 4 字节 MAC-I，RLC AMD 2 字节头，MAC 1 字节 subheader。
  • MAC 只做了复用/解复用和 FIFO 式调度，没有 LCP、没有链路自适应；HARQ 仅支持定次重传。
  • RLC AM 实现了基本的窗口、STATUS 报告和基于 t-PollRetransmit 的重传，但 segment 接收、t-Reordering 等未实现。
  • PDCP 只做完整性保护（128-EIA2），加密（EEA）与 ROHC 均未实现，接收侧连 MAC-I 校验都省略了——这是教学代码，不是商用协议栈。

第6章 物理层与 SDR 应用

前面几章我们一直在"协议"的世界里打转：RRC、NAS、状态机。这一章往下走一层，到物理层（PHY）。但先说清楚本章的定位：PHY 本身浅讲，代码地图要讲全。读完你不一定能手推 OFDM 公式，但你应该知道——想改某个功能时，去哪个文件、哪个函数。

你会熟悉的那种感觉：PHY 对协议栈就像网卡驱动对 TCP/IP 栈。你不需要懂 88E1512 的寄存器才能写 socket 程序，但当你要排查链路问题时，知道 ethtool 的每个数字从哪个寄存器来，就完全不一样了。

本章路线：先给一套最小物理层概念，再跟 LTE_fdd_dl_scan 走一遍小区搜索，然后把 liblte_phy.h 的函数地图铺开，最后看四个 SDR 应用程序怎么配合、以及 octave/ 下那个"教学版"接收机。

6.1 物理层最小知识集

帧、子帧、时隙

LTE FDD 的时间结构是严格分层的，这组常量在 liblte/hdr/liblte_phy.h:138-140 就能找到：

  • 1 个无线帧（frame）= 10 ms = 10 个子帧（LIBLTE_PHY_N_SUBFR_PER_FRAME = 10，liblte/hdr/liblte_phy.h:140）
  • 1 个子帧（subframe）= 1 ms = 2 个时隙（slot，liblte/hdr/liblte_phy.h:139）
  • 1 个时隙 = 7 个 OFDM 符号（常规 CP）
  • 系统帧号 SFN 范围 0~1023（liblte/hdr/liblte_phy.h:138），这就是 MIB 里 SFN 要除以 4 编码的原因，后面会讲

采样率是带宽的 1.92/30.72 倍频关系，头文件里每个带宽一档常量。以 20 MHz（30.72 MS/s）为例（liblte/hdr/liblte_phy.h:142-147）：每个 OFDM 符号 2048 点 FFT，第一个符号 CP 长 160 采样、其余 144，一个时隙 15360 采样，一帧 307200 采样。你做离线分析时"一帧多少字节"就是这么算出来的。

OFDM 一句话

OFDM 就是把宽带信道切成一堆 15 kHz 的窄子载波并行发，每个子载波上调一个 QAM 符号；发端做 IFFT、收端做 FFT。你熟悉的"傅里叶变换把时域变频域"在这里就是字面意义：IFFT 的输出直接就是 SDR 要发的 IQ 采样。liblte/hdr/liblte_phy.h:100-104 列了各带宽对应的 FFT 点数（128/256/512/1024/2048）。

RE 与 RB

  • RE（Resource Element）= 1 个子载波 × 1 个 OFDM 符号，是最小资源格子。
  • RB（Resource Block）= 12 个子载波 × 1 个时隙（LIBLTE_PHY_N_SC_RB_DL_NORMAL_CP = 12，liblte/hdr/liblte_phy.h:126），是调度的最小单位。

带宽和 RB 数的对应是固定的：liblte/hdr/liblte_phy.h:107-112，1.4 MHz=6 RB，一直到 20 MHz=100 RB。把它想成一张 Excel 表：列是时间（OFDM 符号），行是频率（子载波），每个单元格是一个 RE，各种信道就是往这张表的不同区域里填数据。

信道地图

往这张时频表里填数据的"写入者"一览（下行为主）：

信道/信号方向一句话作用在表里哪个位置
PSSDL粗同步 + 扇区号 N_id_2（0/1/2）子帧 0、5 中央 6 RB
SSSDL帧同步 + 组号 N_id_1（0~167）子帧 0、5 中央 6 RB，PSS 前一个符号
PBCHDL广播 MIB（24 bit）子帧 0 中央 6 RB，跨 4 帧重复
PCFICHDL告诉 UE 本子帧 PDCCH 占几个符号（CFI）每个子帧第 1 个符号的 4 个 REG
PHICHDL上行 HARQ 的 ACK/NACK第 1 个符号若干 REG
PDCCHDL调度信令（DCI）：哪个 RNTI 用哪些 RB每个子帧前 1~3 个符号
PDSCHDL真正的下行数据（SIB、寻呼、用户数据）除掉控制区后的大部分 RE
PRACHUL随机接入前导上行预留资源
PUCCHUL上行控制（ACK/NACK、CQI、SR）上行带宽两端
PUSCHUL上行数据上行大部分 RE

记住优先级最高的三个就够了：PBCH 给 MIB，PDCCH 做调度，PDSCH 搬数据。规范出处是 3GPP TS 36.211（物理信道与调制）和 36.212（编码复用）。

6.2 小区搜索：PSS → SSS → PBCH

UE 开机后两眼一抹黑：不知道基站在哪个频点、不知道帧边界在哪、不知道自己听到的是哪个小区。小区搜索就是解决这三个问题，OpenLTE 里它的完整实现是 LTE_fdd_dl_scan 的状态机。

状态枚举在 LTE_fdd_dl_scan/hdr/LTE_fdd_dl_scan_state_machine.h:65-72，一共 6 个状态：

typedef enum{
    LTE_FDD_DL_SCAN_STATE_MACHINE_STATE_COARSE_TIMING_SEARCH = 0,
    LTE_FDD_DL_SCAN_STATE_MACHINE_STATE_PSS_AND_FINE_TIMING_SEARCH,
    LTE_FDD_DL_SCAN_STATE_MACHINE_STATE_SSS_SEARCH,
    LTE_FDD_DL_SCAN_STATE_MACHINE_STATE_BCH_DECODE,
    LTE_FDD_DL_SCAN_STATE_MACHINE_STATE_PDSCH_DECODE_SIB1,
    LTE_FDD_DL_SCAN_STATE_MACHINE_STATE_PDSCH_DECODE_SI_GENERIC,
}LTE_FDD_DL_SCAN_STATE_MACHINE_STATE_ENUM;

整个状态机跑在一个 GNU Radio sync_block 的 work() 里（LTE_fdd_dl_scan/src/LTE_fdd_dl_scan_state_machine.cc:202）：采样先攒进一个大环形 buffer（SAMP_BUF_SIZE = 307200*20，即 20 帧的余量，LTE_fdd_dl_scan_state_machine.cc:54），攒够了就按当前状态处理一段。下面按状态走一遍。

第一步：粗定时 + 粗频偏

LTE_fdd_dl_scan_state_machine.cc:264-292：调 liblte_phy_dl_find_coarse_timing_and_freq_offset。它的原理是 OFDM 符号的循环前缀（CP）是符号尾部的一段复制——用你熟悉的词，这相当于用"消息头里嵌了一段和尾部相同的 sync word"来做自相关。相关峰的位置给出符号边界，相关值的相角给出载波频偏（CFO）。找不到峰就重试，MAX_ATTEMPTS = 5 次失败就换频点（LTE_fdd_dl_scan_state_machine.cc:53）。注意这里可能找到多个峰（多小区/多径），存在 timing_struct 里用 corr_peak_idx 逐个试。

第二步：PSS，精定时 + 扇区号

LTE_fdd_dl_scan_state_machine.cc:294-312：调 liblte_phy_find_pss_and_fine_timing。PSS 是 3 条已知序列（Zadoff-Chu 序列，3 个根），把接收符号和 3 条本地序列分别相关，哪条峰最高就给出 N_id_2 ∈ {0,1,2}，峰位置给出符号级精定时。成功后如果残余频偏还大于 100 Hz，再做一次频偏校正（LTE_fdd_dl_scan_state_machine.cc:304-308），然后进 SSS 搜索。

第三步：SSS，帧同步 + PCI

LTE_fdd_dl_scan_state_machine.cc:326-373：调 liblte_phy_find_sss，168 条候选序列相关，解出 N_id_1 和帧起始位置 frame_start_idx。然后拼出物理小区 ID：

chan_data.N_id_cell = 3*N_id_1 + N_id_2;   // LTE_fdd_dl_scan_state_machine.cc:336

PCI = 3×N_id_1 + N_id_2，范围 0~503，这就是你在各种网优工具里看到的"PCI"。SSS 在子帧 0 和子帧 5 的内容不同，所以解出 SSS 的同时也知道了 10 ms 帧边界在哪。如果这个 PCI 之前解过了，就 corr_peak_idx++ 回去试下一个相关峰（LTE_fdd_dl_scan_state_machine.cc:338-350）——这就是单频点多小区的来源。

第四步：PBCH，解 MIB

LTE_fdd_dl_scan_state_machine.cc:374-413 的调用链值得贴出来看，因为它是整条接收流水线的缩影：

if(LIBLTE_SUCCESS == liblte_phy_get_dl_subframe_and_ce(phy_struct, ..., 0,    // 取子帧0并做信道估计
                                                       chan_data.N_id_cell, 4, &subframe) &&
   LIBLTE_SUCCESS == liblte_phy_bch_channel_decode(phy_struct, &subframe,     // PBCH 信道译码
                                                   chan_data.N_id_cell, &N_ant,
                                                   rrc_msg.msg, &rrc_msg.N_bits, &sfn_offset) &&
   LIBLTE_SUCCESS == liblte_rrc_unpack_bcch_bch_msg(&rrc_msg, &mib))          // RRC 层解 MIB

三个函数、三个层次：PHY 采样→符号（get_dl_subframe_and_ce，内含 FFT 和基于 CRS 的信道估计）、符号→比特（bch_channel_decode，解扰/解调/解速率匹配/Viterbi/CRC）、比特→结构体（liblte_rrc_unpack_bcch_bch_msg，这就是第 3 章讲的 RRC 编解码）。注意天线数 N_ant 不是配置出来的，是解 PBCH 时试出来的——PBCH 的 CRC 掩码携带天线数，下面 Octave 部分会看到细节。

MIB 一共 24 bit，布局如下（3GPP TS 36.331；解包实现见 octave/lte_bcch_bch_msg_unpack.m:42-45）：

字段比特数含义
dl-Bandwidth3下行带宽（6 档 RB 数）
phich-Config.duration1PHICH 时长 normal/extended
phich-Config.resource2PHICH 组数因子（1/6、1/2、1、2）
systemFrameNumber8SFN 的高 8 位（低 2 位靠 PBCH 40 ms 周期内的位置推出）
spare10保留

解出 MIB 后状态机做两件关键的事：把 SFN 拼完整 sfn = (mib.sfn_div_4 << 2) + sfn_offset（LTE_fdd_dl_scan_state_machine.cc:414），以及按 MIB 里的带宽调 liblte_phy_update_n_rb_dl 重配 PHY（LTE_fdd_dl_scan_state_machine.cc:424）——此前一直按最小带宽 1.4 MHz 盲收，因为同步信号和 PBCH 永远在中央 6 RB，不需要先知道带宽。这是个很漂亮的协议设计，值得你停下来想一想为什么。

第五步：PDCCH+PDSCH，解 SIB1 和其它 SIB

SIB1 固定在偶数帧的子帧 5，用 SI-RNTI 加扰。状态机先对齐到偶数帧（LTE_fdd_dl_scan_state_machine.cc:435-439），然后 LTE_fdd_dl_scan_state_machine.cc:467-494 又是一条四段链：取子帧 → liblte_phy_pdcch_channel_decode（先解 PCFICH 拿 CFI，再盲检 PDCCH 拿 DCI 调度信息）→ liblte_phy_pdsch_channel_decode（按 DCI 指的位置解数据）→ liblte_rrc_unpack_bcch_dlsch_msg（出 SIB1）。之后进入 PDSCH_DECODE_SI_GENERIC 状态（LTE_fdd_dl_scan_state_machine.cc:527-645），逐子帧监听 SI-RNTI，把 SIB2~SIB8 都收一遍，通过 interface->send_ctrl_sibX_decoded_msg 上报给控制端口。

整个搜索流程的"失败回退"也很工程化：每一级失败都是回 COARSE_TIMING_SEARCH 重试，超过次数就 channel_not_found 换下一个频点（LTE_fdd_dl_scan_state_machine.cc:786-808）。

6.4 四个 SDR 应用程序的分工与联动

仓库根下四个以 LTE_ 开头的应用目录构成一个闭环：

                ┌────────────────────────┐
                │ LTE_fdd_dl_file_gen    │  纯软件生成下行 IQ 文件
                └──────────┬─────────────┘
                           ▼
 SDR 硬件 ──► LTE_file_recorder ──► IQ 文件 ──► LTE_fdd_dl_file_scan（离线解）
    │                                        └ 或 octave/lte_fdd_dl_receive
    └──► LTE_fdd_dl_scan（实时扫，直解直报）

LTE_file_recorder：录 IQ

最简单的 GNU Radio 流图：osmosdr source → file sink（LTE_file_recorder/src/LTE_file_recorder_flowgraph.cc:168 建 file_sink，:214 连接）。没有命令行参数，main 起来后开一个 TCP 控制端口 25000（LTE_file_recorder/hdr/LTE_file_recorder_interface.h:47，LTE_file_recorder/src/LTE_file_recorder_main.cc:63-67），用 telnet 127.0.0.1 25000 连上后发文本命令。命令解析在 LTE_file_recorder/src/LTE_file_recorder_interface.cc:199-220：

write earfcn 1930          # 设置频点（EARFCN）
write file_name /tmp/x.bin # 设置输出文件
start                      # 开录
stop                       # 停录

参数名常量在 LTE_file_recorder_interface.cc:46-47。支持 USRP/HackRF/bladeRF/RTL-SDR，探测逻辑在 LTE_file_recorder_flowgraph.cc:128-165，和 dl_scan 几乎一样的套路。录出来的就是交织的 I/Q 字节流（RTL-SDR 是 int8），也就是 Test captures/LTE_test_file_int8.bin 这种文件的来源。

LTE_fdd_dl_scan：实时扫描

带 SDR 的完整接收机。main 同样没有命令行参数，起控制端口 20000（LTE_fdd_dl_scan/hdr/LTE_fdd_dl_scan_interface.h:52，LTE_fdd_dl_scan/src/LTE_fdd_dl_scan_main.cc:63-67）。telnet 上去后的命令在 LTE_fdd_dl_scan/src/LTE_fdd_dl_scan_interface.cc:1429-1450：

write band 1                     # 扫哪个 band（整 band 的 EARFCN 列表自动生成，见 :116-123）
write dl_earfcn_list 100,300     # 或者手动指定频点列表
write repeat 1                   # 列表扫完是否循环
write enable_pcap 1              # 解出的消息写 PCAP
start / stop / shutdown

flowgraph 层（LTE_fdd_dl_scan/src/LTE_fdd_dl_scan_flowgraph.cc:121-328）负责硬件自动探测：依次试 USRP B 系列（主时钟 15.36 MHz）、USRP N、UmTRX、USRP X300、HackRF、bladeRF、RTL-SDR（:138-210 这一大段 if-else），按探测结果选采样率建状态机（:214-240），再按 EARFCN 设中心频率（:297）。之后 work() 里跑的就是 6.2 节那台状态机，解出的小区信息通过控制端口回报——send_ctrl_channel_found_begin_msg 把频点、PCI、SFN、天线数、带宽打成一行文本发出去（LTE_fdd_dl_scan_interface.cc:206-228）。

LTE_fdd_dl_file_scan：离线扫描

dl_scan 的"文件版"，但架构不同：它是一个 Python 驱动的 GNU Radio 3.7 流图。LTE_fdd_dl_file_scan/python/LTE_fdd_dl_file_scan.py:36-38 就三行核心：file_source 读文件，接一个叫 samp_buf 的块，跑。用法：

LTE_fdd_dl_file_scan.py -d int8 "Test captures/LTE_test_file_int8.bin"

-d 指定采样数据类型（int8 或 gr_complex，LTE_fdd_dl_file_scan.py:18-19）。启动后它会在 stdin 打印配置菜单等你输入采样率（LTE_fdd_dl_file_scan/src/LTE_fdd_dl_fs_samp_buf.cc:1774-1796 的 print_config，默认 fs=30.72MHz，见 :119；可设 1.92/3.84/7.68/15.36/30.72，见 :1832-1852），直接回车用默认值开始扫。

samp_buf 这个块本身是 C++ 写的（LTE_fdd_dl_fs_samp_buf.cc，1852 行），状态机和 dl_scan 的几乎同构——枚举在 LTE_fdd_dl_file_scan/hdr/LTE_fdd_dl_fs_samp_buf.h:89-95，六态一一对应。Python 怎么能调 C++ 块？靠 SWIG：LTE_fdd_dl_file_scan/src/LTE_fdd_dl_fs.i:11 一行 GR_SWIG_BLOCK_MAGIC(LTE_fdd_dl_fs,samp_buf); 把头文件包成 Python 模块，src/__init__.py 再 from LTE_fdd_dl_fs import *。这就是 GNU Radio 3.7 时代 C++ 块的标准封装方式。

LTE_fdd_dl_file_gen：下行信号发生器

镜像结构：Python 流图里 samp_buf 块当信源，接 file_sink 写文件（LTE_fdd_dl_file_gen/python/LTE_fdd_dl_file_gen.py:36-38），SWIG 接口同样是 LTE_fdd_dl_file_gen/src/LTE_fdd_dl_fg.i:11。用法：

LTE_fdd_dl_file_gen.py -d int8 /tmp/my_lte.bin

运行后先在 stdin 配参数——带宽、采样率、band、帧数、天线数、PCI、MCC/MNC、TAC、负载百分比等等（菜单见 LTE_fdd_dl_file_gen/src/LTE_fdd_dl_fg_samp_buf.cc:761-919）。C++ 块内部手工填好 MIB/SIB1/SIB2 结构体（默认值在 LTE_fdd_dl_fg_samp_buf.cc:125-208），然后逐子帧走完整的发送链：PSS/SSS 映射（:341-345）→ MIB 打包 + BCH 编码（:362-364）→ SIB 打包 → PDCCH 编码（:550）→ PDSCH 编码（:559）→ liblte_phy_create_dl_subframe 出 IQ（:569）。

这四个程序合起来就是一个不需要任何硬件的 PHY 教学闭环：file_gen 造信号 → file_scan 解信号 → 对不上就去看 octave 参考实现，或者直接拿 Test captures/LTE_test_file_int8.bin 这份真实空口录音。

6.5 Octave 接收机：看得见的流水线

octave/ 目录 60 多个 .m 脚本是一个"教学版"LTE 收发机，和 liblte_phy.cc 功能对应但可读性好得多——矩阵操作直白，没有性能优化噪音。跑法（仓库自带测试文件，30.72 MS/s int8）：

fid = fopen("Test captures/LTE_test_file_int8.bin", "r");
iq_vec = fread(fid, inf, "int8");
iq_split_vec = reshape(iq_vec, 2, []);
addpath("octave");
lte_fdd_dl_receive(iq_split_vec(1,:) + i*iq_split_vec(2,:));

octave/lte_fdd_dl_receive.m:37 是主函数，流水线就是 6.2 节的脚本版：

  1. 粗同步：find_coarse_time_and_freq_offset（lte_fdd_dl_receive.m:57，内部函数在 :181-265）——CP 自相关，顺带估计分数频偏并校正（:59-61）。
  2. PSS：find_pss_and_fine_timing（:65，实现在 :267-333）——本地生成 3 条 PSS（octave/lte_generate_pss.m），逐符号相关找峰，得到 N_id_2 和精定时。
  3. SSS：find_sss（:76，实现在 :335-381）——168×2 条候选（子帧 0/5 两种，octave/lte_generate_sss.m）相关，得 N_id_1，拼 PCI = 3*N_id_1+N_id_2（:93）。
  4. 信道估计：get_subframe_and_ce（:98，实现在 :383-601）——对每个子帧做 FFT 变到频域，用 CRS（octave/lte_generate_crs.m）做信道估计：CRS 位置的接收值除以本地 CRS 得信道响应，再线性插值填满整个时频格（:450-473）。这是全脚本最长的函数，值得读一遍——"信道估计"听起来玄，说白了就是拿已知导频点除一除、再插值。
  5. PBCH 译码：decode_mib（:99，实现在 :603-664）——解资源映射、解扰（lte_generate_prs_c 生成扰码）、按 1/2/4 天线尝试发送分集译码，PBCH 一个编码块跨 4 帧所以再按 mod-4 相位试 4 次（:634-662）。
  6. PDCCH/PDSCH：decode_pdcch（:144，实现在 :666 起）先解 PCFICH 拿 CFI（lte_cfi_channel_decode），再避开盘点 PCFICH/PHICH/CRS 占掉的 REG，组 CCE，在公共搜索空间用 SI-RNTI 盲检 DCI 1A/1C；然后 decode_pdsch（:158）按 DCI 解数据，最后 lte_bcch_dlsch_msg_unpack + lte_sib1_unpack 出 SIB1 并打印（:161-170）。

编码链的底层积木也都摆在你面前。以 BCH 为例，octave/lte_bch_channel_decode.m:30-48 四步走完 36.212 的 BCH 译码：

d_bits = lte_rate_unmatch_conv(bch_bits, 40);            % 解速率匹配，恢复 40 个编码比特
d_bits = reshape(d_bits, 1, []);
c_bits = cmn_viterbi_decode(d_bits, 7, 3, [133, 171, 165]); % Viterbi，约束长度7、码率1/3
a_bits = c_bits(1:24);                                    % 24 bit MIB
p_bits = c_bits(25:40);                                   % 16 bit CRC
calc_p_bits = lte_calc_crc(a_bits, 16);                   % 重算 CRC

后面 :46-68 用三种 CRC 掩码（全 0/全 1/0101…）逐一比对，比对上哪种就说明基站是 1/2/4 天线——这就是 6.2 节说的"天线数是试出来的"。Viterbi 本体在 octave/cmn_viterbi_decode.m，卷积编码在 cmn_conv_encode.m，速率匹配/解匹配在 lte_rate_match_conv.m / lte_rate_unmatch_conv.m，Turbo 码对应 lte_turbo_encode.m / lte_turbo_decode.m，CRC 在 lte_calc_crc.m。想改哪个环节，直接改脚本重跑就行——这是用 C++ 版本很难获得的迭代速度。

6.6 想继续深入 PHY 的话

到这里你手里已经有三张地图：函数地图（6.3）、状态机（6.2）、可执行的参考实现（6.5）。再往下走，建议的顺序：

  1. 规范：3GPP TS 36.211（物理信道与调制，回答"每个 RE 放什么"）和 36.212（复用与信道编码，回答"比特怎么变符号"）。这两本对照 octave/ 脚本读，几乎每个公式都能在脚本里找到对应行。调度过程看 36.213。
  2. 信号处理补课：你至少需要——复数基带与 IQ 的含义、DFT/FFT、相关与匹配滤波（PSS/SSS 检测就是它）、卷积码与 Viterbi、最小二乘信道估计与插值。顺序上建议先把 lte_fdd_dl_receive.m 逐行啃透，遇到不懂的再去查理论，比先读书后看代码快得多。
  3. 回到 C 实现：liblte/src/liblte_phy.cc（一万四千行级别）做工程化版本——SSE 优化的 Turbo/Viterbi、fftw 集成。对照 Octave 版本读，重点看同一算法在"正确性优先"和"性能优先"下长相差多少。
  4. 动手实验：用 LTE_fdd_dl_file_gen 生成不同 PCI/带宽的信号，用 file_scan 和 Octave 各解一遍；然后试试在 Octave 里给信号加噪声、加频偏，看哪一级先崩——这比任何教科书都能教你"同步为什么难"。

小结

  • LTE FDD 帧结构：10 ms 帧 = 10 子帧 = 20 时隙，带宽决定 RB 数（6~100），所有时频常量都在 liblte/hdr/liblte_phy.h 开头。
  • 小区搜索是 PSS（扇区号+定时）→ SSS（组号+帧边界）→ PBCH（MIB）的串行流水线，LTE_fdd_dl_scan/src/LTE_fdd_dl_scan_state_machine.cc 的六态状态机就是它的完整实现；PCI = 3×N_id_1 + N_id_2，MIB 只有 24 bit。
  • liblte_phy.h 按信道分组暴露约 30 个入口函数：scan 只用"同步+下行译码"一小组，enodeb 用收发全套，调度计算函数给 MAC 用。
  • 四个 SDR 应用构成闭环：LTE_file_recorder（端口 25000）录 IQ、LTE_fdd_dl_file_scan 离线解、LTE_fdd_dl_scan（端口 20000）实时解、LTE_fdd_dl_file_gen 生成信号；后两者是纯 C++ 加 TCP 控制口，中间两者是 Python+SWIG 的 GNU Radio 流图。
  • octave/lte_fdd_dl_receive.m 是整条接收链的可执行教科书，配 Test captures/LTE_test_file_int8.bin 可以直接跑；BCH 译码四步（解速率匹配→Viterbi→CRC→掩码试天线数）是理解 36.212 编码链的最好入口。
  • 深入路线：36.211/36.212 + Octave 脚本互相对照，再回 liblte_phy.cc 看工程化实现。

第 7 章 支撑组件与内部库：胶水层全景

前面几章我们沿着信令面（RRC/NAS）、用户面（MAC/RLC/PDCP）、物理层一路读下来，会反复撞到一些"边角色"：LIBLTE_BIT_MSG_STRUCT、LTE_fdd_enb_msgq、cnfg_db->get_param()、libtools_scoped_lock……它们不属于任何一层协议，却撑起了整个系统。本章把这些基础设施逐个讲透。读完这一章，仓库里应该没有任何一个文件是你没概念的了。

typedefs.h：编码风格的地基

全仓库所有代码共享一份类型定义 cmn_hdr/typedefs.h，它就一件事：把定宽整数 typedef 成不带 _t 的短名字（cmn_hdr/typedefs.h:50-57）：

typedef char               int8;
typedef unsigned char      uint8;
typedef short              int16;
typedef unsigned short     uint16;
typedef int                int32;
typedef unsigned int       uint32;
typedef long long          int64;
typedef unsigned long long uint64;

你熟悉的 std::uint32_t 对应这里的 uint32。这份 2012 年写的代码比 C99 的 <stdint.h> 普及更早，作者自己造了一套，于是 uint32/int64 成了全仓库的"官方语言"。顺着这个头文件你还能看到整个项目的风格基座：

  • 所有类型/枚举/宏一律全大写加前缀：库内是 LIBLTE_*、LIBTOOLS_*，eNodeB 应用内是 LTE_FDD_ENB_*，一眼能看出归属；
  • 每个枚举的最后一项都是 _N_ITEMS，后面紧跟一个同名的 *_text[][] 字符串表，用于日志打印（比如 libtools_socket_wrap_error_text，libtools/hdr/libtools_socket_wrap.h:68-72）；
  • 每个文件开头都是同一个五段式模板：INCLUDES / DEFINES / TYPEDEFS / GLOBAL VARIABLES / CLASS IMPLEMENTATIONS，这是从 GNU Radio 时代继承的习惯。

liblte 的消息缓冲区：全仓库的"物流系统"

BIT_MSG 与 BYTE_MSG

先纠正一个容易望文生义的地方：liblte_interface.h/cc 里装的其实是 band 和 EARFCN 换算表，消息缓冲区结构定义在隔壁的 liblte_common.h。这两个结构是全仓库协议层的"标准集装箱"（liblte/hdr/liblte_common.h:68-76）：

typedef struct{
    uint32 N_bits;
    uint8  msg[LIBLTE_MAX_MSG_SIZE];
}LIBLTE_BIT_MSG_STRUCT;

typedef struct{
    uint32 N_bytes;
    uint8  msg[LIBLTE_MAX_MSG_SIZE];
}LIBLTE_BYTE_MSG_STRUCT;

要点有三个：

  • msg 数组的每个元素只装 1 个比特（BIT_MSG）或 1 个字节（BYTE_MSG），不是紧凑打包的位流。这让编解码代码完全不用管字节对齐，代价是内存浪费——LIBLTE_MAX_MSG_SIZE 固定为 5512（liblte/hdr/liblte_common.h:54，注释里作者自己写了 "This was chosen arbitrarily"）。
  • 控制面（RRC/NAS/PHY 信道）走 BIT_MSG，因为 ASN.1 PER 编码天然是比特流；用户面 IP 包走 BYTE_MSG，比如 GW 模块收 IP 包用的就是它（LTE_fdd_enodeb/src/LTE_fdd_enb_gw.cc:267）。
  • 结构里没有长度上限检查的责任方，写爆数组全靠调用方自觉——读代码时记住这一点。

比特流的"游标 API"

liblte_common.cc 里只有两个函数，但 RRC/NAS 的每一行编解码都建立在它们之上。打包方向（liblte/src/liblte_common.cc:62-73）：

void liblte_value_2_bits(uint32 value, uint8 **bits, uint32 N_bits)
{
    uint32 i;
    for(i=0; i<N_bits; i++)
        (*bits)[i] = (value >> (N_bits-i-1)) & 0x1;
    *bits += N_bits;
}

它干的事等价于网络编程里的 memcpy + advance：把 value 的高 N 位逐位（MSB first）写进 bits 指向的位置，然后把指针本身前移 N 格。注意参数是 uint8 **——指针的指针，就是为了能移动调用方的游标。解包方向 liblte_bits_2_value（liblte/src/liblte_common.cc:80-92）完全对称：读 N 位拼成一个 uint32，游标前移并返回值。

你在前面章节看到的 RRC pack/unpack 代码，本质就是这两个函数按 36.331 的字段顺序反复调用。MSB first 的顺序也正是 PER 编码的约定。

EARFCN 与频率换算

liblte_interface.h/cc 把 36.101 的频段表和 EARFCN 范围表直接硬编码成了几个大数组：liblte_interface_band_text[]/band_num[]（liblte/hdr/liblte_interface.h:106-118，对应 36.101 频段定义）、first_dl_earfcn[]/last_dl_earfcn[]（liblte/hdr/liblte_interface.h:132-151，对应 36.101 的 EARFCN 范围）。换算公式在 liblte_interface_dl_earfcn_to_frequency（liblte/src/liblte_interface.cc:101-116）：先线性扫描找到 EARFCN 落在哪个 band，再按 36.101 的公式计算：

F_dl = F_dl_low[i] + 100000 * (dl_earfcn - N_offs_dl[i]);   // 单位 Hz，步进 100 kHz

FDD 的上下行 EARFCN 换算简单得近乎粗暴：同一个 band 内下行 + 18000 就是上行（liblte/src/liblte_interface.cc:124-132），TDD 频段则直接相等。这两个函数是 cnfg_db 里 "改 dl_earfcn 自动带出 ul_earfcn 和中心频率" 的底层支撑，后面讲 cnfg_db 时会接回来。

libtools 四件套

libtools/ 是 2015-2017 年间从各模块里抽出来的公共工具库，一共四个组件，编译成 libtools（库名 tools，见 libtools/CMakeLists.txt:2-7）。

scoped_lock：最小的 RAII

全仓库只有这一处锁封装（libtools/src/libtools_scoped_lock.cc:57-77）：构造函数对 sem_t 做 sem_wait 或对 pthread_mutex_t 做 pthread_mutex_lock，析构函数对称释放。这就是你熟悉的 std::lock_guard，只是手工版，且同时兼容两种原语。典型用法随处可见，例如单例的 get_instance（LTE_fdd_enodeb/src/LTE_fdd_enb_timer_mgr.cc:72-82）：

LTE_fdd_enb_timer_mgr* LTE_fdd_enb_timer_mgr::get_instance(void)
{
    libtools_scoped_lock lock(timer_mgr_instance_mutex);
    if(NULL == instance)
        instance = new LTE_fdd_enb_timer_mgr();
    return(instance);
}

注意项目用二进制信号量（sem_init(&x, 0, 1)）当互斥锁用的场景比 mutex 还多——这是历史包袱，2015 年有一次从 boost::mutex 到 sem_t 的全量迁移（见 libtools_socket_wrap.cc 头部 12/06/2015 的修订记录）。

socket_wrap：telnet 控制台的地基

eNodeB 的运维面是两个 TCP 文本端口：控制口 30000、debug 口 30001（LTE_fdd_enodeb/hdr/LTE_fdd_enb_interface.h:73-74）。它们的实现基础就是 libtools_socket_wrap。构造函数的参数表把设计说得很清楚（libtools/hdr/libtools_socket_wrap.h:102-109）：给 IP、端口、server/client 类型，外加四个回调——handle_msg / handle_connect / handle_disconnect / handle_error，全是指向自由函数的函数指针，靠 static 成员函数绕回对象（LTE_fdd_enodeb/src/LTE_fdd_enb_interface.cc:258-265）。

server 端收包循环是教科书式的 select 单线程模型（libtools/src/libtools_socket_wrap.cc:221-230）：

while(1)
{
    select_timeout.tv_sec  = 0;
    select_timeout.tv_usec = 500000;
    tmp_fds                = fds;
    if(select(fd_max+1, &tmp_fds, NULL, NULL, &select_timeout) == -1)
        break;
    ...
}

随后按 fd 分发：监听 fd 可读就 accept 并把状态切到 CONNECTED（libtools/src/libtools_socket_wrap.cc:239-262）；连接 fd 可读就 read，然后手工剥掉行尾的 \n / \r，按行调用 handle_msg（libtools/src/libtools_socket_wrap.cc:298-324）——所以控制台命令天然是"一行一条"。两个提醒：这个类只支持单客户端（listen backlog 为 1，见 libtools/src/libtools_socket_wrap.cc:209）；client 端线程是空的 FIXME（libtools/src/libtools_socket_wrap.cc:337-341），全项目只用到 server 模式。发送侧 send() 就是加锁后的 write（libtools/src/libtools_socket_wrap.cc:173-189）。

ipc_msgq：跨进程的胖管道

libtools_ipc_msgq 包的是 boost::interprocess::message_queue，用于 eNodeB 和外部 UE 进程之间的直通通信（mac_direct_to_ue / phy_direct_to_ue 调试模式）。消息格式是"类型枚举 + 匿名 union"（libtools/hdr/libtools_ipc_msgq.h:100-111），和 eNodeB 内部消息队列同一套路。实现上有三个细节值得记住：

  • 接收端用 open_or_create 建队列，容量固定 100 条、每条固定 sizeof(LIBTOOLS_IPC_MSGQ_MESSAGE_STRUCT)（libtools/src/libtools_ipc_msgq.cc:120-123）——union 的尺寸就是最大成员 phy_samps_msg（里面塞了 4 天线的 I/Q 缓冲，libtools/hdr/libtools_ipc_msgq.h:92-98），所以这条队列的消息相当大；
  • 发送端每次 open_only + try_send，队列满了直接丢（libtools/src/libtools_ipc_msgq.cc:95-110）；
  • 析构时先发一条 KILL 消息再 cancel/join 接收线程（libtools/src/libtools_ipc_msgq.cc:83-90），KILL 在接收循环里把 not_done 置假退出（libtools/src/libtools_ipc_msgq.cc:137-140）。

回调机制是手写版的 std::bind：libtools_ipc_msgq_cb 存一个 void* 对象指针加自由函数指针，再用模板 wrapper 把成员函数指针转成自由函数（libtools/hdr/libtools_ipc_msgq.h:118-133）。这套"cb 结构体 + 模板 wrapper"的模式在 eNodeB 的 msgq 和 timer 里又原样复制了两遍。使用点在 MAC 和 PHY 里：开启 direct-to-UE 模式时各自创建名为 enb_ue 的队列（LTE_fdd_enodeb/src/LTE_fdd_enb_mac.cc:187、LTE_fdd_enodeb/src/LTE_fdd_enb_phy.cc:322）。

helpers：字符串 ↔ 数字的苦力

libtools_helpers 是控制台参数解析的底层：to_string 一族重载（含定宽补零和字节数组转大写 hex，libtools/src/libtools_helpers.cc:103-128）、to_number 一族（十进制逐位累乘，libtools/src/libtools_helpers.cc:171-196；hex 按 nibble 拼字节，libtools/src/libtools_helpers.cc:197-235）、输入校验 is_string_valid_as_number（libtools/src/libtools_helpers.cc:266-303），外加日志时间戳 get_formatted_time（libtools/src/libtools_helpers.cc:242-258）。控制台里 write mcc 001 能变成数字，走的就是这里的 is_string_valid_as_number + to_number。

eNodeB 内部消息队列：LTE_fdd_enb_msgq

eNodeB 各层之间不直接互相调用，全部走 LTE_fdd_enb_msgq。消息格式同样是"类型 + 目标层 + union"（LTE_fdd_enodeb/hdr/LTE_fdd_enb_msgq.h:372-376）：

typedef struct{
    LTE_FDD_ENB_MESSAGE_TYPE_ENUM type;
    LTE_FDD_ENB_DEST_LAYER_ENUM   dest_layer;
    LTE_FDD_ENB_MESSAGE_UNION     msg;
}LTE_FDD_ENB_MESSAGE_STRUCT;

type 枚举本身就是一张协议栈交互图，注释按方向分组写好了（"PHY -> MAC Messages"、"PDCP -> GW Messages"……见 LTE_fdd_enodeb/hdr/LTE_fdd_enb_msgq.h:85-129）。与 ipc_msgq 的跨进程队列不同，这里用 boost::circular_buffer（容量 100）加两个信号量做进程内队列（LTE_fdd_enodeb/src/LTE_fdd_enb_msgq.cc:91-98）。send 侧是标准的"sync_sem 保护环形缓冲、msg_sem 计数通知"（LTE_fdd_enodeb/src/LTE_fdd_enb_msgq.cc:140-158）；接收线程 attach_rx 之后才创建（LTE_fdd_enodeb/src/LTE_fdd_enb_msgq.cc:121-127），它做了两件实时性相关的事：

  • 按构造时传入的 prio 设置 SCHED_FIFO 调度优先级（LTE_fdd_enodeb/src/LTE_fdd_enb_msgq.cc:192-197）；
  • 用 pthread_setaffinity_np 把自己钉在"除最后一个核之外"的所有核上——最后一个核留给 PHY/Radio（LTE_fdd_enodeb/src/LTE_fdd_enb_msgq.cc:199-202）。

所有队列在 handle_start() 里一次性 new 出来，一共 13 条，名字直接标出方向：phy_to_mac、rrc_to_mme、pdcp_to_gw……（LTE_fdd_enodeb/src/LTE_fdd_enb_interface.cc:992-1004）。这就是第 3 章那张多线程架构图的物理实现。

timer 与 timer_mgr：1ms 心跳驱动的定时器框架

定时器分两层。LTE_fdd_enb_timer 本身只是个计数器：构造时记下到期毫秒数和回调（LTE_fdd_enodeb/src/LTE_fdd_enb_timer.cc:79-87），increment() 加一、expired() 比较（LTE_fdd_enodeb/src/LTE_fdd_enb_timer.cc:99-113），完全没有线程——它不会自己跑。

驱动它的是 LTE_fdd_enb_timer_mgr（单例，LTE_fdd_enodeb/src/LTE_fdd_enb_timer_mgr.cc:72-82）。启动时它挂到 MAC→timer 的 msgq 上（LTE_fdd_enodeb/src/LTE_fdd_enb_timer_mgr.cc:121-135），而 MAC 每收到 PHY 的一个 ready-to-send（即每 TTI，1ms）就发一条 TIMER_TICK（LTE_fdd_enodeb/src/LTE_fdd_enb_mac.cc:376-389）。timer_mgr 收到 tick 后遍历所有定时器加一、收集到期的、统一回调并删除（LTE_fdd_enodeb/src/LTE_fdd_enb_timer_mgr.cc:236-266）。也就是说：整个 eNodeB 的定时器精度锚定在 PHY 的 1ms 子帧时钟上，无线一停，所有定时器停摆。这个设计很 LTE——协议里一切时间本来就以子帧为单位。

注册接口是 start_timer(m_seconds, cb, &timer_id)（LTE_fdd_enodeb/src/LTE_fdd_enb_timer_mgr.cc:149-174），id 从 0 递增分配。实际使用者包括：user_mgr 给每个新用户开 5 秒的 C-RNTI 预留定时器（LTE_fdd_enodeb/src/LTE_fdd_enb_user_mgr.cc:300）、user 级的 inactivity timer（LTE_fdd_enodeb/src/LTE_fdd_enb_user.cc:758）、RLC 的 t_PollRetransmit 100ms（LTE_fdd_enodeb/src/LTE_fdd_enb_rb.cc:791，对应 36.322 的轮询重传定时器）。需要说明的是，36.331 里 UE 侧的 T300/T301/T310 是跑在 UE 上的，eNodeB 侧这套框架承载的是 RLC/MAC/用户管理自己的定时需求，别去代码里找 T300。

cnfg_db：运行参数的单一事实来源

存储模型

LTE_fdd_enb_cnfg_db 是又一个单例，内部就三个按值类型分开的 map（LTE_fdd_enodeb/hdr/LTE_fdd_enb_cnfg_db.h:146-148）：

std::map<LTE_FDD_ENB_PARAM_ENUM, double> var_map_double;
std::map<LTE_FDD_ENB_PARAM_ENUM, int64>  var_map_int64;
std::map<LTE_FDD_ENB_PARAM_ENUM, uint32> var_map_uint32;

参数没有注册表，"某个参数属于哪个 map"完全由构造函数里写默认值的位置决定（LTE_fdd_enodeb/src/LTE_fdd_enb_cnfg_db.cc:125-175）：bandwidth 是 double，dl_earfcn/tx_gain 是 int64，mcc/mnc/ip_addr 是 uint32。默认值也值得看一眼：band 1、10 MHz、50 RB、单天线、MCC=0xFFFFF001（即 "001"，0xF 是填充位）。MCC/MNC 的 nibble 布局（对应 24.301 中 PLMN identity 的数字打包思路）：

set_param 的级联魔法

set_param 不只是存值，它维护参数间的派生关系（LTE_fdd_enodeb/src/LTE_fdd_enb_cnfg_db.cc:183-233）：

  • 写 n_id_cell 自动拆出 n_id_1/n_id_2（LTE_fdd_enodeb/src/LTE_fdd_enb_cnfg_db.cc:197-200，即 PCI = 3×N_id_1 + N_id_2，36.211）；
  • 写 dl_earfcn 自动重算 ul_earfcn 和上下行中心频率——用的正是前面 liblte_interface 的换算函数（LTE_fdd_enodeb/src/LTE_fdd_enb_cnfg_db.cc:201-204）；
  • 写 tx_gain/rx_gain 会直接穿透到 radio 对象实时生效（LTE_fdd_enodeb/src/LTE_fdd_enb_cnfg_db.cc:220-223）；
  • 写 bandwidth 会按档位同步 N_rb 和 RRC 的 DL_BW 枚举（LTE_fdd_enodeb/src/LTE_fdd_enb_cnfg_db.cc:246-274）。

控制台 → cnfg_db → 各模块：完整链路

你在 telnet 里敲 write dl_earfcn 1575，数据流是这样的：

  1. socket_wrap 的 server 线程按行收到字符串，回调进 LTE_fdd_enb_interface::handle_ctrl_msg，按关键字分发到 handle_write（LTE_fdd_enodeb/src/LTE_fdd_enb_interface.cc:690-734）；
  2. handle_write 在 var_map（键是参数名字符串）里查到 LTE_FDD_ENB_VAR_STRUCT，按声明的类型（DOUBLE/INT64/HEX/UINT32）解析值、查只读标志，再交给 write_value 做上下界检查（LTE_fdd_enodeb/src/LTE_fdd_enb_interface.cc:887-970；VAR_STRUCT 布局见 LTE_fdd_enodeb/hdr/LTE_fdd_enb_interface.h:253-263）；
  3. write_value 调 cnfg_db->set_param(...) 落库并触发上述级联；
  4. 各模块在需要时 get_param 读取——比如 radio 启动时读 EARFCN/带宽/天线数（LTE_fdd_enodeb/src/LTE_fdd_enb_radio.cc:1101-1110），construct_sys_info 把参数翻译成 MIB/SIB 结构（LTE_fdd_enodeb/src/LTE_fdd_enb_cnfg_db.cc:426 起）。

如果开了 use_cnfg_file，每次 set_param 还会把全量参数写回 /tmp/LTE_fdd_enodeb.cnfg_db（LTE_fdd_enodeb/src/LTE_fdd_enb_cnfg_db.cc:980-1082）；下次启动时 read_cnfg_file 逐行读文件并回调 handle_write（LTE_fdd_enodeb/src/LTE_fdd_enb_cnfg_db.cc:959-979）——配置文件和 telnet 命令复用同一条解析路径，很省代码。这个回放在 main() 里执行（LTE_fdd_enodeb/src/LTE_fdd_enb_main.cc:70-72）。

radio.cc：UHD 收发如何被包成模块接口

LTE_fdd_enb_radio 是门面类，底下按设备分三个实现类：no_rf（空跑时钟）、usrp_b2x0（UHD）、bladerf（libbladeRF），见 LTE_fdd_enodeb/hdr/LTE_fdd_enb_radio.h:115-192。start() 从 cnfg_db 读参数后按选中的设备类型分发（LTE_fdd_enodeb/src/LTE_fdd_enb_radio.cc:1115-1158），最后拉起一个 radio_thread（LTE_fdd_enodeb/src/LTE_fdd_enb_radio.cc:1161）。

UHD 的 setup 就一段标准流程（LTE_fdd_enodeb/src/LTE_fdd_enb_radio.cc:249-258）：set_tx_rate/set_rx_rate 设采样率，set_tx_freq/set_rx_freq 用 liblte_interface_*_earfcn_to_frequency 把 EARFCN 换算成 Hz，再设增益、开流。收发主循环用 UHD 的时间戳做精确对齐：TX 按 next_tx_ts += N_samps/采样率 排产（LTE_fdd_enodeb/src/LTE_fdd_enb_radio.cc:341-366），RX 每收满一个子帧的采样就回调 PHY 的 radio_interface()——PHY 是被 radio 线程以 1ms 节奏"踢"着走的，没有自己的时钟。

gw.cc：用户面数据怎么出基站

OpenLTE 没有实现 S1 接口的 GTP-U，数据面出口是一个 Linux TUN 设备——基站进程自己在内核里注册一块虚拟网卡 tun_openlte，UE 的 IP 包从这里进出主机网络栈（配合根目录的 enodeb_nat_script.sh 做 NAT 转发）。

构建系统：谁链接谁

顶层 CMakeLists.txt 依次 add_subdirectory 七个组件（CMakeLists.txt:160-166），并在开头集中 find_package 了全部外部依赖：Boost、GNURadio 3.7、Osmosdr、UHD、LibbladeRF、FFTW3F、PolarSSL（CMakeLists.txt:91-117），缺任何一个直接 FATAL_ERROR。链接关系一张图：

  • liblte/CMakeLists.txt:2-12：库 lte（common/interface/phy/mac/rlc/pdcp/rrc/mme/security），外加一个 liblte_common_test 单测（liblte/CMakeLists.txt:15-19，顶层开了 enable_testing()，CMakeLists.txt:27）；
  • libtools/CMakeLists.txt:2-7：库 tools（四件套），include 了 liblte/hdr——因为 ipc_msgq 的消息结构里嵌了 LIBLTE_PHY_* 常量；
  • LTE_fdd_enodeb/CMakeLists.txt:7-27：可执行文件 LTE_fdd_enodeb，target_link_libraries(... lte fftw3f tools pthread rt polarssl uhd bladerf boost gnuradio...)，是所有库的汇点；
  • 其余四个目录（dl_scan / dl_file_scan / dl_file_gen / file_recorder）都只依赖 lte 加各自的 SDR 库。

要把一个新模块加进构建，步骤是固定的：在顶层加 find_package（若有新外部依赖）和 add_subdirectory；在子目录 CMakeLists.txt 里 add_executable/add_library，include_directories 指向 liblte/hdr、libtools/hdr、cmn_hdr；target_link_libraries 按"应用链接 lte + tools，库之间不互链"的原则接上。enodeb 内部加新协议层则更轻：把 .cc 加进 LTE_fdd_enodeb/CMakeLists.txt:8-26 的源文件列表，在 msgq.h 里加消息类型，在 handle_start() 里加队列和 start 调用即可。

小结

  • cmn_hdr/typedefs.h 定义了全仓库的类型方言（uint32 等）和"枚举 + _N_ITEMS + _text 表"的风格约定。
  • LIBLTE_BIT/BYTE_MSG_STRUCT（liblte_common.h）是全仓库的消息集装箱，liblte_value_2_bits/liblte_bits_2_value 的"游标前移"API 是所有编解码的地基；band/EARFCN 表在隔壁 liblte_interface。
  • libtools 四件套：scoped_lock 是手工版 std::lock_guard；socket_wrap 是控制台两个 TCP 端口的 select 服务器；ipc_msgq 是跨进程胖管道；helpers 负责字符串和数字互转。
  • eNodeB 内部靠 13 条 LTE_fdd_enb_msgq 环形缓冲队列解耦；所有定时器挂在 PHY 的 1ms TTI 心跳上，无线停则定时器停。
  • cnfg_db 用三个 map 存参数，set_param 负责级联（EARFCN→频率、带宽→RB 数）；配置文件和 telnet 命令复用同一条 handle_write 路径。
  • radio 用 UHD 时间戳对齐收发并以 1ms 节奏驱动 PHY，采样率恒为带宽档位对应的 1.92~30.72 MHz；gw 用 TUN 设备代替 GTP-U，把数据面折叠进本机网络栈。
